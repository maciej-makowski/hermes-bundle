# Design docs with an adversarial review loop

## When to Use

Use when the operator asks for a research/design doc, deployment plan, or hardening review of a design — anything written as a document and then defended. Do NOT use for ordinary task execution, PR code review (github skills), or quick answers. DO use it when the operator asks where a design stands ('is X ready for review?', 'did X publish?', 'where did we leave X?') — the loop and landing state that question turns on is this skill's machinery; answer from live repo checks (references/pitfalls.md, publishing/registry/status section), not from the local header or a fact row alone.

Trigger breadth: when the operator says "design X" — even without the word "doc" — treat it as a doc+loop request. A chat-inline design plus artifact files is not the deliverable (his test: "Where's the design doc? Has it been reviewed?"); the artifacts accompany the doc, never replace it. Sketch inline only when he explicitly asks for a sketch.

the operator's standing protocol for design/plan documents: research subagent → write doc → dedicated adversarial-review subagent → patch → re-review, until the reviewer reports `CONSENSUS: reached` or a 15-iteration cap. Final doc publishes to the design repo `<your-org>/design-docs` (canonical source of truth): branch `design/<name>` → adversarial loop → PR → squash-merge, where the merge is the checkpoint (the publish mechanics live in `references/publishing-and-target-identity.md`). Proton Drive `/design-docs` is a frozen pre-migration archive — never upload new docs there.

Unslop scope (the operator's clarification, Nov 1 2026): the unslop requirement is forward-looking — it applies to any design currently PROPOSED and to every future design. Already ADOPTED or WITHDRAWN designs are exempt; no retroactive pass.

## Procedure

1. **Clarify ambiguous topic names first** (one clarify call) — a wrong expansion sends the researcher down the wrong rabbit hole. Ambiguity also covers which artifact a name denotes: verify a renamed or sibling-shared name against live evidence (probe the live hostname, read the repo's self-description) before dispatching, and if research contradicts the assumed referent, stop and re-confirm the target with the user before building on it. Do not guess acronyms. The same rule runs one level up when the task names a deployed app: before dispatching research, resolve the name→repo→domain→app mapping with a cheap pre-flight (repo description read plus one live probe of the domain, or one row in the clarify card) — memory about what an app 'is' goes stale exactly when a repo is renamed or a new app takes the old name, and an unverified mapping costs the whole research dispatch, not one finding. Decode two answer shapes before dispatching: a free-text reply that overrides the offered choices is a locked requirement, passed verbatim into the researcher dispatch (not re-interpreted back into the closest option); and a bare one-token reply that arrives right after the clarify card is usually an accidental duplicate answer to one of its questions — decode it with one small clarify listing the plausible readings instead of guessing or re-running the batch — a reply that matches NO offered option (an app-approval button artifact, a UI label) is the same noise class; and a card response whose text is an attachment filename is the FILE arriving (the gateway records the attachment as the reply text), not a selection — take the attachment as content for whichever question it answers, mark the untouched selections unanswered, and let the partially-answered-card rule fold them as D-row assumed defaults; and a response that ADDRESSES a different question than the slot it landed in (a clarification of one question recorded as another's answer) resolves the addressed question — fold it there verbatim, mark the slot's question unanswered, and re-ask ONLY that displaced question alone (recommended option first) rather than re-running the whole card; and an explicit self-explanatory reply (it names the question and the change in words) needs no re-ask — apply it and restate the full decoded decision set back to the user so a misread can be vetoed at zero cost; and a reply that echoes one option's scope word ('it should be per-bot') can attach that word to the wrong axis: a posture choice (the setting varies per bot) versus an ownership claim (each bot gets its own key/resource). Decode both readings, restate each with the concrete mechanism it implies for the procedure, and let the user pick; guessing the axis costs a correction round. Two more shapes settle without a round: a letter-joined reply ('c+d', 'a+b') selects BOTH options, so fold each as its own locked decision and never collapse it to the first letter; and a reply asking you to compare two offered options ('analyse B and C and recommend') is not a pick, so carry both as an open decision row with your recommendation and the reasoning behind it, recorded as your recommendation rather than his choice. **Fold live-state capture into the same card.** When the design depends on host state the sandboxed terminal backend cannot read (installed plugin inventory, config values, a directory listing), add one open-ended question carrying the exact copy-paste command for the operator's shell: his paste answers it in the same round as the decisions and doubles as the design's inventory capture, stamped into the evidence dir as an E-file with its command and date. Deferring the request to a later turn costs a round, and probing the host path from the sandbox fails silently because only a fixed subset of host paths is mounted.
2. **Classify the writer path first.** Re-read the `linked_files` of every skill that covers the design's subsystem; a skill can gain a reference between sessions, and a prior-art table that misses it bills as a finding. Before either path, run the prior-art sweep yourself and hand the results into the brief: (a) the Hermes catalog (`manage_catalog` action=search) for plugins and skills that already implement the mechanism — the search result carries only id, kind, display, tier and installed, never a description, so read each candidate's marketplace page or repo README before judging it; the plugin-catalog JSON at `/docs/api/plugin-catalog.json` is a different, plugins-only index (`entries` is a list keyed by `name`, so an `id`-keyed search returns zero for everything), and hub skills appear only in the `manage_catalog` search — a name absent from the JSON is not absent from the catalog, and the doc records both sources; (b) DESIGN-INDEX.md for sibling designs governing the same subsystem; (c) for external systems the operator could drive from Hermes, each candidate's control path (CLI, HTTP API, MCP server, webhook, git refs) and whether it runs against local OpenAI-compatible endpoints; (d) the skills that cover the mechanism, including each skill's `references/` — a skill can gain a reference between sessions and neither the catalog nor DESIGN-INDEX lists it, so read the loaded skill's linked files before writing; a design that duplicates a freshly written house recipe is a prior-art finding. The doc carries a mandatory prior-art section ending in a verdict (reuse, configure, or build): a design that reinvents a catalog plugin is a defect the reviewer bills, and a prior-art section that lists names without verdicts is the same defect one level down. When the parent already holds the doc's core material first-hand (sources fetched and pinned at deployed versions during scoping, live tool captures, probe records on disk), write the doc inline from that material and build the evidence dir from the parent's captures — dispatching a researcher to re-derive parent-verified sources burns a round and can only weaken fidelity (the zero-findings reviewer loop is the fidelity gate, not the dispatch). Dispatch the ONE research subagent (delegate_task, background) when the material is not yet in the parent's hands, with: primary sources to fetch (URLs, drafts, docs), the local artifacts it may inspect (repos, configs — paths), the working-doc path per the upload-path convention in `references/pitfalls.md`'s publishing section (`<topic>-design.md`; the synced design tree (the host: /home/hermes/design-docs) when the sandboxed terminal backend is active, the home dir otherwise; NOT the pruned-after-idle scratch dir). For an HOUR-SCALE writer (live probes plus a multi-hundred-line doc), dispatch it as an agent-mode one-shot cron job (schedule 'in 2m', the full self-contained brief as its prompt, deliver origin) instead of delegate_task; stamp every date inside the brief (and any same-turn fact-store rows) from a live `date` read taken at create time, never from the conversation-start header, which goes stale in multi-day sessions and once shipped wrong dates into a brief and two fact rows before the job's own next_run_at exposed them: a delegate writer died silently with nothing written when the owning thread switched mid-run, while the cron fire survives thread switching, keeps the run in cron history as the audit trail, and delivers its summary into the chat; keep delegate_task for short-scoped writers and verify the cron writer's job in `hermes cron list` after create. The brief-file rule covers writers too: when the writer brief runs past a few paragraphs, stage it as a file in the synced tree and dispatch with a short context naming the file — the payload then composes reliably, and the staged brief doubles as the dispatch's durable record in the evidence dir. The brief opens with the deliverables and exact paths, then the clarify answers quoted verbatim as locked decisions, the sibling docs to read on disk, the prior-art sweep, the evidence rules, the style rules, and a do-not list (no installs, no commits, no config changes). A requirement the operator adds after the dispatch lands patches the BRIEF FILE first and steers the child with a one-line pointer to the changed brief, so the steer channel carries no requirement text of its own and the child re-reads one authoritative file instead of reconciling two. An update to a one-shot cron writer's prompt can lose the race with its own fire (the scheduler's next_run timestamp may already be in the past while the job still reads scheduled), so after correcting a just-created writer's brief, verify the LANDED doc carries the correction (the decision rows and dates are the tells) and fold whatever the fire missed as a parent-side pre-review fold BEFORE the first reviewer dispatch, so the reviewer sees decided rows instead of re-litigating the stale brief. A cron-platform fire has no cronjob_manage and no hermes CLI, so a cron writer cannot fire relay payloads or register cron jobs itself: design its box-side verification as the doc's phase 0 (parent-session work), hand the parent's preflight results into the brief marked re-verify-not-trust (the writer re-proves only what it builds on instead of re-deriving connectivity), and require the honest-notes section to carry everything the fire could not reach. Pre-flight WHERE the synced tree lives and whether the design's host box is reachable before planning any probe — a desktop sandbox can hold the synced tree locally at the same convention path while the host box refuses ssh, in which case write the local tree, record the unreachable-host boundary as its own probe, and hand host-attended runbook steps to the user or the host session instead of planning to execute them from the sandbox, the sibling-alignment brief (survey DESIGN-INDEX.md in the synced tree for existing designs that already govern the same subsystem; hand the researcher each sibling's path plus the specific decisions that constrain the new doc, and require the writer to declare the relationship — companion, amendment, or override — in the new doc's scope and decision record instead of silently contradicting a sibling's locked call, the way a companion mail-gate doc must position itself against a server design's 'no email anywhere' decision), the design-repo convention sources (for a doc targeting the design repo, read the repo's own AGENTS.md + DESIGN-INDEX.md before writing the dispatch — the GitHub MCP file-read works without a local clone, and when the MCP read 403s on the private repo (`Resource not accessible by personal access token`), read the synced design tree at `/home/hermes/design-docs` instead — same content, and DESIGN-INDEX.md's header remains the authority; they are the authority on folder layout, branch naming, the doc template, and the CI gates; when AGENTS.md is absent at the repo root, DESIGN-INDEX.md's header is the authority (taxonomy, the update rule, the index row landing in the same PR as the doc); they also stand in when the skill's own references/ files (pitfalls, publishing mechanics) do not resolve inside the sandboxed backend — treat unreachable skill references there as expected, not a blocker), an explicit honest-notes requirement (what it did NOT verify; it must read source, not guess), and instructions to (a) re-derive every parent-supplied 'fact' from the deployed source before using it — anything that survives only on the parent's word goes to the honest notes as task-context, never into the facts sections, and (b) run read-only probes of the live target the design migrates onto (handshake/tool inventory/sample reads) and record them as the doc's live-claim baseline — reviewer iterations then re-verify live claims against that reproducible baseline instead of trusting prose. Pre-flight the probe's prerequisites yourself before writing the brief (one cheap call: does the sandbox actually hold the credential, can it reach the target at all), because a brief that assumes SSH access the sandbox never had burns the writer round; and when the approval gate blocks a probe, do not burn the turn or retry around it — fold the probe into the doc's own runbook as a phase-0 step with an explicit the operator-executor fallback, and record the blocked boundary in the evidence dir as its own capture so the doc states why no live probes exist. Then (b2) persist every probe script, raw output, and full `--help` capture per subcommand in a durable evidence directory next to the doc (`<topic>-design-evidence/`; NOT the pruned-after-idle scratch dir) — the reviewer dispatch's ground-truth list points at that directory, so every round verifies the doc's claims against the recorded files instead of re-probing — write host pastes into the evidence file word for word, because a re-typed transcript drifts in spelling and package names and the next round bills the drift as a false record, and (b3) keep a README.md in that evidence dir holding a per-file manifest (source, ref/blob sha, capture scope) plus a corrections index (file, change, round, finding) — evidence changed across fix rounds is otherwise discoverable only by mtime diffing, and inline per-file notes alone read to the next round as unexplained rewrites; every file any round leaves in the dir (check batteries, helper scripts, staged payloads) gets its manifest row in the same round, since the manifest is the next round's inventory of what is authoritative and an unmanifested helper script is a finding — and (c) apply the `unslop` skill (skill_view('unslop'); the operator's standing requirement for design docs) to the finished doc before delivering — rewrite every AI tell per its rules. Give it output_schema (plan_path + summary + top decisions). For a parked draft the operator asks to review and finalise, this dispatch is a sync-and-polish writer, not fresh research: re-derive every doc claim against the live box, fix stale tenses and mechanism phrasing, record every probe in the evidence dir, run the unslop pass, stamp the Rev/verdict-history header, then enter the reviewer loop at step 4. Fire the doc's open-questions clarify in the same turn as this dispatch (recommended option first) so his answers fold into the doc before consensus instead of after upload; when an option's viability depends on facts the writer will establish, pre-name the fallback inside the option text ('recommend X; if the research shows X breaks <mechanism>, take fallback Y and harden') so a research verdict resolves the question without a second card round; a card that settles after the dispatch returns is not a lost answer — the reply typically arrives while the writer still runs, so queue it with delegate_task action=steer (it lands in the child's next tool result) instead of holding it for the next round; when the dispatch can wait one turn, prefer card-first-then-dispatch: fire the clarify card alone, and once it settles fold the answers into the dispatch as locked decisions — that removes the steer round the same-turn pattern pays for when the card settles mid-run; on a card timeout, the adoption-kickoff numbered-one-liners rule applies — restate them in the turn the timeout lands, never at a later pause — unless the user explicitly asks for the card back: then re-send the identical card, since an explicit instruction overrides the no-re-fire default. If the STEP-1 scope clarify itself times out, do not stall the dispatch: proceed with the recommended options, mark each one 'assumed, overridable by the operator' as a D-numbered row in the doc's §0 decision record, and say so in the status reply — a row the user SKIPPED inside a settled card takes the same path (skipped is not decided; assumed default + D-row), so a partially answered card still yields a fully decisioned §0; one exception: when another ANSWERED row's own text names the skipped axis's decision (an unlock answer like 'no TPM hardware, keyfile now' names the mechanism for the skipped unlock row), fold that named mechanism as the skipped row's answer instead of the assumed default, and flag the derivation for one-line confirmation at the next review round — the researcher's re-derivation corrects wrong assumptions anyway, and the record makes each assumption visible for a one-line veto instead of hiding it inside the doc's facts.
**Decision-support variant (before any doc exists):** when the operator asks to explore options before committing ('is there a smaller X', 'suggest alternatives', 'compare A vs B'), dispatch a SCOPING-research subagent that writes NO doc — a notes file plus a chat-facing decision fork — and end the turn on the fork as a numbered decision list. Dispatch the doc-writer only after he picks, and hand the pick to the writer as locked §0 decisions (steer it in if the card settles while the writer runs). Running the full doc loop on an undecided software pick burns review rounds on a target he may replace.
**Record docs (born-adopted):** when the operator asks for completed work written up AS an adopted design doc, the doc is a record, not a proposal: write it inline from the session's own verified material, quote the session's decisions as M-blocks with the parent-verified attestation, build the evidence dir from fresh captures of the live end state plus the surviving session artifacts (session-captured-only items go to the evidence README as provenance notes, never as captures), file it directly under ADOPTED/ with the PR body declaring the deviation from the PROPOSED-first flow, and still run the reviewer loop to the zero-findings bar — the review validates the record against live state, not a future design. No open-questions card: the decisions already happened in-session; any claim that did not survive in a capture goes to the honest-notes section instead of prose.

**Move-and-modernise variant:** when the doc's job is moving existing artifacts (plugins, configs, skills) into a new home and the operator folds a review into the ask ('take this opportunity to review and modernise'), the doc opens with a review section, not a move plan: one row per installed item, scored on capability (does native Hermes or a first-party skill already cover it), use, per-session cost, and maintenance, each ending keep, trim, or retire. Usage counts the parent cannot read from the sandbox are phase-0 measurements (`hermes curator usage --provenance plugin --json`; `hermes curator status` reports only curator-managed skills, so it cannot see a plugin's skills), so every verdict that depends on them is a D-row default with the measurement named, never an asserted fact; and each retire call ships with its cross-reference sweep (grep the surviving tree and the agent for the retired item's name) so the removal step lands with the decision instead of surfacing later as a broken reference. Items that already have a pinned upstream (catalog plugins, a maintained fork) stay references to that upstream, never copies inside the new home: the bundle carries first-party artifacts plus pointers, and only a fork with no usable upstream is vendored.

3. **Read the doc yourself** before dispatching the reviewer — you own consolidation. Fold user steers that arrived mid-research into the doc yourself or re-dispatch with a steer. Before dispatching, run the cheap defect sweep yourself so round 1 spends its budget on substance: grep every cross-reference (test IDs, probe numbers, decision IDs, section pointers) against its definition — a dangling one (a test ID cited in a methodology section but never defined in the phase table) is a free first-round finding; check the rev instances (header, verdict history, registry-row fence) agree; grep every single-letter ID series against every other one — two namespaces sharing a letter (risk rows R1-R9 against review-round history R1-Rn) read as one series in the verdict line and cost a rename round; confirm no -final file exists yet. One terminal call covers the mechanical part: dash/curly-quote grep (`grep -nP '[\x{2014}\x{2013}\x{201C}\x{201D}\x{2018}\x{2019}]' doc.md`), an evidence-pointer cross-check (every `S01`-style cite against the evidence dir listing), a source-section census (every sibling or source the body relies on must appear in the doc's consolidated source section, and the evidence README's reused-evidence map must agree with that section entry-for-entry in both directions — the section is a body claim's verification path, so an omitted source strands the verifier exactly where the claim is load-bearing, and late rounds keep re-deriving the same omission class unless the census runs at round 1), and the census checks ACCURACY not just presence: each named source must actually carry the claims attributed to it (a claim carried by a pair of docs names the pair), every read-route frame in the sources section must be record-backed (a file fetched by another route must not sit under an MCP-reads frame), and every capture's informal name in the body must match its manifest row's record shape (a 'commit-list capture' whose record is a single commit sends the verifier grepping for a record that does not exist), decision-row vs decision-ref counts, the -final twin check, and the unslop vocabulary battery at STEM precision using the SAME grep list the reviewer dispatch will carry — copy the dispatch's list verbatim, never re-type a paraphrase of it (`grep -icE 'surfac|landscap|harness|substrate|vector|tapestr|showcas|underscor|delv|crucial|pivotal|additional|leverag|utiliz|robust|seamless|intricat|holistic|realm|foster|garner|interplay|enduring|enhanc|vibrant|testament|facilitat|serves as|stands as|boasts|not just' doc.md`), because a paraphrased pattern (`surfacing?`) misses inflections (`surfaced`) and ships the tell to round 1 as a guaranteed finding; when a sequence grep's count exceeds the expected list, locate each extra match before treating it as a defect — rollout steps and other sections reuse the numbered-bold format. Read match presence from the grep OUTPUT, never from the exit code after a pipe — `grep ... | head` followed by `echo $?` reports head's status (0), so a clean file and a dirty file both exit 0 and only the printed lines tell the truth. Run the sweep's greps with `-P` alone: `-P` combined with `-E` aborts with "conflicting matchers specified" and prints no matches at all, which is indistinguishable from a clean file — a grep that prints an error line did not run; rerun it with one matcher flag. Then run the doc's own commands: execute every gate, grep, and script invocation the text tells an operator or CI to run, against a scratch copy — a gate written `grep -nE ... skills/` without `-r` prints `Is a directory` and exits 2, and a case-sensitive pattern misses the capitalised names the scrub pass targets, so a gate that cannot run is worse than no gate and the reviewer reproduces it as a finding. Trace every script flag to the layer that consumes it too: the script's `--force` must appear on the underlying CLI line, and a per-component default (`enable: true`) must not silently override a global opt-out (`--no-enable`) — a flag that never reaches the command it names is a contract defect the parent can catch for free. A flag name is not portable across subcommands: `--force` is a reinstall/verdict override on `hermes plugins install` and the security-scan override on `hermes skills install`, so derive each flag's meaning from that subcommand's own parser, never by analogy from a sibling command.
4. **Dispatch the adversarial reviewer** with MINIMAL context per the operator's protocol: goal + which artifacts count as ground truth (cloned source, deploy configs, official docs) — NOT your narrative or conclusions. It writes numbered findings to a per-doc comments file (`review-comments[-<topic>].md`), each tagged [BLOCKER]/[MAJOR]/[MINOR]/[NIT] with evidence (file:line / doc § / URL), plus a final `CONSENSUS: none|reached` line. The reviewer also runs the required unslop pass (skill_view('unslop')): every remaining AI tell is a finding citing the unslop rule id — [MINOR] for content/language/jargon tells, [NIT] for punctuation/quotes/casing/emoji tells. Vocabulary sweeps match the word STEM (`surfac` catches surface/surfacing), never the exact word — an exact-word grep let the same tell survive two review rounds (Nov 12 2026). A misquote is the same class one level up: every double-quoted span the fix round added or touched is checked against its named source, because a paraphrase inside quotation marks (a generalized 'flaky source cannot cry wolf' standing in for the sibling's 'flaky Codeberg') survives rounds that only grep vocabulary (Nov 16). Stock idioms that appear in the WRAPPED PROJECT'S own code comments (e.g. "belt-and-braces" in a helper's comment) still count as doc tells — the doc speaks in the house's voice, not the source's; only evidence captures keep source-faithful phrasing. the operator flagged one such survivor after a zero-findings consensus (Nov 12 2026): six sites shipped as "belt-and-braces" because every round read it as domain terminology, and the errata rev was the fix. Do not trust a holistic vocabulary pass: a reviewer that reports 'no AI-vocabulary hits' can still miss a high-frequency tell family (a seven-site 'surface' family coexisted with one round's clean report). In the dispatch, name the concrete grep list — the unslop abstract-noun vocabulary (surface, landscape, harness, substrate, vector, tapestry, showcase, underscore), the dash and curly-quote character classes — and have the reviewer run each as a plain terminal grep over the whole doc, reporting the raw counts. Run several reviewers in parallel (one per doc) when multiple docs are in flight, and name the sibling loops in each dispatch context (doc + status) so a reviewer that sees another doc's live delegation classifies it as expected instead of investigating it as a concurrent-writer race.
5. **Patch the doc per iteration**: read the FULL comments file, fix every finding, then — before re-dispatching — sweep the fix round's own added lines for unslop tells and re-grep the numbered sequences (facts, rollout steps, tests) and the S-style cross-references. Run the unslop battery over the fix script's REPLACEMENT strings BEFORE applying the batch (extract the replacements and grep them, not only the doc after): the fixer's own fresh phrasing is where the tells return — a 'tool surface' or 'migration surface' noun rides in inside fix prose after the battery had gone clean, and a pre-apply catch saves the post-apply residue pass every hit otherwise costs. Fix-round prose re-introduces what the base text never carried (a Rev header line and a rewritten fact each shipped an em dash the base text did not have); the rev-history nodes are a body-text surface too, so any claim a fix rewrites in the body must be swept in the nodes that restate it (a corrected claim survived in its own node after the body was fixed and cost a round), and a batch of same-file patches collides when one patch's old/new region overlaps another's — a replacement carrying its own list number can land under the wrong number, and a renumber patch anchored below an unedited sibling line leaves the old line in place beside the new; each survivor reads as landed to the writer and bills back as a finding next round. When consecutive rounds cluster on one contract block (a script's command list), stop patching it clause by clause and replace the whole block in one edit composed from the verified commands: each piecemeal fix lands a new clause the next round falsifies, and the block rewrite is what ends the cluster. Prefer the design_doc plugin's doc_batch for a multi-edit fold: one call applies every replacement in order against the evolving content, all-or-nothing, and returns per-edit counts plus the new sha256, which removes the collision class entirely; it cannot ride inside a multi-call tool_call block (one local tool per call), so edits to several different files go one doc_batch per file across sequential calls while native patch calls batch freely across different files in one message, and doc_batch marks the file re-read-required for any later patch/write_file. doc_batch is all-or-nothing INCLUDING no-op edits: a find string identical to its replace (a stale placeholder edit left in the list) fails the whole batch and nothing lands — strip no-op leftovers before composing, and when a batch aborts on one edit, re-read that line from disk (the miss is usually a trailing-punctuation mismatch) and re-run the whole list, since earlier edits in the aborted batch never applied. Re-read the touched region BEFORE composing a doc_batch fold: find strings reconstructed from memory of your own earlier edit text carry silent typos (one wrong token fails the whole all-or-nothing batch and nothing lands), and the fresh read catches a junction a previous fold already moved. Probe every find string with `grep -cF` (expect count 1) before composing the batch — the cheap probe beats an all-or-nothing abort mid-batch, and it catches anchors built on an assumed bullet order: an insertion anchored on the bullet you ASSUME follows another one (a new section-5 check spec anchored after 'ghcr-tags' when the list actually runs pin-first) aborts the whole batch with count 0, so the probe list must cover EVERY edit, not the risky-looking ones. And probe against the file's CURRENT bytes immediately before the run, never from an earlier render: anchors composed from an offset read or a comments-file quote inherit that render's wrapping and indent — a continuation-indent guess (two vs three spaces inside a numbered list) or a leading-prefix guess costs a full all-or-nothing abort cycle even though both lines exist on disk. Keep every find anchor SINGLE-LINE: a two-line find silently misses (count 0) even when both lines exist on disk, and the same two-line probe reports unreliable counts, so anchor inserts on one existing line and let the replacement text carry any new lines. When the insert is a NEW SECTION (heading plus content), anchor it after the previous section's LAST paragraph, never on the next section's heading - a heading-anchored insert lands the new subsection before an earlier-numbered one and the section order reads out of sequence. Formatted prose anchors carry their markdown markers: a phrase quoted semantically without the line's surrounding ** or backticks misses with count 0 at fire time (a sibling-status line exists as `- **name (STATUS Rev N):** prose`, and the un-bolded form matches nothing) — compose prose anchors from the grep -n'd line's actual bytes, never from memory of the sentence, and never from the reviewer's quoted wording — a finding that quotes 'independent' where the line reads 'independently' aborts the whole all-or-nothing batch with count 0, so copy anchors from a fresh grep of the line itself. A count above 1 can also be one live site plus one rev-node site: a fix round's own rev nodes quote the old forms they fixed verbatim, so disambiguate the live site with a longer context anchor and never edit a node's historical record to make the count land. patch itself can transiently fail to READ a file it just edited ("Failed to read file") with nothing wrong in the content; retry the identical patch once before diagnosing. The write side has the mirror trap with a nastier failure mode: write_file can return a short timeout AFTER the write fully landed, so the identical retry then hits the stale-write refusal, and a blind retry of a landed PATCH duplicates the inserted block — on ANY write or patch timeout, stop and read the target before retrying: the content is usually already on disk (a partially-landed large write shows as a short file), merge only what is missing, and never blind-retry a timed-out mutation. The stale-read guard also refuses a write whose read_file rode the SAME batch as the write (the guard evaluates before the batched read registers) — never pair a read with its dependent write in one batch; patch the file in place instead, or stage the fold as a script whose replacements each assert their match count and run it via terminal (this also sidesteps quote-dense payload mangling). Two more guard mechanics: the guard's pagination flag is STICKY — a file once read with an explicit limit keeps refusing full overwrites even after a fresh complete read, so the reliable rewrite path for a blocked artifact is a fresh sibling filename plus a plain `mv` over the target, not a re-read loop; and the ungated shape for a large multi-edit batch is a script FILE composed via write_file (write_file never gates) executed by a plain `python3 /path/script.py` terminal call — inline heredocs of the same edits sit on consent cards and die unexecuted when the user is away. From round 2 on, expect most findings to be fix-round residue of your own making — a surviving pre-fix clause, an un-extended preamble, a pointer the renumber missed, an off-by-one in a capture you added, no test for a refusal the fold just spec'd, an ordering the rewrite contradicted — so run the fix round's self-check primarily against your own diff, not just the base text. A rewrite that MERGES paragraphs must span every superseded paragraph in its old_string — anchoring on the surrounding headings leaves the predecessor paragraph beside its replacement, and the duplicate reads as landed prose. patch's fuzzy matcher splices replacements into long one-line bullets the same way: after a patch on a long bullet, grep a distinctive phrase from the replacement and require count 1. After inserting a guard line at the top of a numbered command fence, re-read the fence — the insert can swallow the first step's comment and leave steps 2-N numbered with step 1 unlabeled. **A reviewer's redaction-artifact finding can be a display phantom — codepoint-verify the disk before composing the fix anchor.** The tool channel masks credential-scheme words (the word Bearer renders as asterisks) and long token shapes in its OUTPUT, so a fix anchor transcribed from the reviewer's quoted text misses with count 0 against the real bytes and the 'defect' may not exist on disk (a quoted `Authorization: ***` was really `Authorization: Bearer` with balanced code spans). Print the suspect span as space-separated codepoints (the dump survives masking where a re-read through the same channel does not), disposition the finding as a display phantom in the fix list when the disk is clean, and defuse repeat flagging by rewording the prose to mask-proof phrasing ('an Authorization bearer credential') — the reviewer dispatch carries the reviewer-side warning; this is the parent-side half of the same rule. - **Land a reviewer's prescribed replacement wording VERBATIM in the doc — paraphrasing the prescription reintroduces the defect round after round.** The same applies to a prescribed FLAG: verify the flag in that subcommand's own parser before landing it. A prescription that names `--force` where that flag is the security-scan override rather than a reinstall converts the fix into a new MAJOR, so a flag-naming fix is re-derived from `--help` or the parser, never accepted on the prescription's word. A mechanism-description sentence cost three consecutive fix rounds because each pass rephrased the reviewer's prescribed trigger and semantics descriptor differently while the embedded script's own comment carried the correct wording every time; quote the prescription (or the fence comment it mirrors) word-for-word, and when the prescription and the comment disagree, the comment is the surviving mechanism - copy it. The prescription bounds the edit list too: an UNPRESCRIBED fix-round edit (a completion or extension the fix list did not name) is itself a next-round finding even when its content is true, because its route or coverage claim then rides on no record; make no edit beyond the prescribed strings, and if an extension is genuinely needed, land it and declare it in the fix-verification list as an owned extension so the reviewer verifies it as declared rather than discovering it.
**Verify the fix batch LANDED on every surface the fix list names before re-dispatching** — a multi-file push can carry fewer files than the fix list intends (a files-array omission ships one file and strands its fix), and a fix claimed on a surface that was never touched reads as landed until the next reviewer re-flags it as partial at full round cost; re-read each named surface (doc regions, each kit file, manifest rows, index cells) and confirm the fix text is present before dispatching. The re-dispatch's fix-verification list is part of that proof: derive each per-finding claim from the APPLIED batch (the fixer script's applied-edit count, or a post-apply read-back), never from the pre-fix plan — a hand-written edit list can omit planned edits without the writer noticing, and a dispatch asserting a fix the script never carried bills a full round AND poisons the durable records (corrections-index and manifest rows then describe a doc state the doc contradicts), which the next round bills again as false records. Then re-dispatch the reviewer with a fix-verification list (what changed, which finding each addresses) and instructions to verify the fixes AND hunt for new issues the rewrite introduced. Write the fix round's OWN rev-history node in the same batch as the fixes, composed from a read-back of what landed — a fixer that extends the previous node's coverage while skipping its own node ships an unrecorded round, and the review that catches the omission runs after the comments file that documented the fixes was overwritten, so the audit trail must not depend on it. The node carries the round's tag tally '(x MINOR, y NIT)' (the comments file it names is overwritten each round, so the node is the only durable tally holder), an umbrella clause for the unlisted residue fixes, and its finding-number anchors; the node's date is the fix write's LANDING date — a node dated the session's start date is a false record when the fix crosses midnight (the file's mtime falsifies it), so date each node to its landing day, declare older nodes' dates as their landing dates in the next dispatch, and never backdate a later node to keep the dates uniform; take the landing day from a live `date` read, never the conversation-start header in context (multi-day sessions run under a stale header date; the writer-dispatch rule below carries the same requirement); a tally whose round records are already overwritten is declared unrecoverable in the comments file, never invented. Each fix node carries a 'Fix-verification pending (R<n>)' tail while its verification round is in flight, and that tail RESOLVES to the landed outcome when the round returns ('fix-verification R<n>: x findings, fixed by the node above') — exactly the newest node may carry a pending tail, and a stale pending marker on an older node is a false record the reviewer flags (the verification it names already landed). Sweep EVERY node's tail in the same batch that adds the new node — resolving only the node you just wrote leaves the previous one stale, which the next round bills as a false record, and the bug repeats every round until the sweep is scripted. Gate the result with `scripts/check-tails.py <doc> <expected-round>` before dispatching the verification round: it asserts exactly one pending tail and that it names the round under review. When the fix batch runs as a staged script, land the node text in a SECOND pass after the read-back, never inside the same script as the fixes: a node written alongside the fixes is composed from the plan, and its false clause (a section 'marked' that the batch never touched) is exactly the false-record finding the read-back rule exists to prevent. Every finding the node's tally names gets its own anchor — one unanchored finding leaves the fresh corrections-index row unreconcilable against the node. State the round-label scheme at loop start (review round N, its fix round N+1) and carry it identically through the doc's rev history and the evidence README's corrections index — the same round under two labels across those records is itself a finding. Where a fix touches load-bearing text, anchor it inline with its finding number ('R1 finding 2') so the audit trail lives in the doc, and declare those inline anchors as EXPECTED EXCEPTIONS in the next dispatch — the reviewer verifies each anchor against the prior comments file instead of spending a finding on the citation itself. Anchor finding numbers ONLY in round-transient or audit surfaces (Rev nodes, the fix-verification list): a durable body cell (a decision- or probe-table row) must never cite a comments-file finding number, because the comments file is overwritten every round and the cell's pointer dangles the moment the next round lands; durable text points at the doc's own Rev node or loop record instead. Scope the prior round's verified-clean list in the re-dispatch: every item the fix round touched (evidence files whose bytes changed, new probes, re-derived arithmetic) leaves the skip-list and gets re-verified — a skip-list that still covers a changed file ships a stale integrity claim and hides exactly the defects the fixes introduced. Two more fold rules keep fix rounds converging: (a) a fix that REVERSES a claim (X had property P, now it does not) guarantees stale sibling prose — before re-dispatching, grep the doc for every sentence that compared against, leaned on, or PARAPHRASED the old claim and fix those too, because a comparison bullet that survived the headline fix reads as a partial fix next round, and a section intro that restates the old behavior in its own words cites nothing and survives a citation-scoped grep; the same sweep covers multi-site values a fix renormalizes (a band list stated in three places must change in all three), and it runs in inverse on fold-ADDED sentences: a new sentence carrying a load-bearing number greps every other site of that number and carries the same qualifier there — an added unqualified figure re-teaches exactly the drift the base text's qualified sites removed. (b) a 'true but uncaptured' finding (the reviewer corroborated the claim by re-fetching, but no evidence capture contains it) folds by ADDING a provenance-stamped evidence capture — one file, per entry: URL, the claim, the fact, who recorded it and when — and citing it, or by marking the claim unverified in place; never leave the text asserting an uncaptured claim. When the new capture takes a number the doc already reserved as a forward reference (a 'P21+' future-probes note in the runbook), renumber the forward reference past the new high-water mark and update the header's evidence-range line in the same fold — a reserved range that collides with a real capture misnumbers every later probe. Run the direct fetches yourself when the source fetches cleanly; reserve search-snippet captures for sources behind walls, with the fetch method noted in the capture. **Walk the doc's own behavioral promises against the patched sketch, not just its text** — a text-preserving edit can silently move a side effect across a control-flow boundary (replacing a truthiness check with presence-keying dragged an unconditional timeout assignment inside the branch, contradicting the doc's own test table; the next round's reviewer caught it only by walking the empty-list call end-to-end), so a fold that touches any code sketch re-runs the mechanism against every test row and promise the touched section makes and fixes the mismatches pre-dispatch. **A fix's added prose can promise work in another section: when a rewrite introduces a sentence promising tests, gates, or config keys the doc does not yet name, land those promised sites in the same batch and grep each promise's target before re-dispatching — a landed paragraph whose promised test-list entries never appear is the fixer-side partial fix (a join-window paragraph promising three test cases shipped while the phase-4 test list stayed byte-identical; the next round re-flagged it as the round's only major).** **Treat every command, flag and file path the doc prescribes as a factual claim and verify it against source before it enters the doc** — a plausible-looking flag can mean the opposite of what the prose assumes (a `--force` that is a security-scan override, not a reinstall), and a command template that omits a flag makes the documented path inert. When a script's exact invocation is not yet implemented, state the invariant and defer the exact command to implementation with tests instead of inventing flags. **Custody-sweep every fold-added transfer, staging, or copy step against the design's own security model: name what the addition moves, where it lands, and who may hold it** — fix-round additions that move files or credentials are where custody violations hide, because the reviewer audits the mechanism the text produces, not the writer's intent. **Re-derive every count word and stage-grouping cross-ref the fold touches, section headings and flow-summary lines included** — a fix that extends an enumeration ('two races' → three shapes) leaves its own count word stale, a stage-alone cross-ref ('tests 5-8') still naming the old grouping reads as landed next round, and a fix that MOVES a step renumbers its siblings — grep 'step [0-9]' after any in-phase reorder. **Sweep the singularity claims when the fold ADDS a second instance of a mechanism the text declared singular** — 'the only old-box traversal', 'one named exception', 'a single channel' read as structural guarantees, so an additive fix that creates a second instance (a second fetch riding the same session, a second source file) leaves every 'only/sole/single/unique' sentence about that mechanism false while reading as landed; grep the mechanism's name together with only|sole|single|unique and fix each hit in the same round, restating the guarantee's new scope ('the host-key copy plus the admin-keys fetch together are the one traversal') rather than deleting the claim.
6. **Stop** at the ACTIVE bar: default = `CONSENSUS: reached` with no BLOCKER/MAJOR; overnight variant = cap lifted AND zero findings at every tag including NITs — keep polish-cycling until the reviewer reports zero, and after applying a final one-clause fix require one verify pass that could have found nothing (a clean verdict ends the doc, not the absence of findings in the patch). The loop runs unattended on completion-message wake-ups (each re-entry: act on that one batch, patch/dispatch, end turn); **publish each finished doc the moment it passes the active bar** — do not hold finished docs for a final batch. Then report verdict history + remaining open decisions to the user.

## Post-consensus decision folds

When the operator makes design decisions in chat after a doc reached consensus, the fold is its own sub-procedure — distinct from both a fix round and the mechanical one-liner pass (reserve that for renames/footers/quote completions; a fold touches dozens of sections and always gets a fresh review round):

1. Quote each decision as a numbered M-block in §0 (the decision + which sections it touches) so the fold inputs live in the doc itself, recoverable verbatim by a later session. Verify each quote against the live chat thread YOURSELF before writing it (reviewers often cannot read chat history — session_search can return nothing on every query) and record the attestation ('parent-verified against the live thread') in the next reviewer dispatch so the quotes are not re-litigated each round. An idea the user asked you to INVESTIGATE that the evidence rejected ('can X seed this?') also lands as an M-block — the question, the primary source checked, the verdict, and what the examined mechanism still does — so the next session never re-litigates the rejected path or re-derives the answer.
2. Execute authorized pre-steps dry-run-first, then record each as a NEW numbered probe (P<n+1>, P<n+2>, …) with artifacts in the doc's durable evidence directory (never the pruned-after-idle scratch dir) — per the baseline rule, evidence living only in chat or a comments file is unverifiable next round.
3. Retarget every live reference with a grep sweep of the old forms (old folder paths, consumed rule clauses, renumbered steps, now-moot fallback options); fix the hits that are live claims, leave historical-baseline tables untouched, and reconcile them with one state-delta paragraph that says what changed since the baseline.
4. Delete consumed exceptions in place — an exception whose precondition no longer holds re-teaches a dead rule; then re-map every cross-reference to the removed mechanism (a file dropped from a move group must not stay expected by the verification step that follows it).
5. **Run the unslop sweep over the fold's own added text before dispatching** (skill_view('unslop'), vocabulary check over the diff's added lines): the doc's closed loop left the tell vocabulary at zero, so any tell a fold reintroduces ('stands as', 'surface', 'serves as') is a guaranteed tagged finding and a burned round — catch it pre-dispatch. Fold writers run under auto_load; fold subagents do not, so the sweep is the writer's job, not the reviewer's default. Then dispatch a decision-fold reviewer whose context enumerates: each decision, the sections it touched, the cross-referencing sentences that must now agree with each other, the baseline-immunity list (which tables legitimately describe the pre-fold state and stay unchanged), which phase build lists and verification-ladder M checks each decision's binding must appear in, the honest-notes entry any newly adopted but never-exercised mechanism needs (plus the M check that will first exercise it), and the failure semantics of every script the fold's spec touches (a set -e script plus a fresh-install missing-state path turns an unconditional change into a guaranteed failure). A fold that mixes mechanical adoptions with one override still reviews the WHOLE diff — the record-level defects hide in the mechanical parts. Verification rounds of a fold may carry an output_schema ({verdict, findings[{tag, location, problem}], fix_checklist}) instead of the comments file: the round count is small and the schema-validated reply skips the file lifecycle; keep the comments file for the doc's main loop.

Fold bookkeeping that rides every fold: put the new Rev line ABOVE the retained prior Rev lines (newest first, so the audit trail survives) and keep ONE relabeling convention for the whole loop — either leave the retained lines as their own **Rev:** lines or relabel each displaced head **Prior rev:**; the relabel-per-step shape leaves every rev appearing twice (its own line plus the Prior label), which reads as a duplication defect unless the next dispatch declares it as the loop's verified convention. Then extend the verdict-history line with the fold round (tag counts → incorporated in Rev N) and update the header's evidence-range line for the new probes. Re-stage the fold's artifact chain at every round boundary in one terminal pass — `git hash-object` the staged doc, rewrite the blob-pointer file, regenerate the unified diff against the fold base, and move the index row's Rev blob cell to the new hash: base+diff must byte-reproduce the staged doc — run the reproduction as part of the pass (patch the diff onto a copy of the base, hash-compare the result against the staged doc), never assert it from intent; any parent edit made AFTER the diff was captured (a Touches-tail fix, a dash fix) invalidates the captured diff, so regenerate and re-prove in the same pass before the diff goes to any reviewer. A diff left stale from an earlier round makes the recorded blob name bytes no round or publish will ever reproduce. The verdict-history line names only rounds whose results have landed — extend it per completed round with its tag counts and keep exactly one 'R(N+1) pending' tail; a tally for a round still in flight is the same currency defect as a stale one. A pending marker that must come off because the round never ran (superseded by a later fold before dispatch) is replaced by an explicit supersession clause in the same line — dropping it silently leaves the round's review state unrecordable and the superseded fold's content unreviewable. The loop's closing round lands as post-APPROVE bookkeeping: append the final round's record to the comments file (its tallies plus a 'CONSENSUS (fold loop): reached' marker), extend the verdict-history line with the close ('fold R<N> 0 → CONSENSUS reached at every tag incl NITs (fold loop closed)'), and disclose in the PR body that only those records changed after the approving round — the approval attests the design text, the close record is mechanical and named, and a later reader never mistakes it for unreviewed prose. When the adoption record also lands in the fact store, prose-ify resource limits ('a 200 percent CPU quota', never an assignment shape like KEY=200%) and keep pin-adjacent numerals out of the text — the fact-store credential classifier reads assignment forms and pin-adjacent numbers as secrets and rejects the add, burning retries on an otherwise clean record. Build the stale-reference sweep as a CONCRETE grep list from the old values — old numbers, percentages, unit ids (a quota in cores, a cpu.max figure, a threshold), and the consumed prose forms ("is proposed", "if any", "if adopted", the "Open decisions" heading) — and sweep the preamble sections (non-goals, honest notes) and the risk table too, not just the runbook: the runbook retarget is the easy part, the §0/§7/§9 leftovers are what the reviewer finds. Re-anchor every line-number cite into sibling design docs against each sibling's CURRENT rev at fold time, and bump the References section's sibling rev labels to match: parallel adoption threads move sibling revs — and their header line counts — independently, so a cite correct when this doc closed lands one line off a day later; verify each re-anchored cite against the sibling file on disk, never from the reviewer's mapping alone. Attribute every hit (mentions inside M-blocks framing the OLD value as overridden are legitimate). Delete consumed conditionals downstream of a rewritten step in the same pass — an "inserted, if any" hanger-on re-teaches the dead branch. When the decision blocks share the runbook's letter prefix (M-numbered decisions vs the operator-executed steps M8/M9), add one disambiguation sentence to the decision record — the namespace collision is a reviewer finding otherwise.

Fold-hygiene rules from a fold-fix round (each has bitten):

- Derive BOTH the M-blocks' Touches claims and the reviewer dispatch's footprint list from the ACTUAL diff against the pre-fold rev (fetch the pre-fold blob from main first), never from memory of your own patch calls — a remembered enumeration misses rewrites made inside claimed sections (a gate paragraph) and can claim touches that never landed, and the reviewer's footprint census then discovers what the writer should have caught. Run the audit BEFORE the push: every claimed touch must exist as an edit, and no unclaimed section may carry fold content (`scripts/fold-census.py` runs the census — per-heading changed-line counts from the byte-verified base against the staged doc).
- When a fold REWRITES a paragraph instead of appending to it, re-read the pre-fold text and carry every unrelated clause forward — a rewrite that only needed new sentences still deleted the old ones (an env-absent recovery clause and a no-typed-token security sentence), and the loss only surfaces in the next round's diff census.
- A fold that adds or rewrites a runbook materialization fence gets a FUNCTIONAL walk before dispatch (scratch HOME, real key material, the happy path and the variants): bash -n green shipped a dead custody chain, because env-file delivery strips trailing newlines and cannot carry multi-line values while the materialized file (an SSH private key) needs its exact bytes — any env-sourced byte-exact file rides base64 (`-w0` at the paste step, with the rationale stated there; `base64 -d` at materialization), and the keygen step states the empty-passphrase requirement, since the non-interactive agent flow cannot answer a passphrase prompt and a passphrase chosen at generation poisons every later step.
- **Dedent fenced heredocs inside numbered lists — a list-indented EOF terminator still passes bash -n (warning-only, exit 0) while a paste consumes every step after the fence as heredoc content.** When a fold adds a fence inside a numbered item, move it out of the list indent to column 0 and grep the fold's added fences for indented terminators (`^ +EOF`) before dispatching; an exit-code-only battery calls the fence clean while the pasted run bricks the procedure exactly where the fence sits.
- **A fold-added command rationale must cite a capture or name the box-side check that settles it — a mechanism asserted from intuition gets falsified by the reviewer's own staged experiments, which then costs a capture and a reword round anyway.** When the rationale carries behavior claims about a tool's flags (what --force wipes, whether a prompt fires), either pin a capture with the experiments or write the claim as an owed box-side check; a reviewer with a sandbox runs the experiments and the asserted mechanism loses.
- **When a fold's new mechanism depends on a stored config form (an fstab line shape, a header format, a partition-table id), grep the base text for every OTHER site carrying that form and reconcile them in the same fold.** A mechanism built on one form while another section still prescribes the opposite form bricks the run at the earlier step - the contradiction surfaces as a MAJOR because both sites read as landed instructions.
- A fold's M-block may not assert as fact what its own honest-notes or acceptance entries mark open — grep the M-block's mechanism sentences against the open-check entries before dispatch; and every back-reference the fold's added text makes (an option number, a 'probed present', a named follow-up) must resolve to a doc section or an evidence file — ground it against the capture or drop it; the same rule binds round/rev RANGES the added text names — both endpoints must exist in the doc's own records (a 'rounds R8-R16' clause when the verdict history ends at R15 names a round the doc never recorded; name the recorded span or drop the range clause).
- An 'applies unchanged' claim about an existing section is diff-checked against that section's actual wording — generic-sounding sections are often mechanism-specific (a compromise runbook written for tokens does not cover a signing key; name the class's real disposition, its RK row).
- A fold's citation of a SIBLING design's record (its Rev lines, its evidence dir, or its DESIGN-INDEX row) as a claim's verification record is checked on disk BEFORE dispatch — read the sibling and confirm the named record exists and its dates cover the claim: a sibling can have no evidence dir at all, its header lines can date the record differently than the claim's span, and the record that actually holds the fact may live under a different sibling's row than the route's origin suggests (a relay-verification record lived in the attachment design's smoke row, not the transfer design the route came from).
- A fold's References-row additions are citation bookkeeping, not mechanism touches — the M-block's Touches list stays mechanism-scoped; when a reviewer surfaces the adjacency (a row the Touches list omits), record the parent ruling as a named block in the next dispatch instead of editing the Touches list.
- Every fold-added capture lands with its README manifest row and corrections-index entry in the SAME fold, and its fetch date matches the capture's on-disk mtime — a manifest row added a round later, a missing Rev entry, and a claimed date contradicted by the mtime are three components of one finding. A capture added outside a fold moves four surfaces in one pass: its manifest row, the doc header's capture count, the evidence README's row count, and the sources table's next S-number row. The same two-half discipline covers LATER EDITS to an already-landed capture: the manifest sha re-hash and a corrections-index row both land in the modifying round — a re-hash without the corrections row reads as an unexplained rewrite next round, and a row whose claims cell lags the capture's new content hides the very claims the fold cites the capture for. When a fix CORRECTS a defect inside an existing capture (a printed predicate that was itself wrong), append a dated correction block to the capture and keep the original lines as the record of what ran — never rewrite printed historical lines; the corrected mechanism statement lives in the correction block and the doc cites it. The manifest row can carry the same defect: re-word any row whose scope note over-claims the capture (a row listing counts for files the capture recorded as not-extracted) to match the capture's own words in the same pass.
- A STATUS/gate sentence is a promise evaluated against OTHER sections' lists — annotate every row it evaluates in the SAME fold. A phase-0 STATUS claiming 'steps N done, the gate evaluates per-row' is unmet while the §2 list it evaluates still carries unannotated rows: each measured item gets its P-cite inline, each deferred item an explicit NOT-OBTAINABLE note naming where the read happens instead. The STATUS text alone reads as landed; the next reviewer evaluates the gate against the list and re-flags the whole thing as the round's only MAJOR (twice on one doc before the rule landed).
- When a fold re-points a step's scheduling (a probe moved to 'the build session'), grep the DECISION ROWS and open-decisions list for the old scheduling phrase — 'phase 0 measures it', 're-derived in phase 0' clauses in §0's assumed-decision rows contradict the recorded reassignment while every prose site is already fixed; decision rows are where stale scheduling hides.
- A renormalization sweep runs over the EVIDENCE DIR's manifest and corrections rows, not only doc sections — a count fixed in the doc (14→15 fingerprints) while the README's manifest row still carries the old number is the same partial fix; grep the README rows for every renormalized value before dispatching.
- A decision that overrides a CADENCE, threshold, or count word gets a whole-doc grep of the OVERRIDDEN WORD itself (the old value as a bare token), not a sweep of the sections the decision names — an adoption fold that moved weekly to daily left seventeen live 'weekly' tokens across fifteen lines, including two operative rows (a non-goals exclusion still citing the overridden decision, an install step still registering the old cadence), because the fold swept only its named sites; quote cells, locked card text, and historical records are the only immune sites, and each survivor class is named in the sweep's exception list.
- A newly adopted mechanism's spec is incomplete without its deployment route in the SAME fold: who authors the artifact and where its kit custody lives, which named executor lands the privileged acts (root-side installs, crontab lines — the doc's convention names every non-hermes executor explicitly), and which install step exercises it first. A fold that retargets three sections to a report file nothing deploys is a silent failure the reviewer catches as a MAJOR; grep the fold's added sections for every path the mechanism claims to write and confirm an install step creates each one.
- Any 'recorded on all N runs' count over a log that APPENDS (relay out-files, run logs) is stale the moment a new run lands after a review round — re-grep the log's run headers at every round and reconcile the count in both the doc and the manifest row; a post-shred FATAL attempt is worth recording as the custody corroboration, and the count phrase must name the successful subset explicitly.
- A session that lands TWO folds in a row still bookkeeps each separately: one Prior-chain node per fold (newest first) with its own review tally, and one verdict-history entry per round. A chain that jumps from the newest entry straight past the intermediate rev (skipping its node) or a verdict history missing a round's tally is its own finding — the audit trail is the header's job, and 'the tallies live in the comments file' is not enough (that file is overwritten each round).
- Rebuild BOTH bookkeeping lines — the multi-hop Prior chain AND the verdict-history line — as ONE whole-line pass (python over the two header lines, node list composed programmatically), never as fragment-by-fragment find/replace edits: incremental patches on these lines duplicate nodes (a Rev 10 hop inserted while the original Rev 10 node already sat below), mangle adjacent words, reorder hops out of sequence, and leave mid-sentence joins between verdict entries — each state a reviewer reads as a bookkeeping finding. Compose the node list (rev + date + fix description per hop, plus each hop's review tally), render each line once, verify the chain descends strictly (grep 'Prior: Rev N' in order) and the verdict entries sit in round order with one tally each, then write. Verify the rebuilt line's neighbors too: an insertion that anchors on a stale fragment lands before the wrong node. When consecutive fix rounds converge to pure bookkeeping residue (every finding sits in these two lines), do ONE comprehensive rebuild of BOTH lines in a single scripted pass and require the verify round — a bookkeeping patch per round bumps the rev and adds a fresh node for the next round to catch, which self-perpetuates the loop instead of converging. Build the verification battery INTO the producer script and run it before dispatching the verify round: assert the landed lines byte-equal the script's embedded strings, walk the chain census (strict descent, no duplicate nodes), cross-check every chain clause's tally against its verdict-history entry's numbers, and census the batch's added text for dash/curly/tell hygiene — a producer that lands and self-checks in one run catches its own bugs pre-dispatch (one tally-renderer format bug falsified 8 chain clauses and the round dispatched before any check ran). Write each check's expectation from the prescription, not from intuition — a hand-derived expectation (a line count that forgets the trailing empty element after split, a clause the prescription says to DROP) fails a correct batch and masks the real defect.

- Size the fix batch's tooling to the batch: a one-or-two-token or one-cell fix needs native patch calls plus pre-batch byte snapshots (cp doc + README to /tmp), not a new producer script — a fourth script dropped into a custody dir whose manifest declares three is the undeclared-tooling finding the batch was fixing. Prove the delta by diffing the snapshots (exactly the named lines/rows may differ; each changed row shows as one '<' plus one '>' diff line) and state that delta shape in the next dispatch so the reviewer verifies the delta instead of discovering it.
- A record's claim about what a script 'carries' must match the script's embedded content: an in-place-correction producer embeds only the correction spans, not the corrected text — scope the claim precisely ('embeds X byte-for-byte; produced Y by an in-place correction of Z, which lives in the doc') instead of amending the producer after the fact to make the claim true. The verify round's own test — does the script contain the landed text? — reads the embedded content, and a post-hoc edit also breaks the as-run snapshot the record describes.
- The loop's current-state line family — the Rev-line parenthetical, the loop-record line, and the newest fix node's pending tail — advances TOGETHER in every fix batch: after landing the fixes, grep every family member for the in-flight round and advance each to the new state. A prescription that names only some members is the prescription's sweep gap, not permission to leave the rest behind — land the missing advance in the same batch and declare it in the fix list as an owned extension ('the prescription omitted the Rev-line advance; landed and declared'). 'Nothing else' obedience to an incomplete prescription leaves the header contradicting the node line below it and bills a finding either way.
- When a fix round's tally clause and pending tail land on the SAME node line, resolve or strip the pending tail in the SAME batch — a node asserting the verification both happened and is pending is self-contradictory; and when one round's fix completes in a later round (a strip that failed then landed), attribute the SPLIT on every bookkeeping surface in one pass — the loop-record line AND each affected node's fix-verification tail take the plural form ('fixed by fix rounds R18 and R19'), and the earlier round's node summary states what its round actually landed ('the X half did not land this round; landed in R16') — a tail left at 'fixed by fix round R14' while the loop record says R14 and R16 is the stale-sibling finding the next round bills.
- End every fix batch with one mechanical tail sweep: `grep -n 'pending (R' doc.md` must return exactly one hit, on the newest node. A round that resolves its own tail routinely leaves the PREVIOUS node's tail stale, and each stale tail is a finding next round; resolving the older tail belongs to the batch that lands the newer one.
- An adoption go that arrives as free text with no per-row answers ('Otherwise - LGTM') resolves every remaining decision row to its recorded default: fold it as an M-block quoting the free text, mark the parenthetical as the parent's recorded summary rather than card verbatim (the Quote-column header then scopes M1-M5 as card quotes and M6-M8 as the go), and mark each defaulted row decided-by-M8 so the decisions section stops reading as open.

Boundary case: a decision that ADOPTS the already-recommended option is mechanical

- Compose each Rev-node summary FROM a read-back of what actually landed, never from the fix plan: the fix applier and the header writer are the same hand, so a summary composed from intent records fixes that never landed — a false record the next round bills as a MAJOR (the claim is refutable against disk) while the real fixes pass unnoticed. Read back every named surface BEFORE composing the Rev line, and word the summary only over verified bytes; when a fix was attempted and failed, the node says so ('did not land this round; landed in Rev N') rather than omitting it — the audit trail must match the disk, not the intention.

Boundary case: a decision that ADOPTS the already-recommended option is mechanical — record it as an M-block, mark the decision rows decided, bookkeeping rev, no fresh round (the design already implements its recommendation as the default path); a decision that OVERRIDES a recommendation changes mechanics and gets the full fold procedure with a fresh round. 'Mechanical' means the fold's content delta is one constraint line plus the transition mechanics; the self-verification set that substitutes for the fresh review round is: the touched fence re-spliced byte-equal with its staged kit copy, the syntax and behavioral battery re-run over every embedded script, the registry row (and the doc's registry-template fence) updated with the landed sha, and the transition (status flip, folder move, row flip) landing as ONE commit whose blob the parent verifies three ways — a fold touching more than one constraint line takes the full procedure.

## Splitting a consensus-final design (into standalone children)

When the operator splits a FINAL doc into two or more standalone designs, the split is a structural fold on already-reviewed content, not a rewrite: the children inherit reviewed text and each gets its own review loop. Distinct from a fix round (patches one doc) and an in-doc decision fold (§0 blocks): a split re-parents content and must leave no child half-dependent.

1. Derive the boundary from the operator's adoption-timing reasoning (what lands now vs what waits on missing hardware), and quote his split instruction verbatim into BOTH children's decision records. Placement of shared machinery follows the consumer: a mechanism whose only consumer is one child (an external monitor, an alert channel, a standby-side secret copy) lives in that child; shared scripts, contracts, and custody rules are specced whole in the child that builds them, and the consumer invokes them by reference while stating the dependency direction (consumer requires producer; producer stands alone). Make the derivable placement calls yourself and state them for veto in the status reply; they do not need a clarify round.
2. Dispatch ONE writer with an exhaustive section-mapping table: every parent section, decision row, gap, goal row, test ID, phase row, security rail, and honest note mapped to a child or marked deliberately dropped with a reason. Require fresh read-only re-probes of time-sensitive claims BEFORE the children are written (the parent's verified facts may have drifted since its loop closed) and ONE shared evidence directory both children cite, so the pair shares one P-number space. Reviewer-run probes that later rounds depend on are transcribed into that same probe log with provenance ('recorded by the round-N reviewer; transcribed here; next round re-checks before accepting') — evidence living only in a comments file prunes away. Writer tool boundary: read-only probes on the box; writes limited to the child docs plus the evidence dir; no new mechanisms (any added sentence must derive from the parent text or a fresh probe).
3. Cross-references between children name the sibling FILE plus section TITLE, never a § number — each child re-derives its own § numbering, and a numeric pointer into a renumbered sibling silently misdirects. Verify programmatically that no parent-§ reference survives in either child. Shared baseline content (live-stack facts) duplicates into both children with identical wording and re-dated probes.
4. Each child opens with: its own decision record quoting the split instruction, a Relationship paragraph (what this doc owns, what the sibling owns, the dependency direction), and a Rev 1 verdict history stating the section-mapping summary, the parent-row renumbering (decision IDs, gaps, D-numbers, T-numbers), and the re-anchor list — the reviewer's fix-verification reads that entry, not the parent. Keep shared test IDs contiguous across the children (parent T0-T8 split as contiguous blocks) so cross-doc test references stay stable. The child's Rev line states the child's date FIRST, then the parent rev with its own date ('Rev: 1 (<child date>) — split from <parent> Rev N (<parent rev date>)'): a split date bound to the parent's rev number reads as a wrong rev date.
5. Review with one reviewer per child in parallel, each told the sibling's doc + status, and put the split-artifact attack angles FIRST: cross-reference validity in BOTH directions, a nothing-dropped sweep of every parent section (content present in NEITHER child is the classic split defect), duplication drift between the duplicated baseline copies, self-containment of the adoptable-now child, runbook coherence (the consuming child's runbook must introduce every mechanism its phases provision before the runbook uses it), cross-doc TENSE (a child must not describe a PROPOSED sibling's outputs as landed — 'already-landed' contradicts the doc's own dependency statement and fails against the box's live state; name the producing phases instead), and mechanism-name coverage (grep both children for every parent mechanism name). When one child's reviewer flags a defect that exists identically in the sibling (a shared header format, a duplicated baseline line), fix both children in the same pass and say so in each dispatch's fix list — an asymmetric fix re-teaches the drift the split just removed.
6. Publishing completes the split: upload each child the moment it passes; then flip the parent to WITHDRAWN (SUPERSEDED → the children) in the registry and move it. Do not edit the parent in place — it stays the fidelity ground truth for every review round until that flip.

## Reviewer dispatch template (keep it self-contained)

- The doc path + rev under review; the comments-file path (overwritten each iteration).
- Ground-truth artifact list (absolute paths) + any official docs URLs. If a ground-truth source becomes unreachable mid-loop (a private repo starts 404ing unauthenticated, a page moves), the last recorded byte-level read stands as the record: corroborate it against one independent record (a sibling doc's header naming the same commit, an earlier round's capture) and have the reviewer disclose the unavailability in the round's method line — never re-derive the fact from memory, and do not let the next round treat the missing source itself as a finding.
- A **declared parent edits** section listing every fix the parent landed before round 1 or between rounds, each with what changed and where, so the reviewer verifies them as parent claims instead of re-litigating them as writer defects; an undeclared parent edit the reviewer discovers is a finding, and the section doubles as the round's declared scope.
- Attack angles specific to the doc's domain (fidelity to source, feasibility, security, internal consistency, ordering, omissions) plus the required unslop AI-tell sweep. Add a COMPOSITION angle whenever the design spans modules that interact at runtime (a runner building argv for a CLI, a caller and callee sharing a contract): walk the composed trace end-to-end — every per-file fact can verify true while their interaction fails, and per-file verification rounds will not find it until one round is told to compose the pieces and walk the result. Add a GATE-INTEGRITY angle for any design with a promotion, review or merge gate: walk who writes and who reads every field the gate checks, because a gate that reads a status or a count the gated party can produce is not gated on the review it promises. The gate must read a verdict field written by the reviewing role and bind it to the reviewed artifact (verdict text plus a hash or head SHA), and a field the consuming stage reads but no producing stage writes is a finding. Run the check at every stage boundary, not just the final merge: a split gate that reads the design hash alone has the same hole. Add a CREDENTIAL-BLAST-RADIUS angle for any design that puts a write credential in a worker environment which also runs untrusted target code (test suites, build scripts, integration gates): that code can read the credential, so the design must scrub it from every gate command through a named wrapper, inject it per call for the privileged client, and state the same-uid residual honestly (a separate uid or a host-side proxy is the hard boundary, not the wrapper). The same angle carries a RULE-TO-EXAMPLE check: grep every concrete example and command the doc ships (the card schema sample, the contract block, the runbook fences) for the pre-rule form, because the example is what a worker copies, so a schema sample that predates the rule teaches the violation and is a finding, not a wording nit. Add a REACHABILITY angle for any doc whose runbook gates an agent-run step against a host-side endpoint: the sandbox cannot reach the box's loopback even with zero privilege problems, so a gate labeled AGENT whose curls target 127.0.0.1 can never pass — split such gates into an M-run on-box mode and an agent-run public-URL mode (a verify script with explicit --pre/--public modes is the proven shape), and note that no-agent cron scripts execute host-side, so a cron health script CAN curl the box's loopback where the agent session cannot. Add a SANCTION angle for any runbook step that shells out to a host-side binary: the step is dead code the day it deploys unless the binary exists AND is sanctioned for the INVOKING user on the target box — a deliberately offboarded capability (a removed binary, a session moved into an MCP service) is exactly that; the design's fix routes through the sanctioned service, and the reviewer checks the invoking-user boundary for every named binary rather than existence alone. Add a FAILURE-SIGNAL angle for deployment designs: every pipeline that must not fail silently (backups, restarts, nightly jobs) needs a failure signal reachable by the monitoring runner's identity — a root-run backup script exits nonzero on every failure path and stamps a success marker into a directory the health-check runner can read, and the daily health check fails the day when that marker ages past the schedule; reviewers in this class have caught a backup script that exits 0 through every failure path while its own prose promised verification. The angle also covers half-policed data: a checker that already fetches a listing must assert every promise that listing can police (freshness, retention, sentinel) — asserting only part of the data in hand leaves the unpoliced promise silent until an unrelated failure surfaces it weeks later. Add an AUTO-UPDATE angle for any design that promises updates on an upstream change: verify the detector cannot be silently disabled (a hosted schedule that expires after inactivity, a webhook that can be unsubscribed), that the detector's own runs do not count as the liveness signal it depends on, and that the consumer side can trigger the producer when the detector is dead. Add a TOOLCHAIN-SCOPE angle for any doc claiming a code defect (cannot import/build/parse/lint): the claim must name the toolchain that ran the failing check and compare it against the project's own floor (pyproject requires-python, CI toolchain pins) — a parse failure recorded under one interpreter version is not the project's defect when its floor parses the same bytes (PEP-level syntax additions flip the verdict, and CI green on the same tip corroborates); re-run the check under the floor's toolchain (a uv-managed interpreter when the sandbox lacks it) before the claim enters the doc's facts, which both rescues false defect claims and produces the capture the doc cites. A parent-supplied defect fact inherits this check. Add a PUBLICATION-SANITIZATION angle for any design that publishes content outside the box (skills, docs, plugin code into a public repo): check the publish list item by item against the doc's own exclusion rule, and treat a claim that the set is "free of machine-specific content" without a scrub procedure and a mechanical grep gate as a BLOCKER, not a wording nit — a skill whose value IS a hostname, an internal address, a personal email or personal measurements cannot be published in any form, and gitleaks catches none of those classes. The doc must name the placeholders, the grep pattern, the excluded items, and the human diff read.
Add a SILENCE-SEMANTICS angle for any design that locks a silent-when-quiet or alert-only-on-change property: every report-producing check must diff against recorded state and the first run must seed silently, because a check that re-emits standing state every run defeats the locked silence for exactly as long as that state stands, which standing vulnerability classes make indefinite — the fix family is delta-everywhere, a silent first-run seed, and a full-state record outside the message channel. The angle also covers the run-shape's own control flow: the quiet path must still perform every action some surface promises per run (the report-file write, the state update, the liveness-marker refresh) — a step list that parks those inside the non-quiet branch ages a healthy quiet watcher into false staleness and a false alert every other run, so walk the quiet run against every surface that says 'every run' before dispatching. For migration/cutover runbooks, point the reviewer at this skill's references/migration-runbook-review.md checklist (ordering and circularity, rollback windows vs in-window steps, firewall/admin paths, address families, certificate issuance paths, residual/straggler bounds, decommission inventory) — these classes recur across every migration doc and are easy to miss in a generic attack-angle list.
- Iteration protocol: read prior comments file, verify each fix landed clause-by-clause (a multi-part fix that lands only its headline reads as landed to the next reviewer, which re-flags the orphaned clause as a partial fix), hunt for new issues, overwrite comments file with iteration header, verdict + tag counts in the final response.
- Put attestations (parent-verified card quotes, in-flight merge authority) in a dedicated, explicitly named section of EVERY reviewer dispatch and restate them each round until a reviewer's report acknowledges them in writing; an attestation buried in dispatch body prose reads as absent to the next reviewer and the quoted material gets re-litigated. When a round's finding ends 'revert or accept as the declared convention', the parent adjudicates per part and the next dispatch carries the ruling as its own named block (which parts reverted, which accepted and on what verified-true evidence) — an unrecorded adjudication re-opens the same finding next round.
- Ask the reviewer to end the comments file with a 'verified clean' section (version currency, config defaults, paths, syntax passes it settled this round) so later rounds and the parent skip re-litigating those claims instead of re-verifying them each iteration.
- Have the reviewer PIN the reviewed state in the comments-file header (doc sha256 + line count at read time, re-checked after every batch) — a mid-round edit by another hand (a parallel session's fold, or a reviewer violating its read-only brief) is then detectable and attributable instead of silently absorbed into the round's verdict; the disclosure note that hash enables is what keeps fix-verification aimed at the text that actually exists. On a hash-gate mismatch, settle the expected string itself before refusing: read the live hash as a codepoint-chunked dump (defeats the channel's long-token masking) and require exactly 64 hex chars — a dispatch hash that shares the prior pin's or the live doc's 16-char prefix while running long (65 chars) or diverging mid-string is a composition artifact (an off-by-one splice), arbitrated by byte-reproduction plus inverse-reconstruction against the prior pin (undo the prescribed fixes; the result must byte-equal the prior state), not by refusal (Nov 16 2026). Put the EXPECTED doc sha256 in the dispatch itself with an explicit refuse-to-proceed gate (copy fresh from the live tree, re-hash, refuse on mismatch) — compose that pin LAST, after every doc edit is on disk, immediately before the dispatch call, because one small edit landing between the hash computation and the dispatch wastes the round on a mismatch or forces a stale-pin adjudication — and as the parent verify the report's pin equals the dispatched hash BEFORE acting on the verdict — a round that reviewed its own stale pinned copies produced a confident verdict against wrong bytes and voided entirely. Voiding is two moves: strike the verdict in the loop record, then TRIAGE the round's findings against the current bytes before discarding (a stale-bytes round can still surface real defects — fix the real ones anyway), and salvage any record corroborations its transcript earned before it died.
- Tell the reviewer the comments-file overwrite can trip the stale-read write guard: if write_file refuses, write the round's content to a staging path and move it over the target after reading the current file in full — never loop on the refusal (separate loops each burned minutes on it before the workaround was shared). When the doc or evidence quotes auth-header material, warn the reviewer that the tool channel masks credential-scheme words in its DISPLAY (the word Bearer renders as asterisks): a redaction-artifact finding must be settled by codepoint or shape against the file before it stands, or it is a phantom that costs a round — and reword maskable scheme words out of prose where a neutral phrasing reads naturally ('an Authorization bearer credential') so no future masked-display reader re-flags it. Tell it too that its sandbox gates execute_code whole-script even when the parent's surface runs unattended: have it run its machine checks (bash -n on fenced blocks, JSON parses, sha pins, count sweeps) as plain terminal commands, split oversized grep batteries into several simple commands (the command guard hard-blocks deeply nested inline payloads and the whole battery dies unexecuted) — a check needing more than a one-liner runs as a staged plain script file, since heredocs and whole-script execute_code trip approval gates — and record everything durable in the comments file — the delegation transcript prunes after the round, so a full-text capture or probe result that lives only there is unrecoverable afterwards. /tmp is a small tmpfs (512M class) that FILLS with accumulated check tempfiles mid-round and kills the remaining battery with 'No space left on device' — delete each round's staged check files when the battery completes, and run the fence/census battery before any large staged artifact lands in /tmp. When the gate blocks the reviewer's machine checks anyway, have it disclose them as owed in the round record, and the parent runs the battery itself as a staged plain script (write_file the script, run `python3 <path>`), handing the results to the next round as settled facts — re-running a disclosed-owed check as a fresh reviewer task burns a round for what one staged script answers.
- When the operator sets the zero-findings bar (overnight runs), add to the dispatch context verbatim: 'treat every finding you can justify as valid, but do not manufacture noise to seem thorough; when genuinely nothing remains, write CONSENSUS: reached with zero findings' — without the noise-avoidance clause reviewers pad the final sweep with weak findings and the loop never terminates. Pin the verdict semantics in the same context: under this bar 'CONSENSUS: reached' means zero findings at every tag, and any finding at any tag is 'CONSENSUS: none' with the count — a reviewer that reports 'reached' while attaching a residue list has applied the default bar to a zero-findings round, so the parent must not read that verdict as a close and the next dispatch restates the bar inside the verdict line itself. In late fix-verification rounds also name the class migration the loop has walked (falsified records → provenance and placement → record precision) and state that the current round's fix list is complete for it — the reviewer's hunt then targets the live class instead of re-finding closed ones.
- When a fix round leaves known-good look-alike defects (a product-name spelling the source itself uses beside an API-id spelling the design must carry, a historical rev mention inside a sibling's History cell, a decimal that merely contains a matched pattern), enumerate them in the dispatch as EXPECTED EXCEPTIONS with their ground truth — the reviewer then verifies each against the source instead of spending a finding re-flagging it,  and the exception list doubles as the fix round's scope statement (every exception the reviewer CANNOT confirm against the named source is a real finding, so the list raises precision without lowering the bar). The same sweep covers every KIT file whose comment text names a renamed value — a deploy script's precondition comment counts as a finding when the hostnames it names are stale, so the kit-side rename list is part of the fix round, not the reviewer's discovery work. When the fold adds corrections-index rows, the index's own meta-mentions of fixed strings (a row describing a re-point cites the OLD value) join this list — an index that records fixed defects always contains the defect strings as objects of record. The index's HEADING must cover every class it records: when the first doc-internal correction (a fix of this doc's own earlier claim, not a parent-brief or sibling correction) lands, widen the heading to say so — a heading narrower than its contents sends every later round re-litigating whether the row belongs.
- One reviewer task per delegate_task call. The reviewer's own final response carries the verdict, so a companion task like 'return the review verdict' is a stub child that has nothing to do: it burns a dispatch, has to be stopped, and returns an interrupted no-summary record. If a verdict forwarder is genuinely needed (delivery into another chat), make it a `deliver` setting on the reviewer dispatch, not a second child.
- If a `delegate_task` dispatch errors reporting dozens of tasks for a one-element array, the JSON mis-serialized mid-flight (typically an escaped-quote run inside a context string) — rewrite the context with single-quoted inner material and resend as one task; do not retry the identical payload. The same mangle shape bites any hand-built nested JSON payload carrying comma-dense or quote-heavy replacement text (a batched-edit call that reports 'must be an object with name and arguments' instead of applying edits); stage such an edit set as a script file rather than hand-embedding it.
- **Route every long loop brief (writer brief, reviewer fix-verification list, attestations + expected exceptions) through a BRIEF FILE, not the dispatch's context string.** Write the full self-contained brief to a durable path in the synced design tree (`<stem>-design-evidence/r<N>-review-brief.md` shape for reviewers) and dispatch with a one-sentence goal ('read your full brief at <path> FIRST and follow it exactly: pin gate, fix-verification list, attestations, verdict semantics') plus a context line naming the doc, the round, and the ground-truth surfaces — hand-composed dispatch payloads carrying a long brief have dropped the context field entirely, landing the child on a one-line goal with no brief and no error (two reviewer dispatches in one loop burned this way before the file route ran clean); the file carries the identical content with a payload small enough to compose reliably. Manifest the brief file in the evidence README's corrections index as a transient round artifact, and delete the briefs at loop close.
- Two file entries with the SAME path inside one `push_files` call do not merge — the second silently overwrites the first, and a large doc split across entries in one call ships only its tail (hit 2026-11-18 on the strava-export-import publish; the branch blob sha exposed it). A payload too big for one call is split across COMMITS on the same branch, never across entries in one call. The post-push blob-sha check (intended `git hash-object` vs the fetched branch blob) catches exactly this class before any PR or merge.
