# Relay remote probes (approved read-only probes on a host the agent sandbox cannot reach)

Class recipe for an adopted-design phase 0 — and any later probe pass — on a target the agent sandbox has no SSH path to. The publishing-side relay mechanics (slot contention, payload traps (a)-(m), fire scheduling) live in `references/publishing-and-target-identity.md`; this file covers what is specific to PROBES. Do not duplicate those traps here.

## Context map (what each side can see)

- **Agent sandbox:** `/workspace` and `/home` are container-local. The sandbox's `/home/hermes` holds only the shared mounts (`design-docs`, the MCP spool) — no `.ssh`, no `.hermes`, so no SSH from the sandbox, period.
- **Cron no-agent executor:** its `$HOME` is NOT the host home and has no `.ssh`; `/workspace` does not resolve (publishing reference (g2)). Reference every file by ABSOLUTE `/home/hermes/...` path on a shared mount.
- **the operator's host shell:** the real `/home/hermes` — keys, `~/.hermes/scripts`, the target's trusted state. The only writer for files that must land in `~/.hermes/scripts/`, AND the only reader for files behind his 700-mode home (`~/.config/systemd/user/`, `~/.ssh`, ssh client configs): the relay executor cannot traverse the 700-mode home, so capture unit texts and config shapes by redirecting the operator's own shell one-liner into the evidence mount (`{ probes... } > <evidence>/P<N>-<name>.md`).
- **Shared surface all three see:** `/home/hermes/design-docs/**` (design tree + evidence dirs). Stage everything there.

## Recipe

1. Agent stages, inside the doc's evidence dir (a 0700 subdir, e.g. `.probe-auth/`): the probe script (read-only command list; `sudo -n` where the box grants passwordless sudo) and, for SSH, a copy of the admin key (0600) plus the target's known_hosts line — or accept-new with the fingerprint printed into the fire output for the operator's one-time audit against his laptop's pin.
2. the operator heredocs the payload wrapper into `~/.hermes/scripts/<private-name>.sh` (the agent cannot write there; a private name beats the shared slot's cross-session contention, publishing reference (h)/(g3)). Payload: absolute `/home/hermes` paths only; `ssh -i <staged key> -o UserKnownHostsFile=<staged pin> -o StrictHostKeyChecking=accept-new`; capture redirect into the evidence mount; end with `exit "${PIPESTATUS[0]}"` (publishing (e)); stream the report to plain stdout for `deliver: origin` (publishing (i)).
3. Agent fires a one-shot no-agent cron job, `script=<private-name>.sh`, with an ABSOLUTE timestamp from a fresh `date` (publishing (j)). A one-shot missed while the gateway is down is SKIPPED — after any gateway fix, check the job's `last_status` before assuming it ran: state `scheduled` + null `last_run` means still pending, not failed.
4. The capture lands in the evidence mount; the agent reads it by path parity and adds the manifest row.

## Pitfalls (each has bitten)

- A no-agent fire whose payload routes its output into its own out-files can
  deliver as "Status: silent (empty output)" while the run fully succeeded —
  the completion block reports the CRON-delivered stdout, not the payload's
  artifacts. Verify via the payload's bind copies / out-file before deciding
  anything failed; silence alone is not a failure signal and a blind re-fire
  of a mutating payload is the risk it exists to prevent.
- The payload's capture path is FIXED (one RAW target): a second fire overwrites the first capture, and a capture RESTORED to the RAW name is destroyed by the next fire. Preserve one renamed copy per capture BEFORE firing the next, keep each capture under its FINAL numbered name (never restore an old capture to the live RAW path while more fires may run), and rename only AFTER the fire completes (`last_status` ok) — a rename between overlapping fires destroyed a capture once.
- Before numbering a new capture, grep the doc for reserved forward ranges (`P<N>+`) — a reserve consumed by the new capture misnumbers every later probe; take the next free number past the highest reserve and move the reserve in the same fold.
- A systemd `systemctl --user show <unit> -p <Prop>` query can print a DIFFERENT field than asked (a `-p RestartSec` query returned only `Restart=always`). Cite the unit FILE's own directive line as the authority for deployed values, and word the doc's cite accordingly ('the deployed unit's RestartSec=10 line, P25'), never 'the effective value measured via show'.
- Staged-credential custody: the copied admin key lives in the evidence mount for the probe campaign only — which ENDS when the probes end, not at decommission. Shred it immediately after the last probe (the capture's own log then records a post-shred relay attempt FATALing on the missing key: free, on-record corroboration that the copy is gone). The doc's decommission inventory records the shredding as VERIFIED ABSENT; scheduling the shred for decommission leaves a live private-key copy in a shared mount for weeks.
- accept-new records the first key presented. Print the fingerprint into the fire output and get the operator's one-time audit confirmation before relying on the pin beyond the probe itself (the runbook's own fingerprint gate re-checks at build).
- Probe the approval-surface reality first (SKILL.md step 2 pre-flight): an approval-gated command the user never answers stalls the whole turn. When the gate blocks, fold the probe into the doc's own runbook as a phase-0 step (which is exactly where it belongs) and run it through the relay instead of retrying the gate.
- Write the probe script through write_file into the shared mount — sandbox-terminal writes to container-local paths do not reach the executor, and a heredoc inside the payload doubles the mangling risk (publishing reference (l)).
- Prefix every step you hand the operator to run himself (a heredoc payload, a key copy, a known_hosts pin) with one plain-words sentence naming what the step achieves and why the previous attempt failed: a sequence of deep-plumbing commands without purpose statements reads as noise and prompted 'explain to me in simple words what are you actually trying to do' — the ask means the narrative lost him, so restate the goal before the next command instead of appending another bare command block.
- Reading a cron job's stored prompt from a relay fire (hit 2026-11-22, five fires on one read): no greppable config file carries it — the full prompt lives in ~/.hermes/state.db `messages` (the creating/updating session's tool_calls), where tool_call-wrapper arguments nest one JSON level deeper as an OBJECT, and a CREATE call contains no job id. Route: query tool_name='tool_call' plus the job NAME, unwrap calls[].arguments, print .prompt; then sweep cronjob_manage rows carrying the job id to confirm no later update replaced the prompt. And: no-agent 'deliver: origin' never re-entered the live desktop session across five fires — the executor's $HOME is /home/hermes, so its out-file (the operator sudo-cat) is the reliable read-back.
