# Publishing and target identity (design-doc adversarial review)

Depth for two failure classes that cost whole loops when missed: building the doc on the wrong artifact, and the publish mechanics for docs too large for inline pushes.

## Verify the target before dispatching research

A task name can denote different artifacts over time (renames, sibling apps sharing a brand). Before dispatching the research subagent, verify which artifact the name denotes: probe the live hostname (HTTP status and what answers it) and read the repo's self-description (GitHub repo description, README, about page) via the repo tools. Parent memory of the referent is a hypothesis for the researcher to re-derive, not a fact to build on.

If fresh research contradicts the assumed referent, stop and re-confirm the target with the user before any review round: a full doc-plus-loop on the wrong app is the expensive failure mode. Park the wrong-target doc renamed to its true subject instead of deleting it (the research and house format may serve that app later), and fix the parent's memory entry that carried the wrong identity. When later clarify answers reject earlier locked decisions because they were aimed at the wrong referent, re-decode the entire locked-decision set against the revealed target before folding; answers aimed at the wrong referent carry no scope. Re-fire a timed-out clarify card only when the user asks for it; otherwise restate the open questions as numbered one-liners.

Before re-firing or re-asking at a resume, verify the prior turn actually died: delegate list for running children, and search_files (target='files') on the doc plus evidence dir the turn promised. A card with no recorded result may have been answered into a turn that died mid-flight; a doc on disk means the loop moved past the card, and re-dispatching then duplicates work. When restating, pull the questions verbatim from the session record (the card's arguments survive in the message's tool_calls) instead of reconstructing from memory; the user answers by number against the list on screen.

## Git-era publish via the host relay (docs too large for push_files)

The design repo's branch protection makes every publish a branch, PR, and squash-merge. A single ~60-70 KB file CAN ride one inline `push_files` call (one file per call, git-blob-SHA verified against the local file after each push); the relay below is for multi-file batches and payloads that break the tool-call size itself. Three inline-push failure modes ship silently, and one close-out check catches all three: (1) the content API writes exactly the inline string, so a missing trailing newline lands on GitHub and fails MD047 in the required `docs` CI context — end every inline content with an explicit trailing newline; (2) emit drift between the tool-call string and the reviewed text goes unnoticed without a hash — after each push, fetch the file back and compare the SHA in the `successfully downloaded text file (SHA: ...)` header against the locally computed git blob SHA, `sha1("blob <len>\x00" + bytes)`, and on any mismatch re-emit and re-verify before touching anything else; compute that local blob sha AFTER the last content edit — a closing bookkeeping rev (Rev/verdict-history/status refresh) changes the bytes, and a DESIGN-INDEX row whose git-blob cell cites a pre-bookkeeping blob ships a stale cite inside the same push; the blob is content-derived, so compute it from the final staged bytes and put THAT value in the row; (3) nothing forces every file in a multi-file push to be real — emit each file's full verified content in the same call, never a placeholder or a to-be-filled stub, and give the DESIGN-INDEX row the same SHA check whenever it rides the push.

**Sandbox-local clone fast lane for registry transitions:** a git clone INSIDE the sandbox runs the whole small-transition lifecycle without the relay or push_files. Do not assume the clone, `/root` or the `gh` binary survive between sessions: with `terminal.container_persistent=false` the container is ephemeral per spawn (fresh `/tmp` and `/root`, and the image ships no `gh`), so re-clone and reinstall `gh` each session or use the host relay. The slopervisor token answers `gh auth status` once `gh` is on PATH. The lifecycle is: `git fetch origin main`, branch, byte-exact `git mv` for the folder move (a 100 percent rename proves it), python `split('|')` row edits with the pipe-count assert, commit, push, MCP PR, checks, self-merge, blob-verify main. Always fetch origin main first (main moves between sessions; the branch base must include the newest commit), verify the staged file's blob with `git hash-object` before the push, and re-clone fresh when the persisted clone is missing. Prefer it for small registry mutations (withdrawals, status flips, row inserts), and it also carries a full new-doc publish: clone, branch, copy the final into PROPOSED/, append the DESIGN-INDEX row, lint, commit, push, `gh pr create`, `gh pr checks`, `gh pr merge --squash --delete-branch --match-head-commit`, then blob-verify main. An 80-90 KB doc plus its index row is well inside this path; the host-clone relay stays for payloads that break the tool-call size or for kit repos the sandbox cannot clone.

**One-call publish in an ephemeral sandbox.** When `terminal.container_persistent=false`, the container can be replaced between calls (fresh `/tmp` and `/root`, no `gh` in the image), so a multi-call publish loses its clone mid-flight. Run the whole lifecycle in ONE terminal call from a script staged in the synced tree: clone with an inline credential helper (`git -c credential.helper= -c 'credential.helper=!f(){ printf "username=x-access-token\n"; printf "password=%s\n" "$GH_TOKEN"; }; f'`), branch, stage the final and the index row (compute the git blob in the same script), commit, push, open the PR with `curl -X POST $API/repos/$OWNER/$REPO/pulls -d @pr.json`, poll `GET /repos/$OWNER/$REPO/commits/$HEAD/check-runs` until both required contexts are `completed: success`, then `PUT /repos/$OWNER/$REPO/pulls/$NUM/merge` with `{"merge_method":"squash","sha":"<head>"}`. Keep the token in the environment, never in argv; on a rerun, fall back to listing open PRs for the branch when the POST fails. Verify the merged blob on main in a second call, and copy the merged doc and index back into the synced tree.

**MCP 403 on the private design repo is the fallback trigger, not a blocker.** A `get_file_contents` on `<your-org>/design-docs` can return `403 Resource not accessible by personal access token` while the sandbox's `gh` is logged in as `slopervisor` with push access; when that happens, run the whole lifecycle through `gh` (clone, branch, push, PR, checks, merge) instead of the MCP tools. When `gh` is absent, the forwarded `GH_TOKEN` REST route in `github-pr-workflow` runs the same lifecycle from a Python `urllib` script (token from `os.environ`, never a command line). A stale git credential helper pointing at a missing gh binary dies `could not read Username for 'https://github.com'`; run `gh auth setup-git` once (the gh on PATH) and fetch/push work. Verify the merge server-side with `gh pr view <n> --json state,mergeCommit`: the local `fatal: Not possible to fast-forward` warning after `--delete-branch` is the post-merge branch switch, not a failed merge.

**Push-transport mangling (hit live: three repair pushes on one publish).** The transport does not preserve the content parameter byte-for-byte, and the two failure shapes have different countermeasures:
- **Trailing newline stripping is inconsistent, not absent** — the same emission discipline produced a landed file WITH the newline once and WITHOUT it twice, and elsewhere in the same period exact bytes landed as-sent twice while a pre-emptively doubled buffer SURVIVED (+1 byte) and cost a repair push. The strip is not a constant to engineer around but a hazard to verify against: push exact bytes, blob-verify, and repair only on evidence (re-push with one added newline if the strip fired this push; re-push without the buffer if a doubled buffer landed). Keep the doubled buffer only for a session where the strip is CONFIRMED active — pre-emptive doubling when the strip does not fire ships the extra newline and costs the same repair push.
- **Backslash runs mangle unpredictably** — the same emission pattern landed one backslash count on one push and a different count on the next; hand-JSON-escaping the content parameter double-escapes (emit parameter values as literal text, never pre-escaped). Countermeasure: when a push drifts on a line containing backslash-escapes (shell-quoted JSON bodies, `\"` sequences), verify the disk truth by counting backslashes programmatically (`sed -n Np | tr -cd '\\' | wc -c`), then RESTRUCTURE the offending line backslash-free in the source (e.g. build a JSON body with `printf '{"k":"%s"}' "$v"` inside `$(...)` instead of `body="{\"k\":\"$v\"}"`) and bump the Rev line with a disclosed accommodation — behavior-identical, bash -n green — rather than fighting the transport with more escaping attempts.
- **Transcribing pushes byte-exactly without programmatic access: the chunked-write pipeline.** When the pushing context cannot pipe the file programmatically (a subagent with no git/gh/token in its env, push_files taking inline content only), the proven pipeline is: read the source file in chunks into scratch files, concatenate, `cmp` the result against the original (or md5/git-hash compare), then push the verified string. Every transcription rides cmp/hash gates, never the display: the transport redacts Bearer-prefixed patterns in read_file and terminal output (an `Authorization: Bearer ${PAT}` line DISPLAYS as `Bearer ***`), so a mask transcribed from display ships the mask into the pushed file — restore the true bytes from disk before pushing, and verify by counts and hashes, never by echoing lines. Table-separator cells and rare spellings are the other classic transcription slips; the byte-compare gate catches both pre-push.
- **The masking also covers credential NAME placeholders, not just Bearer-prefixed values** (hit live Nov 17 2026, the update-cve-watch publish): a doc's literal `PROTON_MCP_BEARER` placeholder inside an example fence was shortened on EVERY agent-side emission (proven by 24-byte micro-emission bisection), so that file can never push byte-exact from an agent session, whatever route or retry discipline. Fix: the subagent stages the true-bytes source on the workspace bind, asserts its sha256 and git blob inside the relay payload, and the no-agent fire does the final write host-side (fresh clone, blob asserts both sides, CI gate on `mergeable_state: clean` plus the Actions runs API, squash-merge per the repo AGENTS.md, post-merge sha256 verification) — the same lifecycle the publish payload already runs, extended with the doc-copy step. Orchestration split that rides this shape: a delegate subagent's toolset has no cronjob_manage, so the subagent that stages the payload CANNOT fire it — its report hands the fire back to the parent session, which creates the parked one-shot (`schedule` far-future, `script: run-staged.sh`, `deliver: local`) and runs it via action=run (the slot-theft-safe pattern), then reads the payload's out-file through the workspace bind for the PUBLISH-OK/FATAL sentinel. Also: in-session blob-bisection probe files must never land on the branch — they ship as stray `PROPOSED/.p-*` commits and the payload's cleanup step deletes them; keep probes in scratch, not on a shared branch.
- **Post-merge commits to an already-merged branch are STRANDED.** Pushing follow-up commits to a branch whose PR has already merged does NOT update the merged PR, does not notify, and does not reach main — the commits sit invisible on the dead branch while the box-side copies and the doc's kit-content claims drift from kit main (live hit: MemoryMax caps, a display-name correction, and a cache-purge lesson sat unmerged for a day while every surface claimed them merged). Countermeasure: the moment a PR merges, treat its branch as dead — any follow-up for the same kit goes on a NEW branch off the strand tip and a NEW PR that the body names as consolidating the strand ("post-merge strand" pattern: branch from the dead branch's tip so its unmerged commits ride in), and every doc/index claim about merged kit content is verified against kit MAIN (get_file_contents), never against the dead branch's state.

**The blob-verify loop is the only truth**: fetch the pushed file back (get_file_contents, its SHA header = the real blob), diff against the local reviewed copy, and attribute each drift before re-emitting; a blob that matches the local reviewed copy ends the fight regardless of how many pushes it took.

**Pre-publish lint gate: run the TARGET REPO's pinned linter against the doc before the publish PR.** The loop's own hygiene battery (unslop, dash/quote greps) does not cover the target repo's markdownlint rules — MD028 (blank line inside blockquote, fired by separate `>` quote blocks joined by a blank line; fix with `>` continuation lines) bit after publish and left main's required lint context red for a cycle. MD056 (table column count) is the second recurring hit: pipes INSIDE code spans in table rows count as cell separators, so a grep pattern carrying pipes inside a `|`-delimited cell adds phantom columns while the lint names the row and the extra count; escape each pipe as `\|` inside table code spans (renders literal), a mechanical fix localized by the lint's line numbers — disclose it as a publish-prep mechanical edit in the close rev when the doc's loop already closed on the pre-fix bytes. Recipe: fetch the repo's lint config, replicate it as `.markdownlint-cli2.jsonc` in a scratch dir (markdownlint-cli2 has no -c flag; it only reads the dotfile from the scanning tree), copy the doc in, run the repo's pinned version (`npx --yes markdownlint-cli2@<pinned>`), and fix every hit before the PR. When publishing from a sandbox clone, skip the scratch copy and run the pinned version from the clone root: the committed config is found automatically and the whole tree lints in one pass. The sandbox wipes /tmp between calls, so recreate the scratch dir (or keep it under the sandbox HOME) every session that lints — a surviving dir from an earlier session is a stale assumption, and a repo without a committed lint config means the config itself must be rebuilt each time from the repo's CI workflow or a fetched copy. After the merge, re-verify the merged blob on main against the local reviewed copy — a merge that succeeds with `mergeable_state: unstable` can still carry a red lint context (unstable = failing/pending NON-required checks; required failing would read `blocked` and refuse the merge), so the post-merge blob check plus one local lint run of the merged bytes is the real green confirmation.

1. Copy the final doc to the workspace bind as `<stem>-design-final.md` and sha256 it. Stage into a FRESH per-publish directory on the bind — never clean or rm -rf an existing staging tree from the parent side, because a destructive-looking parent-side command trips the approval gate and stalls the unattended run on the consent timeout (stage fresh, or let the payload itself clean); the same discipline applies to every staged input batch. Verify you are actually on the bind before staging: from inside the sandboxed backend the sandbox-side bind path is `/workspace`, confirmed by `/proc/mounts` (the bind shows as a real device mount there) and by prior relay residue (older `out-*.txt` files, nonce files, `staged-payload.sh.prev-*`) — a `write_file` that reports creating a directory you expected to pre-exist means you are on a container-internal path the host-side payload cannot see. Stage the final in TWO places: the bind (the payload's first-choice source, addressed by `$BIND_DIR`) and the synced design tree (host-reachable by path parity, doubling as the post-publish local record) — one staging location is a single point of failure, and the payload should try `$BIND_DIR/<stem>-design-final.md` first and fall back to the tree path.

**Publish-payload input and read-back traps (hit live Nov 12 2026 — a wrong-looking branch, a wasted repair push, two red herrings):** (a) every payload input is staged through the workspace bind with a sha256 computed sandbox-side and asserted as a literal in the payload (refuse on mismatch); never let a payload read `/home/hermes/...` inputs directly — path parity is NOT guaranteed for every subtree, and the workspace bind is the one guaranteed channel. Refinement (hit live 2026-11-13, docker-sandboxed desktop backend): SANDBOX-TERMINAL writes to /workspace did not reach the host slot — only write_file-side /workspace writes did (the slot resolves at $HOME/.hermes/sandboxes/docker/default/workspace/staged-payload.sh); the synced design tree path IS two-way live (the payload-side sha check passed from the tree). So stage every payload input via write_file into the bind, or via the synced tree with the sha assert — never via sandbox-terminal writes to /workspace, which read as a missing staged file (two FATALs from one cause, two fires burned). And spell git calls inline (`git -c credential.helper="$H" fetch ...`): a GIT='...' variable invoked as a bare `GIT fetch` dies 'command not found' and burns another fire. (b) The diagnostic of record after any push is the pushed content read back via the COMMIT endpoint (get_commit's per-file stats), not the payload's DONE banner and not the contents fetch: the contents API can serve STALE bytes for a branch right after a push or force-push — it returned the pre-push blob sha for a branch that provably moved, which read as 'the push landed wrong content' and triggered a redundant repair. When a contents fetch disagrees with a confirmed push, re-check with get_commit before concluding anything about the push. (c) When a manual `cronjob(action='run')` job's scheduled tick also remains live, it re-executes the slot payload at its own time — remove the job the moment its manual fire returns, or a second ghost fire runs the payload you meant for yourself. (d) Payload sanity greps are REGEXES: an unescaped `**` after a character is a quantifier and never matches the literal `**` in the text, so the guard fails and reads as 'the doc is wrong' when the doc is fine — escape metacharacters (`\*\*`) or use `grep -qF` for literal guards. (e) The `{ ...; exit 1; } 2>&1 | tee "$OUT"` wrapper runs the block in a subshell, so `exit 1` inside kills only the tee stage and the fire reports ok while the FATAL sits in its stdout — end every payload with `exit "${PIPESTATUS[0]}"` so the fire's real status surfaces in last_status.
(f) The index-row insert rides a pipe-count assert (10 pipes for the 9-column table) and the payload normally runs without `set -e`, so an assert failure kills only the insert while the doc still commits — verify the row commit's FILE LIST via get_commit (one DESIGN-INDEX.md file, 1 addition), never the commit message or the DONE banner; hit live 2026-11-13 when a 9-pipe row cost a second fire — and a second time the same day because the fix round rebuilt the row as multi-piece string concatenation again and dropped a separator again. Assemble the row as ONE literal line and count its pipes sandbox-side BEFORE staging: multi-piece concatenation is where cell separators get dropped, and the assert is the backstop, not the layout method. For a row REPLACE on an existing doc, locate the row by its Doc-cell startswith match and rewrite the whole line the same way.
(g) One-shot relay jobs auto-disable after their scheduled fire: a later manual `action: run` then refuses ("paused/disabled") and `resume` refuses a past one-shot time — the second fire needs a NEW one-shot job. Scheduler lateness up to ~1 minute past the fire time is normal, and an empty out-file after a successful fire is the known flush quirk already covered above.
(g2) Host-side `/workspace` does NOT resolve for no-agent cron scripts (the spanish-tutor and jumpbox fires both died on `tee: /workspace/...: No such file or directory` while the identical path works from the sandbox bind) — payload out-files and staged inputs must live at `$HOME/...` paths (`OUT="$HOME/<name>-out.txt"`), and a failing `tee` under `exit "${PIPESTATUS[0]}"` still exits 0 because PIPESTATUS[0] is the block's exit, not tee's: an "ok" fire proves nothing about the report until the report's byte count is verified or stdout carries it. (g2b) The visibility asymmetry is between MOUNTS, not between hosts: the synced design tree (e.g. `/home/hermes/design-docs`) is visible to BOTH the sandbox and the relay executor, while the sandbox's workspace mount and the hermes user's own 700-mode home (`.ssh`, `.config`, anything outside the design tree) are visible to neither the other side nor the executor. A direct-script fire (a private `script: <name>.sh`, bypassing the wrapper) therefore resolves shared-tree paths but not user-home paths: stage every direct-script input under the shared tree and have the user's shell capture user-home files INTO it (one `{ cat ...; } > <shared-path>` command). The user-home files a probe needs are captured by the user, never by the relay.
(g3) A root-owned install is a one-line user gate that beats slot contention entirely: stage the script on the spool (`/srv/mcp_files/send/<name>.sh`), have the user run one `install -m 755 ... /home/hermes/.hermes/scripts/<name>.sh`, and fire with `script: <name>` — no shared slot, no ghost overwrites, no foreign-payload theft. The spool is also wiped by HOST REBOOTS, not just per-session: after any reboot on the box, re-stage send-side payloads and re-download receive-side artifacts (an export pulled the day before is gone) before firing — yesterday's successful read of a spool path proves nothing about today. For reports the user needs to see, `deliver: origin` re-injects the stdout into the originating chat; `deliver: local` writes it into chat history where a running session never sees it (three fires lost this way before the rule was written down).
(g4) No-agent fires run as the HERMES user, not root: they cannot traverse `/home/mcp` (the `-d` test fails with FATAL even when the dir exists — hit on the garmin supplement ingest Nov 14, both fires) and cannot chown to another user. Any op needing root (store writes under /home/mcp, chown) goes through the user's sudo on a single command or a root `/etc/cron.d` entry, never through the relay.
(g5) `exit N` inside the redirected `{ ... } > "$OUT"` block kills the whole wrapper before the REPORT START/cat block runs — the fire then reports exit N with empty stdout while the real output sits unread in $OUT (the FATAL was only found by the user tailing the file). Failures inside the block must fall through to the report (e.g. `FAILED=1` flag, or wrap the body in `( ... )` and capture `$?`).
(g6) A deployed server missing a feature does not mean the code never merged — CI builds the ghcr image asynchronously, so `update.sh`'s "already on the latest image" was only true for the moment it ran: an image built before that hour's merge ships without the feature until a later build lands, and env knobs for it sit inert (no store block in api_status for days while the store PR was merged). Before debugging config or env for a missing server feature, compare the running image digest against ghcr's CURRENT latest manifest digest — `curl -s "https://ghcr.io/token?scope=repository:<org>/<image>:pull"` for the token, then `curl -s -H "Authorization: Bearer $T" -H 'Accept: application/vnd.oci.image.index.v1+json' https://ghcr.io/v2/<org>/<image>/manifests/latest -D - -o /dev/null | grep -i docker-content-digest` — and reconcile with update.sh FIRST: digest mismatch means pull, digest match means the problem is env or code.
(g7) Dry-run a mutating helper against a TEMP destination on the real input data before handing it to the user as a sudo command: a substring path filter that assumes zip namelists carry a leading slash, and a patch that leaves the write block indented inside an `else`, both surface in seconds in a temp-dir dry-run — in the field each costs a full user round-trip per discovery. Same rule across script versions: an idempotent script whose path-derivation rule changed between runs re-lands already-written files under the new path as duplicates — keep the landed layout stable, or remove the orphaned old-path copies in the same run.
(g8) Off-host carriage from root cron scripts rides the box's MCP services, never a hermes-side CLI (the hermes-side proton CLI is offboarded — its session lives in the MCP server): stage the artifact through the shared spool (`/srv/mcp_files/send/`, 0644 suffices for an encrypted blob — the container's keep-id identity reads it over its bind mount), drive the server's loopback MCP (initialize → notifications/initialized → tools/call, bearer from the server's env file read as root through the curl stdin-config precedent, never argv), verify the committed name/size in the tool result, and remove the stage on every exit path (the spool is tmpfs — RAM). The MCP has no folder-create verb: a needed Drive folder is a one-time user-side creation step.
(h) The slot is a GLOBAL cross-session resource: a live parallel session stages and fires its own payloads between your stage and your fire, silently replacing yours. When contention is active, poll the slot's marker; when it changes to a foreign payload, wait out that session's fire (its jobs run 'in Nm' schedules, so the fire lands about N minutes after each of its stages, plus up to ~1 minute scheduler lateness), then stage your payload and create the fire job immediately in the gap — the payload's own marker guard turns a lost race into a clean exit-3 retry, never a wrong-task execution. The scheduler rejects absolute script paths (`script` must be relative under ~/.hermes/scripts/). When gap-timing loses repeatedly (multiple foreign stages per minute), bypass the slot entirely: have the user install a PRIVATE script into ~/.hermes/scripts/ — from the spool (`install -m 755 /srv/mcp_files/send/<name>.sh /home/hermes/.hermes/scripts/<name>.sh`) or pasted through a heredoc when the spool path cannot resolve host-side — and create the fire job with `script: <name>`; the scheduler then execs your private script, the shared slot never enters the picture, and no `/workspace` dependency exists (g2b: resolve all paths inside the shared tree). Keep a private copy of your own payload outside the slot file — a foreign session can overwrite the slot and even delete your bind out-files mid-flight (observed: out-files vanishing between calls); the spool copy doubles as the private copy. The bypass has a per-script install cost (one user line per script), so batch related operations into ONE payload rather than round-tripping the user per step, and when a payload needs a fix, re-issue the same install line for the UPDATED spool file — the scheduler always runs the freshly installed bytes. The reverse hijack has no marker guard: your own scheduled fire executes whatever the slot holds at fire time, and a sibling that re-stages inside your scheduled window makes your fire run THEIR (still-valid) payload — your self-gate never runs because the file is not yours. Detect it from the fire record's stdout banner naming a foreign task (or your out-file never appearing), treat the foreign execution as usually-benign (their idempotent work ran once more), and disclose anything it stranded mid-flight — a branch their payload pushed before its own crash is THEIR recovery to complete (a fresh PR off the strand tip), never yours to clean up. Re-stage and re-fire with an absolute one-shot timestamp and a tight window; prefer the parked-create + manual-run pattern whenever a sibling is actively cycling the slot.

(i) When the parent must READ the payload's output (probe reports, smoke ladders, comparison verdicts), create the fire job with `deliver: origin`, never `deliver: local` — a local delivery writes the stdout into chat history as a note that never re-enters the running session. An origin delivery posts the verbatim stdout back into the originating chat; keep the payload's stdout bounded (trim tool responses to the sections that matter) so the delivered block stays readable. Deliverability mechanics, learned after FOUR fires in a row reported ok with the report lost: (1) no-agent cron scripts run host-side, where the bind path under its sandbox name does not resolve — write the durable report to a `$HOME`-anchored path (e.g. `OUT="$HOME/<name>-out.txt"`), never `/workspace/...` or a bind name (the host-side sandbox workspace lives under a different absolute path than the sandbox sees); (2) the report file is written INSIDE the payload with a direct redirect (`{ ...; } > "$OUT" 2>&1`) and a `sync` after — a `| tee "$OUT"` can leave the file empty (buffer unflushed when the scheduler records the run) while the block itself still exits 0, so last_status ok proves nothing about the report; (3) end the script by streaming the report to plain stdout with a final `cat "$OUT"` — a pipe-free write the scheduler capture receives whole — then read the delivered block, falling back to the $HOME out-file. A tee failure is silent under `exit "${PIPESTATUS[0]}"` because PIPESTATUS[0] is the block's exit, not tee's. If the origin delivery still does not surface in-session, hunt the report in the cron fire's captured stdout before re-running anything: list the cron jobs and grep their recorded stdout, and grep the spillover cache for the report's distinctive literals — one lost report was recovered from a SIBLING session's spillover transcript that had echoed the job's context, and one was never delivered anywhere (origin-delivery notes can land in the chat's stored history without re-entering the live session; the $HOME out-file written by the payload itself is then the only reliable read-back). When even that read-back is out of the session's reach (the executor's $HOME is the host hermes home, invisible to the sandbox), hand the user ONE line — `sudo cat /home/hermes/<name>-out.txt` — which reads the payload's own out-file deterministically; after two lost origin deliveries in a row, prefer this over re-firing.

(j) Re-run `date` immediately before creating any one-shot schedule after an idle gap — the wall clock advances while the user is away, and a fire time derived from a stale mental 'now' reads as a scheduler misparse when it is correct (an 'in 1m' job created after an 8-hour idle gap landed the next morning, and the replacement attempt then failed 'more than 120s in the past' on a timestamp computed from the stale clock). The absolute ISO one-shot form plus a fresh `date` is the reliable path.

(k) The scheduler kills long fires at roughly a ten-minute ceiling, and the kill reports as `last_status: error, exit 1` with EMPTY stdout — the wrapper redirects everything into the out-file and the final `cat` only runs when the block completes, so a killed fire produces no report at all (distinct from the benign empty-out-file flush quirk above, where last_status reads ok). Size host-side bulk work (multi-thousand-file unpacks, mass chowns, big copies) to finish inside the window, or make it idempotent-resumable: skip outputs that already exist, write via tmp+rename so a kill leaves no half-written files, and print skip counts so the final fire's report proves what earlier fires completed. A killed fire needs no diagnosis — the partial out-file is host-side and unreadable from the sandbox; create a NEW one-shot job (an auto-disabled one-shot cannot re-fire) and let it resume where it stopped. Disambiguation: the same exit-1-with-empty-stdout symptom is ALSO (g5)'s block-exit failure — have the user tail the $HOME out-file before assuming a kill: a bare FATAL line with no REPORT markers means the block exited by its own guard, not that the scheduler killed it, and the fix is the payload, not another fire.

(l) Keep a staged payload one file per language: real logic (python) lives in its own spool file the wrapper calls by path (`python3 /srv/mcp_files/send/<name>.py`), never as a heredoc nested inside the wrapper — nested heredocs are where staging breaks (quote runs double and the build dies before anything stages), and a separate logic file is independently re-installable when only the logic changes.

(m) In a session that moves between a design repo and its implementation repo, re-derive the target repo and branch from the CURRENT task before every GitHub write (create_branch, push_files, create_or_update_file) — the previous phase's repo stays mentally loaded and the call fires at the stale target, shipping content that already exists there onto a stray branch; the tell you are operating on stale state is that the artifact you are about to write already exists on the target. Delete a stray branch the moment the misfire is spotted — leaving it pollutes the branch list. And never push WIP/marker files onto a shared branch as staging: sandbox-side staging (/tmp, /root) or the spool are where payload inputs live; a marker file on a branch costs a delete commit and a history blemish.
(n) The MCP `get_file_contents` result text opens with a `successfully downloaded text file (SHA: <blob>)` header line before the bytes: strip the first line before any sha256/blob/diff comparison (a hash computed over the raw result text poisons byte-equality checks), and note the header line itself reports the true blob sha — the cheapest blob verification is reading that line, no recompute needed.
2. Write the publish payload to the workspace bind's `staged-payload.sh`: update the host clone (`$HOME/git/<repo>` via the gh-token-helper credential; clone if absent), `git fetch origin main`, `git checkout -f -B design/<name> origin/main`, copy the doc into its status folder (PROPOSED/ for a new doc), insert the DESIGN-INDEX row in the payload against the clone's CURRENT copy (anchor after a stable existing row; skip when the row marker already exists) — never stage an index snapshot from the local tree, because the local copy lags main and a staged snapshot silently reverts every row merged since it was taken; the stale-base shape bites in the SIBLING direction too — a parallel session's row PR built from a pre-your-merge index silently deletes your row when it lands (a row verified landed one day was absent from main the next): enforce the index-never-shrinks rule by checking — before any index-touching PR, fetch main's index and grep for every row your session owns (a missing row re-lands in the same PR), and after a row lands, re-verify main still carries it before relying on it. Then commit with a conventional subject, push, and echo the branch head plus a DONE sentinel. Tee all output to an out-file beside the payload. Idempotent: no-op when the marker exists and nothing differs.
3. Fire a one-shot no-agent cron job (`script: run-staged.sh`, short duration schedule) — the scheduler execs the payload host-side as the hermes user and tees stdout back to the workspace bind. Overwrite `staged-payload.sh` immediately before each fire: the relay runs a FIXED shared file, so a stale payload from an earlier task is what the next fire executes.
4. Read the out-file for the DONE sentinel and branch head; verify the branch via the repo tools (list commits), then open the PR via the MCP create tool and verify the pushed bytes by comparing the PR diff's added lines against the local file. The out-file and the cron output path are HOST-side: a sandboxed session reading them gets ENOENT, and the completion block delivered into the session TRUNCATES long payload stdout — a DONE sentinel or branch head past the cut reads as a failed fire when the push landed. Confirm the end-state through the repo tools instead (list_branches for the branch's head sha, get_commit for the file stats); the delivered block proves only that the fire ran. Even a bind-visible out-file can stay EMPTY after a successful fire — the payload's `exec > >(tee ...)` process substitution does not always flush before the scheduler records the run — so an empty out-file is not a failed fire; the repo tools are the verification of record, always. Pre-create the out-file world-writable before the fire: bind-staged inputs land root-owned while the scheduler execs the payload as the hermes user, and a tee whose target file or parent directory that user cannot write kills the fire before the payload starts.
5. Gate the merge POSITIVELY before attempting it. Per-check CI results are READABLE now: `pull_request_read` method `get_check_runs` returns name/status/conclusion/html_url for every check on the PR head (the old 403 on the fine-grained PAT is gone — verified live; a red `tests (<pkg>)` leg on a diff that cannot touch that package is a real failure in the merge ref, reproduce it on the base commit before debugging the diff). Keep the old fallbacks for when the surface degrades again: the Actions runs endpoint (`/repos/<repo>/actions/runs?head_sha=<head>`) plus the PR read's `mergeable_state: clean`, which is GitHub's own required-checks verdict; attempt the squash-merge only when both confirm, and treat a refused merge as a no-op to re-fire after re-checking, never a reason to force. When the actions/checks surface itself is 403-masked for the token (the same fine-grained-PAT limitation on the runs endpoint), do not deadlock waiting for 'both': `mergeable_state: clean` is already GitHub's positive verdict that the required checks concluded — merge on it with expectedHeadSha pinned, and treat a refused merge as the signal to re-check. Read the repo's own AGENTS.md for the merge policy before deciding who merges: it may authorize agent squash-merge once checks are green (the parent's general ask-to-merge rule yields to the repo's standing instruction), which is what makes the parent-side merge legitimate at all. When AGENTS.md is absent, the DESIGN-INDEX header's update rule carries the same policy. After the merge, verify main carries the commit (list commits) and bring the local working copies (doc, DESIGN-INDEX row) in sync with what landed. Concretely that sync is one more tiny marker-gated relay payload: `git -C $HOME/git/<repo> fetch origin main; git show origin/main:DESIGN-INDEX.md > <local tree>/DESIGN-INDEX.md` (the local tree is host-reachable by path parity), then re-verify the local final copy's git blob sha against the pushed blob and grep the index for the new row and for leftover old-form cites — attribute any remaining old-form mention (Attributes cell = still stale, History cell = historical record, keep) rather than re-firing a repoint that would rewrite history. **When the slot is hot, the post-merge tree refresh skips the relay entirely — two sandbox-side operations, both hash-verified:** (1) the merged -final doc comes from the MCP get_file_contents spillover copy of the merged path (strip the `successfully downloaded text file (SHA: ...)` header line, verify the git blob sha `sha1("blob <len>\x00" + bytes)` against the pushed blob AND sha256 against the local pin, then write the bytes into the tree); (2) the index refresh is CONSTRUCTED, not copied: insert the row file (the exact bytes staged for the publish) after the tree index's last `|` line, then git-blob-hash the built file — when the tree copy was already main-minus-the-row, the built blob equals main's fetched blob and the write is proven byte-exact without transcribing anything; a mismatch means the tree lags on OTHER rows (other sessions' merges) — insert the row anyway (it is this fold's duty) and leave the foreign rows to their owners' syncs.

Post-consensus, close the loop with one bookkeeping rev (fold the final verify round into the verdict history, refresh the status line); it rides its own tiny PR in the same style — except when the closing verify round returned zero findings on unchanged bytes, in which case the bookkeeping rev can fold into the publish PR itself (one PR carries final + index row + registry repoints) and the separate tiny PR is only for bookkeeping that lands after a doc already merged.

The repo ships finals only: working docs (the `-design.md` twins), `review-comments-*.md` files, and evidence dirs stay in the local synced tree. The repo's directory layout differs from the local flat tree (files sit under PROPOSED/ etc.), so list the target directory before the first push and map every local path to its repo path — a push that guesses the path creates a stray root-level file instead of updating the registered doc.

## Adoption transition PR (PROPOSED to ADOPTED)

the operator's adoption go turns a published PROPOSED doc into a transition PR: a Rev+1 whose content changes are the header status line (the flip plus the go recorded), a Revisions-block entry placed ABOVE the retained prior-Rev lines, and the DESIGN-INDEX row update — plus the folder move PROPOSED/ to ADOPTED/ (a real `git mv` inside the host-clone worktree; the MCP tools have no move primitive). Push, CI gate, and self-merge flow are identical to the publish flow above. Mechanics that bit once each: apply the doc edits in one python pass with assert-count-1 fragment replacements (header fragments wrap across lines, which a single-line grep misses), compute the new git blob from the EDITED bytes BEFORE building the index row so the row's History cell carries the transition blob instead of a placeholder, and rebuild the index row by splitting its cells and rewriting only the touched ones (Status plus folder path, Rev cell, the go into the Go cell, Next action into the rollout's next steps, transition blob plus flip line appended to History) so the Subject cell survives byte-identical. Gate the payload on target state before staging: the local twin's sha256 must equal merged main's blob AND the ADOPTED path must not exist on main — a parallel session may have already run the same transition (staged payloads are visible to every session on the box), and the state check turns that duplicate into a clean abort instead of a second PR; the same payload gates the base state before acting: the PROPOSED path must still exist on main with its expected blob sha (the move's source and the byte base), and no open PR may already reference the payload's branch — either hit means the transition already ran under another hand. Post-merge: verify the ADOPTED-path blob on main, then sync BOTH local twins (the `.md` and the `-final`) and the index from merged main. Timing: the flip normally waits for implementation evidence (see references/adoption-kickoff.md); flipping on the go itself is the accepted second shape when the design's rollout is fully specified with pre-authorized merges — state the chosen timing in the status reply so the registry intent is explicit. An adoption go that also changes a decision ("adopt, but make it fully autonomous") is not status-only: fold the decision as an M-block with a Rev bump, carry it in the same transition PR as the folder move and the index row, and record both the decision and the flip in the row's Rev and History cells.

## Withdrawal transition PR (PROPOSED to WITHDRAWN)

the operator's withdrawal call runs the same branch → PR → squash-merge shape, but the mechanics differ from adoption:

- The doc FILE moves (git mv in a clone worktree) PROPOSED/ → WITHDRAWN/ with NO content edit: the withdrawn doc keeps its final header as the fidelity record, the index row is the registry of record, and WITHDRAWN docs are unslop-exempt (no retroactive pass) and stay unedited afterwards. A git rename detected at 100 percent proves the move byte-exact.
- The index row flips in the same PR. Compose the edit as one python split('|') pass with a pipe-count assert (10 pipes, 9 columns) against origin/main's copy — never hand-edit a huge row line: Doc cell's folder path → WITHDRAWN, Status → WITHDRAWN, Attributes cell → the withdrawal pointer ('SUPERSEDED → <successor stem>' plus the one-clause reason), Next action → '— (withdrawn <date>: the operator's call; one clause)', History cell → append '→ WITHDRAWN <date> (<reason>; successor <stem>)', Withdrawn→ cell → 'successor: <stem>'. Keep every other cell byte-identical, and keep added cell text dash-free (the '—' empty-cell markers are table convention; prose uses semicolons).
- Pre-flight before branching: check open PRs (a sibling transition in flight must not collide), take the row's exact bytes from origin/main (the local tree lags), and git grep origin/main for sibling cites of the doc — cites INTO a withdrawn doc (another doc's References rows citing its Rev) stay as historical records; only a sibling whose LIVE claim depended on the withdrawn doc's pending rollout gets a repoint, and that edit belongs to the successor doc's loop, not the withdrawal PR.
- The successor pointer may name a successor doc that does not exist yet when both land in the same session (the registry records the intent); if the successor publishes under a different stem, fix the pointer in the successor's publish PR.
- Post-merge sync: the clone to merged main, and the synced FLAT tree's index row (the tree has no status folders — only the repo carries them); verify the tree row byte-equals main's row. The tree's working twin (the -design.md) stays put.

## Evidence integrity during the loop

- Correcting a recorded evidence file is parent-owned and provenance-marked: patch the corrected values plus an inline note saying what was wrong and which round recomputed it; never silently rewrite. The doc cites the corrected values, so the next round verifies doc against evidence instead of re-deriving the correction.
- **Capture-display values are display-qualified, never arithmetic operands.** Tool human output grades and rounds on its own scale (du -h ceils a 14,922,380-KiB directory to "15G"; free -m grades in MiB even when labeled MB; df -h rounds within a band), so a figure quoted from display into GiB arithmetic can shift a conclusion by a gigabyte. State the display value WITH its qualification ("df's display; byte-exact in the phase artifact"), derive arithmetic from a byte-exact instrument (`du -sb`, `df -B1`, `lsblk -b`) captured in the artifact list, and when a correction converts display to byte-exact, re-derive every dependent number in the same pass — a size figure locked from display re-scaled a headroom verdict by 2x before the byte-exact chain was imposed.
- **Record both readings when same-day fetches of one page disagree** — providers serve page variants and revise pages between fetches, so a re-fetch hours after the research capture can read a different plan-feature value or column name than the morning transcription. Append a provenance-marked corrections entry to the capture (both readings, fetch times, and the one-line doc-impact check), never overwrite the original transcription, and touch the doc only if a cell actually carries the disputed value — when none does, the doc stays untouched and the entry is the whole fix.
- When a design depends on a vendored third-party library's semantics, capture that exact version's official upstream artifact (dist file, manifest) into the evidence dir at research time with a status note (URL, sha256, byte size). Reviewer rounds then verify semantics against the durable copy instead of re-fetching, and the vendored-versus-upstream identity gets one hash comparison point.
- **Source-fetch captures carry a provenance header and a blob sha, and blob-sha-anchored excerpts are legitimate captures** — per file: source URL, pinned ref/tag, the fetched blob sha (the fetch header reports it), capture date, and capture scope (full file vs named excerpts). A later round re-fetches at the sha and verifies the excerpt byte-for-byte instead of trusting the transcription; excerpts win over full-file dumps when the source is large and the doc leans on named functions, and the header names which functions the capture carries.

## Fold-loop mechanics (decision folds reviewed in fix-verify rounds)

A decision fold that runs fix-verify rounds (schema verdict {verdict, findings[]}) instead of comments files has its own convergence pattern, learned over a SIX-round loop:

- **The loop is a ratchet, not a defect chase: each round's findings are one of three kinds, and the pattern is visible in the tallies (17 → 14 → 5 → 10 → 15 → 11 → …).** (a) Fix-round residue — every fix touches sibling sites the fixer did not know about (a rename sweeping the doc but not the evidence staging/ copies, an INDEX-ROW cell the doc sweep missed, and a CAPTURE FILE'S own section headers and glosses, which carry the same corrected figures the doc and manifest carry); grep for each fixed value across ALL artifacts in one pass — doc, README manifest rows, and every capture file, not just the surfaces the fix round edited. (b) Live-state contradiction — a review round re-probes the box and finds the doc recording 'the target does not exist yet' while the sibling went live mid-loop; when a fold rides a live rollout, the reviewer WILL surface every doc sentence that states the pre-rollout state, so sweep the dependency lines, honest notes, and gate conditions for past-tense claims before dispatching. (c) Kit-vs-doc drift — the doc's embedded fence is a CLAIM about a kit file; when kit fixes ride PRs that may not have merged, the doc, the evidence staging copies, and kit main can hold three different forms of one line. Resolve by building the kit side FIRST (one consolidated kit PR), then verifying doc↔staging↔kit-main blob-equality per embedded file before the next dispatch.
- **The strand trap is the kit-side equivalent of the dead-branch problem**: post-merge commits pushed to a merged PR's branch never reach main, and doc claims citing them read as landed. One consolidated kit PR (branch FROM the strand tip so unmerged commits ride in) beats three separate PRs; close superseded kit PRs with a pointer comment.
- **Keep a running fix ledger in the dispatch context** — each round's dispatch lists every prior finding id + its fix, and the reviewer verifies each clause-by-clause ('a multi-part fix that lands only its headline reads as landed to the next reviewer'). The ledger grows every round; the reviewer's cross-artifact verification surface (doc + staging + kit main + manifest + PRs) grows with it, so budget for later rounds running longer, not shorter.
- **A fix that REVERSES a recorded claim needs its evidence story resolved in the SAME round, not deferred**: when round N+1 flips 'caps pending' to 'caps measured', every site (§ fences, staging, honest notes, §11 item, the kit PR content) plus an evidence capture of the underlying reading must move in the same pass — splitting the evidence capture to a later round guarantees the next reviewer re-flags the uncited claim. Evidence capture is always live: new capture (P<n+1>) + manifest row + README probe-list bullet + the header's evidence-range line, all in one round; the manifest's own meta-rows (STAGING-RESYNC and friends) join the exception list.
- **The DESIGN-INDEX row's summary cell is authoritative on conflict (§0.3 rule)** and every fold sweeps it separately — the doc sweep does not reach it, and a rename the doc carries can survive in the row's Subject cell.
- **Em-dash sweep runs per fix round, not once**: each fix round's OWN added lines re-introduce em dashes the base text never carried (count base-vs-doc dash lines programmatically each round; the Rev-line's leading date dash is the one house exception). A fold that rewrites the header Rev line keeps exactly ONE dash in it (the leading separator after the rev status/date) — restructure any additional dash in the retained prior-rev clause back into prose instead of carrying a second dash through the fold.
- A verdict-history line records EVERY fold round's tally with 'fixes incorporated in Rev N' and the loop's open/closed state ('R<n+1> pending' / 'CONSENSUS reached') — the audit trail is the loop's own output; a 'pending' entry that is actually landed is a finding.
- A post-adoption evidence fold (probes landed, findings folded into the working doc) bumps the working doc's Rev locally round by round while the repo copy and the DESIGN-INDEX row stay at the published rev — the row and folder updates ride the NEXT publish per the declared convention, never per fold; publish once the fold loop closes, not between rounds.

## Reading an existing cron job's full prompt (the config store never greps clean)

A Hermes cron job's full prompt lives in state.db's `messages` table, inside the `tool_calls` JSON of the session that created it — the live cron config never matches a plaintext grep for the job id anywhere under ~/.hermes, so do not hunt a config file. Find it by the job NAME (a create call precedes its own id, so an id-keyed search finds only post-creation rows): query `messages` for `tool_calls like '%<job-name>%'`, then unwrap the stored shape — tool calls are stored as `[{"function": {"name": "tool_call", "arguments": "<json string>"}}]` whose inner payload is `{"calls": [{"name": ..., "arguments": {OBJECT}}]}`; the inner `arguments` is an OBJECT, not a string, and the create/update call's `prompt` field carries the full text. Sweep the same table for update calls by the job id (`tool_name='tool_call' and tool_calls like '%<job-id>%'`): a deliver-only update carries the id but no prompt, so the LATEST prompt-carrying call is the current prompt — confirm against the live `list` output's prompt_preview opening before composing any edit. Read it host-side through the relay (the sandbox cannot open state.db), and when the stored shape resists scripted parsing, prefer one operator-run `sudo sqlite3 substr()` splice of the raw bytes over another scripted fire — the raw dump settles it in one pass.
