# Adoption kickoff (when the operator's go arrives)

Moved out of SKILL.md for size. Drive-era wording kept where it appears — the repo (<your-org>/design-docs) is canonical since the git migration, so read 'Drive-registered final' as 'the repo's merged final'.

The go turns a FINAL doc into an implementation run. The kickoff is one clarify batch plus one dispatch round — not a new research loop, and not yet the registry transition (that follows the registry rule once implementation evidence exists, not on the go alone).

0. **Check the doc's CURRENT state before any kickoff step — the go may already be executed.** Parallel Hermes sessions work the same docs and box: a 'this should now be implemented/adopted' instruction can arrive AFTER another thread ran the adoption card, folded the decisions (M-blocks), bumped the rev to ADOPTED and applied the design live (this happened Nov 3-4 2026 on continuwuity-cpu-budget: this protocol's session fired a clarify card re-asking §8 decisions another thread had already settled, and drafted a stale registry row). Reconcile read-only FIRST, before the clarify batch: the local working doc's Rev/status lines, the Drive PROPOSED vs ADOPTED folders, the DESIGN-INDEX row, and the live box (unit properties, config). If the state shows adopted/implemented, the task becomes verification and confirmation (re-run the doc's post-apply gates read-only and report), not a new kickoff; discard locally-drafted stale edits instead of uploading them.

1. **Reconcile the doc's copies before implementing.** The local working copy and the Drive-registered final can drift — a later style-only pass bumps the rev on Drive without touching the local snapshot. Download the PROPOSED copy and diff: a style-only delta means either copy implements the same spec; a mechanics delta means the Drive copy is authoritative — re-read its changed sections before dispatching anything.

2. **Batch the whole kickoff into ONE clarify call, before the user's announced away-window starts.** Include the doc's open decisions (recommended-first) plus the two operational questions every adoption hinges on: merge pre-authorization (standing default is ask-to-merge; when the operator is about to go afk, ask for squash-merge pre-authorized on clean review + green CI) and the window for each step the agent cannot execute (deploys under another user's credentials, interactive re-auths). Name the gate where the unattended run stops. When the card times out, do NOT re-fire it: restate the open questions in chat as numbered one-liners the user can answer by number whenever he returns, and when a bare number arrives, decode it with a ONE-question clarify that names which pending question each number maps to — a bare number maps to whichever question the user was last reading, and the chat-list position rarely matches the card's question order.

2a. **An open decision the card could not carry implements its recommended default when its consuming phase arrives.** First try to FIT them instead of deferring: bundle the mechanical decisions (every row whose recommendation is already the doc's default and carries no privacy or custody stake) into ONE accept-or-veto question — 'accept all as recommended' as the recommended option, free-text override row for per-row vetoes — and spend the individual questions only on the stakes-bearing rows (encryption at rest, key custody, attended windows, merge authority); ten open decisions have settled in one five-question card this way, leaving zero deferred defaults. What still does not fit defers: the clarify tool takes at most five questions; when the kickoff's open decisions exceed it, leave the low-stakes ones open in the doc's decisions section with the default stated and the CONSUMING PHASE NAMED on each row ('phase N consumes this'). When that phase's PR is drafted, implement the default and flag the veto affordance in every artifact the reviewer and the user read: the PR body ('implements the standing default for OD-x; dropping it later is a one-line change'), the spec's risks, and the implementer's notes. Never default silently (the user cannot veto what he cannot see) and never block the phase on a re-fired card (the timeout rule already forbade re-firing).

3. **Stage the mutable artifacts while the clarify waits.** Patch the kit/source copies and build the gated apply script (pre-restart unit-property gate, auto-restore on gate or start failure) during the card's wait, so the attended execution window stays short once his answers land — the card blocks on his reply, the staging does not. Stage where the HOST can reach them: a dispatch subagent's container home is invisible to the user's shell — a staged kit path the user's `install` cannot stat costs the whole block a re-run. The canonical on-box copy of a pushed repo comes from `git clone` in the attended command list, never from the agent's staging tree. The kickoff can span turns: an answer that requests an explanation first ("explain X to me") is a PENDING decision, not a skip — give the explanation and keep that question open; the answered questions execute on the locked set, and a later free-text reply ("apply the X fix") closes the pending one. When the user asks for EVIDENCE before deciding ("what's the usual setup in the docs", "give me the link"), fetch the primary source live (the docs' own examples, a tracker page) and answer with it — an evidence-backed recommendation converts the decision in one round instead of three.

4. **Trace every override's blast radius before dispatching.** An override that deletes a fallback path also deletes the safety property that fallback provided (a legacy-path retention gate is what keeps an unverified first write from running unattended) — name the lost property explicitly, and add the compensating verification step (stricter backup ordering, a mandatory full-path rehearsal the rollout cannot skip) rather than letting the guard vanish silently. A decision that RESOLVES a sibling design's open decision must be folded in the sibling doc within the same PR — each doc's decision record is authoritative for its own state, and citing a resolution the sibling's record does not carry reads as a contradiction finding, not a fold.

5. **Dispatch implementation subagents in parallel, one per repo, self-contained:** the doc path, the exact § references per deliverable, the amendment list keyed to the clarify answers, the do-not boundaries (no merges, no direct main pushes, no live calls against state the design's own gates protect, no edits to gitignored local config the parent owns, exclude known-dirty tracked artifacts from the PR), the proven push method (verify the repo's directory layout first — a docs repo whose files live under status folders rejects the local tree's flat filenames: a push without the status-folder prefix lands the file at repo ROOT, duplicating it and stranding the canonical copy stale until a repair PR; and when a post-push blob check mismatches, re-fetch the pushed file and diff it against the local source — the diff isolates the exact drift, typically a missing trailing newline or a one-word slip — then re-push the corrected file instead of re-deriving the whole transcription), and an output_schema (pr_url + test summary + deviations). Before dispatching, read the repo's workflow triggers — a repo whose workflows lack a `pull_request` trigger has NO CI gate on PRs, so state the review-based gate honestly in the PR body and the merge ask instead of waiting for checks that never run — and recon the privilege/auth reality up front (`sudo -n true`, `git push --dry-run`): every step the agent cannot execute goes on the user's attended command list prepared BEFORE the window, not discovered at the gate.

**Re-derive 'no API for X' claims against the USER's own data before accepting them.** A design decision recorded as 'no endpoint exists' can be contradicted by data the USER already fetched out-of-band (a GDPR account export, a manual download): before treating an unreachable-data scope as settled, ask whether the user's own exports already hold the data, and when they upload one, census it directly (unzip listing, file counts, date ranges, per-record field keys) instead of citing the design's claim. Two mapping traps from a Garmin account export: the archive's per-activity FIT filenames are WATCH-UPLOAD ids in a different id space from API activity ids (zero filename overlap — link export files to API activities via the FIT's own session/monitoring start_time, never by filename match), and the export's original FITs can run ~2× the API-delivered ZIP for the same activity — the size gap is the stripping signal that converts a risk row into a measured fact.

**Verify the child's PR against the DEPLOY SURFACE before the deploy gate, not just code+tests.** Walk the repo's deploy collateral (the quadlet's Volume lines, the env example's knobs, update.sh's service rows, the cron install contracts) against the design's runtime sections (store dirs, mounts, env names): a code-complete, test-green implementation can miss a bind mount that makes the whole feature inert on the box — the design §3/§6 runtime reach is the checklist, and the quadlet's header comments can still carry stale pre-feature claims ('no data volume') that hide the gap. Also verify every file the child's final report FLAGS via a mutation verifier against the PUSHED branch (get_file_contents + parse) before merging: a refused sandbox write does not mean the pushed bytes are wrong, and the child's fresh-clone claim is the child's own claim, not the verification.

**On-box prerequisites are part of the attended block, not an afterthought discovered by a failed start.** A bind-mounted source directory the quadlet mounts must EXIST before the recreate (podman's statfs on a missing bind source fails the unit start outright) — fold the `install -d -o mcp -g mcp -m 0700 <store-dir>` line into the attended block ahead of the recreate, ahead of any knob. And plan the failure path of the first start: if the recreate fails, the unit is left dead and the server is down — include the instant-recovery line (flip the behavior-changing knob to its off value with sed, re-run update.sh) in the SAME reply as the diagnosis request, so the box is never left down while a root cause is hunted. Diagnose a failed start without journals (this box's users cannot read their own unit journals): `podman ps -a` for a leftover container, then a foreground `podman run` with the quadlet's exact `--env-file`/`-p`/`-v` flags — the crash line lands on the terminal where journals stay silent.

**After the box deploy, the gateway may not re-register the server's MCP tools in the running session — re-search the deferred catalog before assuming the server is down.** A tool_search for the server's tools after a recreate found them registered and fully callable even when an earlier same-session search came up empty; the smoke ladder can then run through the normal MCP tool calls (bearer validity in api_status, live reads, the new api_status block, activity-file fetches) with zero relay involvement. Trust the tool_search re-check over the stale session snapshot.

6. **Run the read-only pre-flight the design marks agent-safe while children work** (handshake/tool-inventory probes against the live target), then end the unattended window AT the first the operator gate — ping with his exact command list, not a status paragraph.

**Runbook designs (decommission/migration docs with no kit PRs) have an empty dispatch round: the implementation IS the operator run.** Run the doc's parent-session phase-0 rows first (the rows it marks 'parent session': cron-store reads, gateway sweeps), then end the window at the operator gate with the doc's own verification ladder as ONE read-only fence; mutating steps wait for the ladder's readings because several consume them (the owning user's elevation, ingress line numbers, the DNS record's identity). Compose operator command blocks from the RENDERED command semantics, never the raw table bytes (an MD056 pipe escape inside a table code span is correct markdown but wrong ERE when run raw; see publishing-and-target-identity.md). Keep a run record in the evidence dir that fills per row, and run any relay-dependent step (a cron-store prompt read backing an in-doc cron edit) through the relay instead of spending an operator round on it.

**Offer and honor the step-by-step walk.** the operator may prefer one step per round over the batched operator block ("lets go step-by-step") — grant it without re-arguing the batching: in that mode each step waits only for the phase-0 rows it consumes, every landing is recorded in the run record the moment its paste arrives, and the dashboard/client rows land at their consuming steps (a DNS record's identity is read in the same dashboard visit that deletes it). Stamp each landing from a PROVABLE artifact (a snapshot file's mtime, an edge Date header, a fresh `date`) — an interactive walk can cross an overnight gap silently, and one composed 'earlier tonight' stamp in the run record falsifies the whole timeline; correct any stale stamp in place with an inline correction note naming what exposed it.

**Refresh the registry row at the run's close.** A gated run's execution makes the DESIGN-INDEX row's Next-action cell stale the moment the run lands ("awaiting go" reads on after the go was spent) — a row-refresh PR (Go evidence, Next action, History append) closes it. Verify the push path BEFORE composing the commit (`gh auth status` in the session's shell; the MCP token's scopes may not cover branch creation) — a mid-session sandbox recreation can strip image-layer tooling while /root and the bind mounts persist; if the path is dead, commit locally, declare the staged deferral in the run record, and let the refresh ride the next index-touching PR rather than leaving the staleness unrecorded.

**Box-probe pattern for cloud/SSH targets the sandbox cannot reach (phase-0 class probes).** Probes of a remote box ride the no-agent cron relay with the credential staged into the shared design tree — the full recipe (executor context map, staged-key custody with a shred-immediately-after rule, capture naming against the fixed-redirect collision, host-key accept-new + fingerprint audit) lives in `references/relay-remote-probes.md`; read it before firing any probe fire. Kickoff-specific notes: the executor sees only the shared design tree, so anything under the user's own 700-mode home is captured by the operator's shell into the evidence mount (one `{ cat ...; } > <shared-path>` command); the probe class the runbook pre-declares is consent-covered and a same-class follow-up drill fires without re-asking, while a change of target or privilege level is disclosed in the dispatch.

**When a long unattended plumbing sequence loses the user, stop and re-ground in plain words.** The tell is the user asking "explain what you are actually trying to do" after several infra round-trips (staged files, relay fires, approval gates): he has lost the thread of WHERE in the plan the work sits, and continuing the plumbing without re-grounding compounds it. Reply with a top-down explanation in simple words: the goal, where the work currently sits in the plan, why the detour exists (what the sandbox cannot do that the relay can), what the last few commands from him accomplished, and the one next action — no tool names, no incident chronology. Then continue on his go. This costs one turn and prevents the silent-drag failure where the user approves steps he no longer understands.

Compose the attended command list from the repo's OWN deploy contract, not from invention: the update.sh header carries the staging + run-as-mcp recipe (fresh clone at the merged sha, a /tmp staging copy because mcp cannot traverse hermes-owned paths, `sudo -u mcp bash update.sh` — never root-invoked, the script derives the user bus from its own uid), and the shipped scripts' Deploy headers carry the install commands and cron lines verbatim (install modes 0700, cron files 0644). Order the block env-knobs-first (values bare), then script/cron installs, then the recreate, and keep it ONE fenced block ending at the recreate. After he runs it, the parent verifies via the MCP probes (bearer 200/401, the new api_status block, backfill progress) and states the expected-transient notes up front — a layer-2 checker run before the first backup has fired reads unhealthy by design and self-corrects on its next run.
