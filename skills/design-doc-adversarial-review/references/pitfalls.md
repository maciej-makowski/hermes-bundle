# Pitfalls archive (each one has bitten)

Moved verbatim from SKILL.md so the main file stays an always-on skeleton; the thematic index lives in SKILL.md's Pitfalls section. Read the matching section before the loop phase that touches it.

## Doc and patch integrity

- **After every rewrite, grep the doc for the names of dropped mechanisms AND for fields/params that only the dropped mechanism sourced** — a fix that rewrites one section but leaves the old mechanism referenced in another section re-teaches the deleted claim (stale cross-references are the #1 iteration-2+ finding type), and a mechanism swap silently orphans the data it used to supply (a revision-source swap strands the `link_id` envelope field and the old size pre-flight sentence). Grep for both before re-dispatching. Grep also for the QUANTITY phrasing bound to the dropped item ('two keys', 'both lines', a 'weight and quota' pairing): sections that name the dropped mechanism only by count or by a pairing phrase escape a name-only grep and re-teach it anyway. The compression variant bites in splits: a step summarized to a phrase ('ownership fix') can leave the mechanism's implementable form in NO document while every section reads complete — grep the children for every parent mechanism NAME and restore the named form wherever a step depends on it.
- **When an operative mechanism behind an ADOPTED sibling design is retired (a CLI offboarded, a server decommissioned, a route replaced), sweep that sibling's coverage matrices, workarounds, and 'until X ships' clauses for rows still routing through the dead mechanism** — the sibling was never rewritten, so the dropped-mechanism grep never fires, yet its matrix row now teaches a route that no longer exists. The new doc that replaces the mechanism records the supersession in its own decision record and relationship paragraph, and the sibling row's one-line errata fold is flagged to the doc's owner rather than silently left; cite the sibling's row by section title, not row position (matrices get renumbered).
- **Diff every sibling-mirrored command block line-by-line against the sibling's original before the doc ships — a mirrored block reads complete while silently dropping the sibling's helper lines (the state-dir creation that precedes a log capture, the ownership flags on a scratch dir, an env export, a umask), and a content-level read cannot catch the gap because every line it checks is correct; only the side-by-side diff sees the missing one.** Make the diff a standing writer output requirement, not a reviewer hope — the omissions surface as feasibility MAJORs in the first review round otherwise.
- **Patch findings from the comment file, not from memory of what you wrote** — the reviewer verifies against source, and 'what I meant' differs from 'what landed on disk'. When the fixes span several batches across turns, walk the comments file's numbered findings against your applied-fix list before every re-dispatch — a finding skipped between batches (typically a NIT lost from a partial mental list) costs a full review round when the next reviewer re-raises it.
- **Patch each round's findings from the comments file on disk, never from the delegation's completion summary** — a background round's summary condenses multi-clause findings to their headline, so a fix list built from the summary lands only headlines and the next round re-flags every orphaned clause; the burned round is identical to skipping the finding. Read the comments file in full before building the fix list, and take each finding's full clause list from the file, not from the dispatch text that requested the review.
- **When the design ships concrete config artifacts, write them to a staging dir BEFORE writing the doc and embed them verbatim** — doc fences and files then carry identical bytes, the reviewer diffs fences against the files byte-exactly as a standing check, and the PR later pushes the same files with no transcription step. When the artifacts change mid-loop, patch the STAGED file first and regenerate the doc fence FROM the staged bytes programmatically (locate the fence span by its unique first inner line through the closing fence, replace it with the language tag, the staged content, and the closing fence) — applying the same patch strings to file and fence separately gives transcription two chances to drift, regenerate-from-file gives it none; a doc block that drifted from its file costs a round. When the write guard refuses the staged file's overwrite (its sticky pagination flag fires even after a fresh full read), write the new content to a `<name>.new` sibling and move it over the target with a plain terminal `mv` — write_file to a path that does not exist yet never trips the guard. When checking fences against files, locate each fence by its inner content's distinctive first line, not by opener type or order — two fences can share the same opener (an env template and a quadlet unit both open with ```ini), and an order-based check diffs the wrong pair and reports a false DIFFERS. Doc = spec, staging files = delivery.
- **When a runbook implements one branch of an open decision as its default, define the branch taxonomy once in the preamble as a named term and qualify EVERY branch-conditional clause with it** — certificate counts, record adds, expiry checks, renewal claims, and stack-mechanic umbrellas each drift back to their unqualified default within two or three fix rounds otherwise: a certificate gets issued for a branch that never publishes, a count bucket omits a publishing sub-branch, a re-derivation umbrella scopes to steps while the same claims live in other sections the runbook's amendments reach. Scope every 're-derives' umbrella by document section (the runbook AND the sections it amends), not by step list alone.
- **Patch findings into the doc in the design's own voice** — finding meta-language ('finding: X', 'No such claim is made', 'the step the previous sketch missed') leaks from the patch context into spec text, where it reads as the review's voice instead of the design's and costs a voice/unslop round; state the fact plainly and cite the section carrying the evidence.
- **Verify every edit on disk before stating it as landed in dispatch context or status replies** — a rev-bump, changelog entry, or wording fix claimed but never applied makes the next reviewer burn a round proving the declared state is not on the page (it happened in the tier1 loop: a dispatch said 'the header moved to Rev 10' and the reviewer verified the claim false three ways). Grep the exact string in the doc before writing 'now says' / 'landed'; the fix-verification list must describe what IS on disk, not what you intended to apply. Recompute any derived figure you plan to quote in the dispatch (a call budget, a battery total, a window count) from the landed text before sending it — a wrong derived number in the fix-verification list propagates into the reviewer's own findings and costs a correction round.
- **Anchor every old_string in a batched similar-edit pass with a distinguishing neighbor line** — sibling lines that differ by one word (the same command block repeated in two steps, list items inside one move group) trip the patcher's uniqueness check or fuzzy-match a just-rewritten neighbor, and the failure surfaces only as silent batch misses; after each batch re-grep the file for every edited marker and re-apply the misses with added context instead of retrying blind. When a batch miss survives while its neighbors landed, check whether an earlier patch in the same batch consumed the anchor's text (two old_strings sharing a region) before building a new anchor — the failed patch's pre-image was real when queued. And when a post-batch verification count exceeds expectation, grep -n and attribute each hit before treating it as a defect: sibling mechanisms legitimately carry the same string (two hooks both setting the same key), and an 'expect N' number written from memory of only one instance is the error, not the file. In an environment that demonstrably runs scripts without approval prompts (ungated terminal/execute_code calls earlier in the same session), a single python replacement pass per file — exact-count old-string verification, marker greps after, misses reported — beats twenty sequential patch calls; keep the patch-tool route wherever scripts gate. Copy every old_string verbatim from the on-disk read, all lines of a multi-line comment block included: a paraphrased or shortened prefix silently misses (count 0) and the edit drops out of the batch unreported unless the miss list is read before moving on. Never build an anchor from the planned content of a batch that did not execute (consent-blocked or aborted): text the batch would have written is not on disk, so the anchor matches nothing — re-read the file and anchor on what is there.
- **A fuzzy-matched patch can GLUE the old line's retained tail onto the new text** — when the patcher reports a non-exact (context-aware) match, the replacement can absorb the old line's remainder into the new sentence (a bullet ending 'arrangement.: user matrix + ...'), and a grep for the intended new marker still passes, so the defect survives a marker-only check. After every non-exact patch, read the returned diff for fused or doubled fragments and repair them in place before the next edit anchors on that text — and a fuzzy match whose old_string begins at a table-row boundary can DOUBLE the row's leading pipe (`|| row |`), shifting every later column in render. The same doubling enters through transcription: read_file's line-numbered output renders a leading-pipe row as `5|| row |`, and a new_string copied from that display writes the doubled pipe into the file — copy patch strings from the line CONTENT, never from the numbered display line, and verify a table row starts with exactly one pipe after any non-exact or transcribed table-row patch. Grep the OLD string on disk immediately after any non-exact patch: a context-aware match can also report success while the target text is unchanged (no diff shown, edit silently skipped), or claim 'File already contains the target text' when its fuzzy layer equates the two strings because your old_string was transcribed from a MASKED display of a token-shaped span (the elided form fuzzy-equals the real bytes). When a patch no-ops this way twice, stop re-anchoring: dump the target line's codepoints from disk, build the old_string from the verified bytes, and if the patcher still fails, do one count-checked per-line replacement in a small scripted edit. And a defect that slips into a pushed commit costs a disclosed-defect round. When a consent gate then blocks the unattended fix, do not bypass it via another tool — disclose the defect in the durable artifact (PR body) and fix at the next attended window.
- **A write that reports '[Command timed out after 3s]' may still have landed — verify BOTH strings on disk before retrying.** The patch tool reports the timeout while the underlying write can complete a moment later (and the inverse exists too: a success report can precede a no-op), so the grep is the only truth: old string count 0 AND new string count 1. On a failure streak, retry ONE file per turn with a fresh grep between attempts — a batch of patch calls contends for the same short write budget — and treat a 'File already contains the target text' response as a landed edit with verification, not an error to fix. Do not route around a failing patcher with a whole-file write_file: its stale-view guard refuses after any patched edit even when a fresh full read intervenes, so fall back to a targeted patch anchored on a freshly-read line — and when a replacement swaps two lines for one, re-grep the returned diff for a dropped sentence tail before moving on (the lost clause only shows in the diff, not in any grep).
- **The write-file guard can refuse a full overwrite of a design-tree file even when a fresh full read just landed, and identical retries only burn the repeated-failure halt** — the refusal ("last read with offset/limit pagination (partial view)") fires on files whose read_file returned every line, and a same-batch read+write is one trigger (the guard evaluates the read state as of the batch, so read first and write next turn, or skip write_file for these files entirely). Working escape routes: doc_batch — the design plugin's own tool applies count-checked, atomic replaces to ANY file inside the design root, evidence files included, with no such guard; a targeted patch anchored on a freshly-read line; or a staged replacement script with per-edit count asserts persisted under the agent's persistent home (scratch dirs wipe between calls). Prefer the script outright when the edit payload is quote-dense: hand-built nested JSON carrying comma-heavy replacement text can mangle mid-flight and report a malformed call instead of an edit.
- **Let the reviewer attack your NEW claims hardest** — each re-dispatch should say 'verify the fixes landed AND hunt for issues the rewrite introduced'. Most post-v1 findings are self-inflicted rewrite residues, not original research errors. The attack reaches BEHAVIOR, not only prose: a fix that restructures a code sketch (re-keying a condition, moving a check) can drag sibling lines under a new branch and silently change mechanics a different section promises (a timeout assignment landing inside a presence-gated branch contradicts the empty-list test three sections away) — after any fix that touched a fenced code block, re-walk the doc's own test list against the rewritten block before re-dispatching, and add the walked consequence to the fix-verification list.
- **When a fix repairs a mechanism the reviewer had fixture-tested, name the fixture re-run as the next dispatch's acceptance gate** — 'the config now sets pass_filenames: false' is prose; only a re-run of the same end-to-end fixture (all hooks on a staged benign file, then a staged trigger file) proves the failure mode is gone, and the re-run transcript becomes that round's numbered probe.
- **Comments that ship inside repo files must be self-contained** — when the design's artifacts are committed files, in-repo comments may not cite the design doc, its evidence paths, or decision IDs (none of those ship with the file); inline what the comment needs or drop the pointer, and have the reviewer grep the artifact set for dead references each round. The rule reaches the design's STAGED kit artifacts in the evidence dir, since they become the repo files at adoption: sweep every staged file each round for design-doc names, probe ids, decision ids, and section numbers, and when the pass edits a comment, patch the staged file AND its embedded doc fence with identical text so the byte-equality check still passes — a partial pass leaves exactly the file the inventory named, and a replacement that swaps two comment lines for one can drop a sentence tail that only the returned diff shows.
- **Re-read the working doc from disk before the first patch of each round — and stat the file immediately before any multi-patch batch, aborting the rest of the batch on the first old_string miss** — the artifact can drift between your last read and your patch (a reviewer that edited the doc despite a read-only brief, a parallel session), and a batch fired from an hour-old snapshot lands on whatever the file became meanwhile: on a contested doc several fuzzy patches can report SUCCESS while silently overwriting the concurrent writer's newer rows before any miss surfaces, and the tell is the replaced pre-image being text you did not author. One miss or one wrong pre-image = halt the whole batch, re-read from disk, reconcile both fix sets, then re-apply only what is still missing — and never trust an 'the only artifact written was the comments file' self-report.
- **When one instance of an entity gets a per-resource correction, grep the doc for sibling instances in other phases and propagate it** — a per-profile path fix applied to one phase leaves the backup list (and any other phase touching the same entity) silently covering only the default instance, and the reviewer re-flags it next round. Propagate corrections to the mechanisms that CONSUME the corrected value, not only to sibling mentions: fixing a destination cell from a hostname to a domain leaves the enforcement mechanism unable to match domains, and the pair re-flags next round. The same applies to repeated CLAIMS of one behavior: after fixing an instance (e.g. a cache-window scope added to one conclusion), grep for every restatement of the claim — sibling cells/rows keep the unscoped wording and re-teach the wrong fact. Same discipline for ordering dependencies: when a step turns out to require an earlier phase's output (a command whose prerequisite is created later), add one forward-reference clause naming the dependency. The inverse direction fires on ADDITIONS: a new sibling instance (a probe, cleanup step, or call site added to a family the doc already regulates) must harvest the guards its siblings carry; enumerate the family's per-instance invariants (delete-guards, count checks, baseline comparisons) and carry them into the new instance, because an instance written from scratch omits them and the omission surfaces rounds later than a stale-reference grep would.
- **When inserting a step into a globally-numbered checklist, renumber every later step AND re-grep all `step N` cross-refs ACROSS THE WHOLE DOCUMENT** — the inserted number collides with an existing one (two different steps share a name) and unqualified references silently misdirect; keep cross-refs phase-qualified while renumbering. The sweep cannot stop at the renumbered section: env-template bullets, failure-mode rows, and honest notes cite rollout steps from other sections, and those off-section cites are exactly the ones a section-scoped sweep leaves stale.
- **The writer runs the required unslop pass BEFORE the first review round, not after style findings arrive** — unslop (skill_view('unslop'), the operator's standing requirement for design docs) applied late burns review rounds on punctuation churn; one pass at write time keeps early rounds on substance. The reviewer still unslop-checks every round, because rewrites re-introduce tells (same mechanism as stale cross-references). The parent's own fix patches re-introduce tells too — after each fix batch, grep the doc for the marker set (em AND en dashes outside code fences, curly quotes, arrows and double-arrows in prose, AI-vocab words, AND every word the reviewer itself cited as a tell — grep the whole doc for each such word, because a reviewer's instance list is often non-exhaustive and the parent's own grep finds the extras) and fix the hits before re-dispatching — scope the dash sweep to PROSE: the Rev/verdict-history header line's em-dash and middle-dot separators are the doc-format convention every doc reuses, so exempt the header in the sweep and say so in the reviewer dispatch, or the header gets re-flagged every round, or the next round burns on punctuation findings the fixer itself authored.
- **Replay an interrupted edit batch from the dead session's recorded tool-call arguments, not from a re-derivation** — the session record stores the full edit list; replaying it is faster and self-checking: each old_string that no longer matches is evidence that edit already landed. Count 'applied now vs already applied' and report both rather than treating misses as failures.
- **After any rewrite that touches prose emphasis, run a delimiter-parity pass over every paragraph (count `**` per paragraph: even; count backticks per paragraph: even; count opening and closing parentheses per rewritten span: equal, because a sentence split or merge that leaves an unbalanced paren survives every text grep and only a count catches it) and render-check any paragraph whose bold span changed** — a rewritten span's missing closing delimiter survives every grep (the text is intact) and mangles only the RENDERED document: the bold span swallows the following sentences (a runbook's later steps rendered as one bold blob) or leaves a literal `**` after a later phrase, depending on the renderer's flanking rules. The defect rode through seven review rounds because text-level checks cannot see it; make the parity pass part of every fix-batch close-out, and render-check runbook/spec paragraphs whose spans were rebuilt. Fold the close-out into ONE scripted pass per batch — fix-marker presence, stale-string absence, delimiter parity, sha256 and line-count pin — one command instead of four hand-greps, and the captured sha is what the next reviewer dispatch pins. If that close-out itself is consent-blocked or times out unattended, do not stall the loop on it: dispatch the fix-verify round with the gap disclosed in the dispatch ('parent pin missing — pin at your read time and note the gap in your header') and let the reviewer's standard sweeps carry the parity, glyph, and residue checks; the applied-evidence record is then the patch-tool diffs. Two counting refinements: exclude intentional LITERAL `` `**` `` code spans from the naive count (backtick-wrapped, not emphasis; they flag as false uneven) and keep a one-line exclusion note so the next counter does not re-chase them; prefer an actual render (python-markdown or markdown_it) over counts for any paragraph whose spans were rebuilt, because a renderer applies the flanking rules the counts approximate.
- **When a command containing a pipe (`|`) sits in a GFM table cell, escape every pipe (`\|`) or the table splits the cell at the pipe and the command renders truncated** — grep table cells for unescaped pipes whenever a command moves into or out of a table (cron lines, `a | b` pipelines, brace alternations such as `{standby\|primary}`).
- **Grep writer-authored code for self-redaction artifacts before review or push** — a writer that redacts its own REPORT can redact the deliverable itself: a Bearer-with-stars placeholder rode through the writer's `bash -n` pass onto the pushed branch and was caught only by the parent's own line-read (the writer's chat summary looked clean). Scan the diff for placeholder classes (placeholder stars, REDACTED, angle-bracket tokens) alongside the dropped-mechanism grep. The inverse failure is unmasked REAL values: before dispatching the first reviewer over a subagent-built evidence dir, run your own secret-shape sweep over it (token prefixes like syt_, bearer-shaped strings, KEY= lines carrying long values) — a writer that caught and fixed its own masking bug mid-run can leave earlier-class misses behind, and the reviewer must not inherit an unmasked baseline. Sweep for non-probe artifacts at the same time: a writer leaves its own fix-pass scripts (apply-fixes-*.py) beside the probes — name them non-evidence in the reviewer dispatch so no round treats them as ground truth.
- **Blob-verify every push_files push against `git hash-object` of the source file before trusting the branch state** — the push channel's newline handling is PASS-THROUGH WITH EMISSION VARIANCE, not a deterministic strip: the same channel has silently stripped a pushed main blob's final newline (MD047 failed on main) and, other sessions, landed bytes exactly as sent; it can also mangle backslash-escape sequences on emission. The tool's success report says nothing about bytes. Recipe: push the exact local bytes (no compensating extra newline), then fetch the file's blob sha (get_file_contents with fields [sha]) and compare with git hash-object of the source; on an off-by-one-newline mismatch, re-push the diagnosed corrected form (verified by hash, never blind retries); on a content mismatch, diff the fetched copy against disk to locate the exact changed bytes. Size alone is not a gate. When one line keeps mangling across attempts, rewrite it to avoid the trigger pattern entirely (build a JSON body with printf instead of escaped quotes) instead of iterating escape variants. For a large document, dispatch a subagent that reads the local file and pushes via MCP through the proven pipeline (chunked scratch writes, concatenate, cmp against the original, push, report the fetched sha) — proven byte-exact four times; the cmp gate is what catches the transcription traps: display-layer Bearer redaction (line ~520 of a doc with an AUTH header line), table-separator cell-count drift, name typos.
- **Re-verify file modes after every git add that follows a mode-setting index change** — with core.filemode=true a re-add re-records the on-disk mode and silently downgrades a staged 100755 to 100644: an amend dropped a new script's exec bit (the bash-prefix cron line masked it; the fresh clone exposed it). After mode-sensitive commits run `git ls-files -s` and diff the modes against intent.
- **Prefer a boundary splice over a giant old_string when replacing a whole numbered section.** Two large section rewrites in one loop missed (count=0) purely on hand-transcription wrap/indent drift (a 3-vs-4-space continuation line; an abbreviated wrap), while a start-marker + end-marker splice (python: text.index('## 7. Rollout plan') .. text.index('## 8. Risks'), replace the span) landed first try and is immune to inner-line drift. Reserve exact old_string replaces for small edits copied byte-for-byte from the on-disk read; for section-scale rewrites, locate the section boundaries, splice, then grep the old section's markers to confirm full removal.
- **Capture a repo's agent-instruction conventions as a topic excerpt file, not a verbatim copy under the original name** — the write guard gates agent-instruction filenames even inside an evidence dir, so the copy burns an approval prompt whose timeout loses the write; the excerpt carries the same review value ungated.
- **Pin the working doc's sha256 at every review round and re-grep exact old_strings on disk before each patch batch** — a concurrent writer (another Hermes session of the user's, or the user himself) can edit the doc mid-loop; this loop absorbed two out-of-session edit batches (one was a phantom re-derivation subagent dispatched from outside the parent conversation). A stale read_file snapshot mismatches disk truth (fuzzy-match failures, duplicate fixes); when a fold lands, record its provenance in the Rev history instead of fighting it, verify its cites like any other claim, and flag the race to the user.
- **Rebuild the doc's bookkeeping lines (Rev header chain, verdict history) wholesale from one deterministic script when a fold's fixes are purely bookkeeping, and verify the script's RENDERED output against the round record before dispatching** — incremental header patches compound their own defects (each fix introduces a skipped node, a dropped separator join, or a summary asserting unlanded work) and never converge; a rebuild script can also carry its own bugs (a format string mapping tuple elements into the wrong tally slots, a dict keyed one-off from the rendering loop) that corrupt every line it writes. Verify the rendered line, not the intent: chain order strictly descending with no gaps or duplicates, every tally matching the round record's known-correct values, separator joins intact — corrupted bookkeeping reads as landed text to the reviewer and bills back a full round.

## Factual and mechanism verification

- **Verify claimed facts against source yourself before accepting them into the doc** — research agents over-verify smoothly-worded claims (feature exists vs feature exists with the claimed semantics; check the feature's own docs exclusions section).
- **Verify every mechanism a design depends on exists in the tool's real output/flag surface BEFORE writing the step** — a JSON field, CLI flag, or config knob cited from memory (a revision id a `get` verb never emits, a request-body-size limit a server never had) may simply not exist; the reviewer tags these 'fictional mechanism' and the fix forces redesigning every consuming step (cache keys, headers, TOCTOU closures). Source-verify the emitted shape or the Config signature first. Existence is not invocation: after the metadata check, run the planned hook or command once END-TO-END in a throwaway fixture (staged benign file, then staged trigger file) — an entry can cite the right command and still fail through registry defaults (an upstream hook block omitting a pass-filenames-style key gets filenames appended, and the tool rejects them as unexpected args), which only an actual run exposes; the fixture transcript is the P-numbered probe the next round's gate re-runs.
- **When a step pins both a library builder and byte-level constraints on its output, review the builder with an OUTPUT test, not only a control-flow read** — a source read of the builder's control flow misses output properties the gate then requires: a dump/serialize call that re-serializes canonically (tight offsets, sorted tags, forced endianness) cannot satisfy an 'every other byte and position identical' in-place gate on non-canonical inputs (a 126-byte camera-style payload rebuilt to 87). Build a spec-valid non-canonical input, run the named builder, and compare lengths/bytes against the gate before accepting the step.
- **A privilege or authorization grant cited from a listing is a hypothesis, not a capability** — `sudo -l` shows what the config declares, not what executes: sudoers last-match-wins means a later untagged rule can leave a listed NOPASSWD grant demanding a password anyway. Before any step depends on passwordless elevation, probe the grant's effect directly (`sudo -n -u <user> true` must exit 0), record the probe as a baseline P<n>, and write every consumer block against the probed reality; a proposed new grant carries the same gate ('validated effective, not merely listed').
- **Trace a new gate's input production end to end before writing the gate** — a log capture or measurement taken before the events it measures exist evaluates against an empty set and can never fire, leaving the underlying defect intact behind a fix that looks landed; place the capture after the steps that generate the inputs (or have the gate's own stage generate them first), and make sure a tolerated-failure step ahead of the capture cannot abort it.
- **Scope-match every 'the phase settles this' assignment to the phase's own steps** — a fix that hands an open question to a named phase must read that phase's steps and confirm one of them exercises the question; a cron-only pilot cannot settle a subagent-dispatch question, and the mis-assignment surfaces as a fresh finding the next round.
- **Design-by-code-block must survive contact with the rest of the doc**: when a spec block defines a route/flag/param, the prose elsewhere must not contradict it (paths in query vs headers, params the implementation refuses). The reviewer treats code blocks as implementable truth. In final rounds, have the reviewer EXTRACT each shell/sudoers block verbatim and parse-check it (`sh -n` for scripts, `visudo -c -f` for sudoers files) — prose-level verification passes code blocks that fail to parse or carry a broken shebang order.
- **Any 'A enforces/covers everything B enforces' sentence needs an enumerated class list, and the shipped-file comments carry the same scoping** — unscoped equivalence claims ('CI re-runs every check', 'this copy is enforced', 'enforces everything') are contradicted by the doc's own named exceptions and re-teach false coverage to every later reader; scope each to the enumerated covered classes AND name the items that exist only on the other side. Before re-dispatching, grep the doc AND every artifact file for parity words ('mirrors', 'every check', 'everything', 'same checks') — the files ship without the doc, so a reader trusts the comment most, and the two contradicting each other in one PR is its own finding.
- **Verify Hermes-behavior claims against the DEPLOYED code on the device, not only web docs** — the adapter/plugin source that will actually run (`~/.hermes/hermes-agent/plugins/platforms/<platform>/`, plus its mautrix/SDK dependency source when semantics matter) is stronger ground truth than docs pages; this is where the highest-value catches came from (gateway self-bootstrap semantics, auto-accept gating, OUTPUT_FILE write-vs-read direction). Add the deployed adapter path to the reviewer's ground-truth list whenever the doc makes claims about how Hermes itself behaves.
- **Verify third-party-tool claims at the DEPLOYED version, not at repo main** — a shallow (`depth 1`) clone hides version history and makes recent-main features look deployed; fetch the deployed release tag and diff the relevant files before asserting a mechanism exists on the box (and record that verification in the doc's facts). GitHub code search without an explicit ref runs on the DEFAULT branch, so its hits are file-path pointers, not deployed-version evidence — fetch each file at the pinned ref for content. And the inverse: absence from the shipped man pages is NOT absence from the tool — the shipped package's own source (orig tarball) and README may implement and document an option the man pages omit; verify a capability against source and shipped docs before writing any 'not usable at the shipped version' rejection, and reject such options on the merits instead. An asset URL answering HTTP 200 proves existence only: before describing what a pinned hook or action RUNS, fetch the tool's own metadata at the tag (.pre-commit-hooks.yaml, README section, --help) — the entry command can differ from the popular one while the tag and asset are perfectly live. When the claim is about runtime behavior routed through a vendored library (reference resolution, protocol handling), pin the check to the dependency version the deployed tool actually vendors — read the deployed tool's dependency manifest (go.mod, lockfile) and fetch the library at that exact tag; a multi-version bracket is weaker than the vendored pin, and a behavior claim that load-bearing gets a durable evidence file (bodies, hashes, file:line cites, one-sentence consequence), not a comments-file mention.
- **Reproduce an empirical-constant finding under the NAMED binary before accepting or rejecting it** — one box can carry two builds of the same tool (distro package + a tools-dir install) whose identical command lines produce different outputs, and PATH resolution differs between agent contexts; a reviewer's contrary constant may be its environment's resolution, not a doc error, and a rejection defended without naming the binary gets re-opened by every future verifier whose PATH resolves differently. When confirming or rejecting such a finding, run the exact committed command through the specific binary path, and record that binary path (with version) in the doc's provenance note.
- **Every command in a test, gate, or impact-table cell must be runnable AS WRITTEN under the doc's own final state** — a positive test exercising a binary the design's own allowlist does not grant, or an impact-table cell still showing the pre-rewrite command after a switch to wrappers, fails on a CORRECT deployment (and a STOP-on-gate-fail rule then aborts the rollout at its own gate); before re-dispatching, trace each test command against the final allowlist/env/wrapper state it must run under. When the test names a scratch clone or fixture, enumerate what that tree carries first: a clone of the repo as it exists today holds only tracked files, so a test of an artifact script or config (absent until the design's own PR merges) must begin with an explicit copy step — 'run the hook' in a tree that never contained it exits 'No such file or directory', which an operator can misread as the guard refusing. Trace against the state the plan's OWN earlier steps create, not only today's box: a command set that resolves at review time can fail 100% after the plan's own move/rename/folder-creation steps run (root-absolute paths are orphaned by the plan's own migration), so derive each path/command from the post-plan state — a 'runnable as written' clean-claim checked at today's timepoint re-fails next round as a MAJOR. Trace the executing IDENTITY too: every step that creates a file or directory must be matched against each later consumer's runner and privileges — an artifact created under sudo (root-owned, mode 700) is unreadable to the invoking user the later steps assume, and a sudo-requiring command inside a block whose runner carries no sudo dies with 'a terminal is required to read the password'; after any edit that adds a command to a block, re-check the block's runner label against each added command's privilege requirement, and re-check the block's executor ROLE TAG when the runbook labels steps with A/M executor roles — an edit that adds a dashboard login under an A tag mis-roles the step and the next reviewer re-flags the label.
- **Reconcile every runbook rollback claim with the state-changing steps inside its advertised window** — a rollback scoped 'at any time before step N' is voided by any step inside that window that creates a new rollback precondition at a third party (a DS trust anchor published at the TLD parent carries a ~1-day cache there, so an NS switch-back after it SERVFAILs validating resolvers until the parent cache drains); scope the window to the first such step, and for post-window rollback spell out the escalated sequence with its TTL cost instead of leaving the old claim standing.
- **Trace each runbook step's executing host and network path against the firewall rules the plan's OWN earlier steps create** — a default-deny allowlist that omits the administration path (SSH from the orchestrating host) locks out every later step that reaches the box over it, and established-session survival only delays the lockout to the next connection; state the admin rule explicitly (port, source, optional post-bootstrap tightening) so the runbook cannot deadlock itself.
- **A reverse-proxy sketch that targets an on-box service over a NEW path (tunnel IP, interface address) must be checked against the service's actual LISTEN address, and the exit criteria must probe each backend FROM the new vantage point** — a loopback-only bind is invisible over the tunnel/interface IP, so 'the on-box side stays unmodified' is false until a rebind or relay step exists, and a staging record aimed at the one backend that was always reachable does not catch the miss.
- **Re-verify every research-phase version pin and upstream-diff claim at review time** — upstream moves between research day and review day (a new release ships, the manifest now serves only the newer version, tags and changelog entries now exist), and an 'X→main diff is empty' equivalence claim collapses when the verifier diffs against a stale clone's own HEAD (the checked-out tag IS the clone's HEAD, so the diff is trivially empty). Put the manifest/tag/changelog re-fetch in the reviewer dispatch; pin the design's version triple-anchored (manifest-listed AND git-tagged AND changelog-logged), and record a used-surface delta register between the source-verification tag and the pinned binary so [S] and [B] describe the same version by construction. When the re-pin SHIFTS line numbers, re-derive every [S] line cite by batch-grepping the anchor strings at the new tag in one script (a `grep -n <anchor>` loop over `git show <tag>:<path>`, then patch from the printed numbers) — hand-translated line numbers from the old tag land on unrelated code.
- **Verify a snapshot-pinned decision table against the SAVED capture, never a live refetch** — the re-verify-pin rule above governs version PINS; a decision TABLE derived from a dated capture (a priced model catalog, an endpoint list, a release-manifest join) is correct as of its capture, and re-deriving it from the live endpoint between writer and reviewer manufactures false findings out of values that legitimately moved. Point the reviewer at the evidence-dir JSON/CSV captures for the re-derivation; the doc's honest note carries the re-derive-at-adoption duty (re-fetch live to UPDATE the doc's snapshot at adoption, never to grade it mid-loop).
- **When the operator challenges the design's premise at kickoff and the simpler path wins, restructure the doc around the decision instead of implementing the original plan** — the challenge usually voids more than the headline feature: add a §0 decision record naming what is deferred and why, verify the replacement path with the doc's own Phase-1-style empirical checks BEFORE treating the flip as settled (if those checks fail, the deferral is wrong and the original build is back on), mark the deferred spec 'preserved for revival' instead of deleting reviewed content, mark now-moot open decisions as moot in place, and grep the doc for every stale consequence of the dropped premise and reverse it — a deferred design leaves booby traps behind (a cleanup phase that deletes the very tool the new decision made PRIMARY).
- **Parent-supplied 'facts' in a research or reviewer dispatch are hypotheses, not evidence** — context assembled from memory can be stale in exactly the details the design turns on (a tool-catalog count, which component runs which gateway); if the researcher cannot re-derive a claim from the deployed source, it must land in the doc's honest notes as 'task-context, unverified', never in a facts section as if probed. Say explicitly in the dispatch which context items came from the parent's memory so the researcher attacks those first.
- **A design that leans on an existing box convention cites the convention's CURRENT HEALTH, not just its shape** — the reviewer probes the live job or config the doc calls a precedent; a broken one becomes two outputs: a caveat in the doc's facts (so the design's own install avoids the same breakage, e.g. an exec bit its install step must set) and a separate user-facing flag, never a silent 'already practiced' claim.
- **When a rewrite consolidates several call sites into one shared execution point, re-map every operation's failure severity explicitly against the consuming pipeline's fatal-stage contract — folding execution moves failure boundaries.** A WARN-wrapped operation whose execution folds into a FATAL stage silently becomes FATAL (one bad request aborts the whole delivery), and if the executor applies requests atomically, one sibling's validity now gates the others' application; either split the consolidated step so each severity class keeps its own call site, or rewrite every error-map row and gate criterion that cited the old call sites — the sections must agree after the fold, not before.
- **Verification/gate commands must be runnable at the phase where they sit, from durable paths, with extents derived from a read — never from a pruned scratch dir or a hardcoded size.** Research-day probes in a pruned-after-idle cache dir will not exist on deploy day, so a post-deploy gate citing one fails at its own moment — put durable probes in a repo the design's PR itself adds; and a gate that takes an extent/size argument should derive it from a metadata read, not a hardcoded number, or a later layout change makes it silently under-cover.
- **Never let a header or Rev line claim a verification the doc does not record** — 'the verified X form' needs a pointer to where the verification lives (a §1.1 probe number, a recorded artifact, or an §8 honest-note for parent-context items); an attribution without a location reads as fiction to the reviewer, and the fix is a downgrade that costs a round.
- **When a finding rejects or reverses a previously-settled claim, verify the live premise yourself before patching and record the verification in the doc** — a mid-loop resumption inherits premises that parallel sessions can invert overnight (a git tip pushed, a cron fired and failed, a kit copy edited); re-run the specific read-only probes behind the affected sentences, cite the fresh probe in the doc's facts, and restate schedule/tense-sensitive claims against what the log now shows rather than what research day found.
- **A policy-rule candidate whose condition needs state the executing mechanism cannot observe gets recorded as evaluated-and-rejected, not repaired with an ungrounded enumeration** — when no recorded artifact carries the concrete values the condition names (a known-domain list, a unit set), patching them from inference plants a fictional mechanism; ground the rejection in the recorded evidence that shows the condition is unstateable (domain-blind finding text, the stateless-guardian constraint), keep the mechanism's default behavior, and cite the artifacts that prove the gap.
- **Upstream version pins age out mid-loop** — a vendor manifest that serves only the latest version can invalidate the pinned binary between research and review (this loop: 2.6.0 dropped from versions.json within 48h). Pin triple-anchored (manifest + git tag + CHANGELOG) with a delta register for the used surface, re-fetch the manifest each round that re-verifies the pin, and re-derive every line-level cite at the new tag before flipping the legend.
- **Check every cited arXiv source's NOTICE line, not just its abstract text** — a paper withdrawn by arXiv Admin still serves the v1 abstract verbatim, so a figures-match verification passes while the source is dead; re-fetch the abstract page, read the submission history for a withdrawal entry, and when one exists, disclose it at every cite site and record the withdrawal as a numbered probe (a rule can stand on the v1 figures, but only disclosed).
- **In LLM-provider designs, verify every pinned model id against the SERVING TOOL's documented id table, not the pricing page's product names** — marketing spelling ('Model 5.5') and API id spelling ('model-5-5') differ at the version segments, and an id transcribed from a pricing page fails at run time exactly like a fictional CLI flag; capture the serving tool's provider page (its id table) as a probe file so the spelling source is evidence, not a comments-file claim.
- **Verify a new public hostname's shape against the zone's edge-certificate coverage before consensus, not at the rollout gate** — Universal SSL on a Cloudflare full-setup zone covers the apex and first-level subdomains only, so a second-level subdomain (an `api.books.example.com` shape) gets no edge certificate and the TLS handshake fails at the edge before any ingress or origin is involved; the defect stays invisible until the rollout's DNS gate probes the name, after the kit, routes, and ingress entries are already built. When a design introduces a proxied hostname, require the doc to state the name is first-level (or that the zone carries a wildcard or advanced certificate covering it), and have the reviewer curl the name when one exists.

## Evidence, counts, and empirical claims

- **Never derive a GiB figure from `du -h` human-readable output — du CEILS to the next unit** (a 14.29-GiB directory prints "15G"), so a sizing arithmetic that treats the display value as the true GiB figure is off by up to a full unit and the error propagates into every headroom number derived from it. Cite the byte-exact figure (`du -s --block-size=1K` or `-B1`) as the authority, compute the derived numbers from it, and when a capture already exists in display-rounded form, note the ceil behavior beside the cite so the next reader does not re-derive a wrong unit from the display line.
- **Name each evidence capture with its own number BEFORE firing a probe batch — a payload whose output redirect target is fixed across fires silently overwrites the previous capture with the next fire's output** (the first capture's content is then recoverable only from session context, never from disk). One capture file per fire, distinct names, verified after each run; if an overwrite already happened, re-run the probe rather than reconstructing the lost capture from transcript context.
- **A fold that records execution progress must update the list its summary points at in the SAME edit** — a STATUS line claiming "steps 1, 2 and 4 are DONE (cites)" while the §-list it cites as carrying the recorded values is byte-unchanged leaves the gate unmeetable against the doc's own text, and the next reviewer re-flags the gap as the fold's own residue. Annotate each list item per-row (its capture cite, or its explicit not-obtainable note naming where the value will land), and point every scheduling phrase at the phase that will actually execute the deferred step ("phase 0 measures it" is stale the moment the fold reassigns the measurement to the build session).
- **To inspect a committed probe script, read the file — never run it 'to see'** — a probe script is a mutation suite, not a reference artifact: executing it to check one recorded constant runs every step in it (uploads, folder creates, album writes, deletes), leaving library residue and burning the mutation budget its parent session authorized for a different purpose. Read it with `read_file` first; execute only the single generator command the question needs, and re-derive constants from that one output.
- **When a reviewer's finding refutes the doc's factual region-map/band claims, stop hand-wording: compute the corrected text programmatically from the reviewer's own probe dump and cite the dump** — three consecutive hand-wordings of a stale-row map each introduced a fresh defect (iteration bounce 8→8→8→7→5→1); one census-derived rewrite computed from the reviewer's saved full-width JSON landed in a single round and survived byte-exact verification.
- **Re-run every enumeration probe (globs, Drive lists, directory counts) at each reviewer round, not only at research time** — parallel sessions create and upload artifacts while the loop runs, so a corpus census complete in round 1 is stale by round 3; classify each newly found instance in the doc AND sweep its sibling mentions (attribute tables, examples, move groups written while it did not exist). The same duty covers enumerations fetched from live WEB pages, not just box probes: transcribe the full list into a durable evidence file at fetch time so later rounds count from the record instead of re-rendering the page (a JS-rendered page such as swagger-ui or an API explorer returns an EMPTY extract from the fetch tool — render it in the browser tool and pull the data from the DOM (e.g. the .opblock-summary-path selectors) instead, then persist the extracted list as the evidence file). A closed range over a numbered evidence-file series ('W00-W11') is an enumeration claim too: list the directory before writing the range, or enumerate the members explicitly — a gap in the series (a never-created middle number) makes the range false and hands the next reviewer a free finding; the correcting fix names the real members., and a fix that touches a sentence carrying an empirical number re-derives that number from its source before patching — rephrasing the sentence around a stale number re-teaches it. Anything on a schedule gets the same treatment: a cron fire, CI run, or nightly job between rounds can flip a tense-sensitive premise (an event the doc describes in the future tense has already happened, possibly failing) — restate schedule-dependent claims against the live log at every re-dispatch. The same applies to a repo HEAD cited as ground truth: main advances when a PR merges mid-loop, so cite the sha as 'at probe time' and put its re-verification in every reviewer dispatch, never as a timeless pin.
- **Late-round findings (rounds 5+) cluster on four classes: stale grammar fragments from rewritten spec blocks, per-entity scoping gaps, fictional mechanisms, and quoted-evidence fidelity** — quoted-evidence = byte-level glyph substitutions inside quoted transcripts (e.g. U+2011 instead of '-'), non-verbatim renderings of a source the doc quotes faithfully elsewhere, and transcriptions of cited file lines that match neither the cited line's quoting nor spacing. Pre-grep all four before re-dispatching: glyph-scan quoted spans against the ASCII/sibling classes, re-read every quoted phrase against its source, re-grep each file:line cite fresh, and re-fetch every cited web page (a cited page 404s, redirects, or reorders its text between research day and review day — the doc's quote must match the live page's current order). And when a finding characterizes evidence it read (a traceback's line split, a file's structure), read that evidence file yourself before rewriting the doc sentence — the reviewer's own premise can be wrong, and patching from its description produces a quote matching neither the file nor the old doc text.
- **State the population and the extraction boundary behind every count.** A friction claim generalized from a sample ('every sampled event is X') is a round-1 finding when the full population splits 7-of-15; re-derive the full population in the research pass, not from a sample. Wherever two counts of the same population coexist (suggest-mined vs note-ledger, monthly table vs total), state the reconciliation and which extraction method misses which events — an unexplained gap reads as a contradiction to a reader who sums the parts, and a join that sees only answered prompts undercounts friction by its timeouts. Dedupe any count taken from the message ledger on tool_call_id before using it, and state the unit (rows vs events) wherever a figure appears: the transcript can record one answered event twice (byte-identical approval note, same tool_call_id, a second row appended later — a re-persist artifact, not two answers), so note-row counts overstate events and every derived figure (class splits, monthly tables, ratios) inherits the overcount. When a unit correction lands, restate EVERY dependent figure in one pass (class tables, splits, ratios, monthly blocks, honest-note counts) and label every figure that legitimately stays on the old basis — a per-finding patch leaves unlabeled stragglers, and each straggler costs its own review round (this loop spent two extra rounds on one worked-example figure and three candidate-motivation counts that survived the main restatement).
- **Date claims from durable on-box records, not session recollection** — when a doc asserts when something happened (deployed, granted, installed, go-live), derive the date from file mtimes, cron-install lines, config timestamps, or session bookends and cite them; approximate session memory misdates by a day, and the reviewer re-derives the date from the same records.
- **A rewritten empirical sentence needs re-probing, not just the stale-reference grep** — the grep sweep catches dropped mechanisms, not plausible-but-wrong facts: a rewrite that smooths a probe-backed description can invent structure that was never measured (an empty-padded band, a wrong vintage boundary), and the next reviewer re-flags it with a fresh probe. Before re-dispatching, re-run the read-only probe (or re-check the reviewer's recorded probe evidence) for any sentence whose content is empirical — rewrites corrupt fact claims, not just grammar. Better still: for STRUCTURAL claims (bands, counts, widths, boundaries), write the sentence from a computed aggregation of the reviewer's saved probe dump — derive the numbers in code, state only those, and cite the dump path in the doc — so the next reviewer diffs claims against data instead of re-deriving them; this ended a three-round hand-paraphrase drift (bands wrong three different ways) in one round. The same duty fires on a fix that INTRODUCES a quantitative claim (an eviction bound, a pool size, an estimate split): re-derive it from the doc's own stated mechanisms before re-dispatch — a number that silently assumes a cadence the doc never states is false under the doc's own literal reading, and the next reviewer re-flags it citing the doc's own text. And when a re-probe's result differs from the recorded one, the durable re-capture becomes the claim and the earlier observation is recorded as intermittent in the honest notes — the doc follows the record, never the first reading.
- **Re-grep every file:line cite at patch time when the repo is an actively-edited working tree** — line numbers drift between iterations while the tree is being edited, and a cite that lands on a bare comment line is next round's finding; transcribe cited commands byte-exact, quoting style included, and when two lines of one file are cited render both forms with per-line cites.
- **Back every exposure/isolation claim with a recorded live probe, output-masked** — "the agent can/cannot read X" is an empirical claim, not a docs claim: run the read-only probe on the box (env listing piped through `cut -d= -f1` for names only, ancestry via `ps -o ppid=`, a target `/proc/<pid>/environ` read test, kernel LSM/config check for any ptrace-hardening claim) and record the probe command + result in the doc's facts; unprobed exposure claims get tagged fictional by the reviewer, and an unmasked successful probe leaks real values into the session.
- **Digit-run and token-shape redaction in tool output is usually display masking, not file content** — some tool-result channels elide or asterisk out phone-shaped runs, long digit runs (16-digit ones can tag as [CREDIT_CARD]), AND long token-shaped strings on the way to the screen: a bearer-var placeholder like `${<SERVER>_MCP_BEARER}` can DISPLAY as `${<SER...R}` and an `<key>` placeholder as `***`, while the file on disk is intact — so a quoted port list, build date, tool path, or config variable can look truncated when it is not. Never re-read through the same masked channel to verify — and the masker can hit the DIAGNOSTIC itself: a codepoint dump's own output can come back with the digit runs replaced by classifier tags, so the dump is not always readable either. The verifications that survive every masking layer are SHAPE and COUNT: map every digit to a placeholder and read the resulting shape (structure with nothing left to mask), count the suspect characters (an asterisk-run quote proves nothing when the file's asterisk count is zero — the file may hold the real digits), and match digit runs by regex LENGTH (digit-count classes) rather than by a transcribed literal. A reviewer's evidence record can quote the masked DISPLAY of a line, so an evidence file that 'carries a masked line' may already hold the real values — shape-check the file before patching it, and record a provenance note beside a misquoted line instead of 'correcting' a value that was never wrong (a reviewer that chased the display burned a round on a finding it withdrew). In a review loop the same channel blinds the reviewer too, so record the byte-level verification as a numbered evidence file in the evidence dir and tell the next dispatch to codepoint-verify (not re-read) any line it plans to flag or quote that carries a token-shaped string — otherwise the finding re-appears every round. The masker also reaches write payloads, not only reads: a scripted fix pass whose old_string was copied from a masked display misses with count 0 against byte-correct disk text (an elided URL in the copy, the real URL in the file), and a token-shaped literal inside a write_file body can land masked in the written file — build scripted old_strings from codepoint-verified disk bytes, assemble such literals programmatically (concatenate the pieces so the raw form never rides in the tool call), and on misses save the applied subset as partial state, codepoint-dump the script's own literal AND the target region, then re-run a pass carrying only the resolved fixes. Verify an assembled placeholder by its FULL TERMINATED form (variable name plus closing brace, or the URL's final path segment), never by the name alone: an assembly slip that drops the closing brace produces a value the consumer cannot resolve, passes every name-only grep, and reads as clean prose until a reviewer byte-checks the termination.

In a doc-review loop this masker manufactures FALSE reviewer findings: an od or grep display of a 'Bearer '-prefixed mechanism line comes back scrubbed to 'Bearer ***', the reviewer flags the missing token interpolation as a MAJOR, and the disk was correct the whole time (this cost a full fix round on a script whose printf line was fine). Two countermeasures: prescribe the redaction-proof verification channels IN the reviewer dispatch — occurrence counts (grep -cF), in-bash boolean line comparisons that print MATCH/MISMATCH, md5sum of the extracted line versus md5sum of the expected string, and containment counts (grep -cF) of files the mechanism writes — never an echoed or od-dumped line; and build such mechanisms so the literal never rides in the format string at all (assemble the header in a shell variable, write it with the bash builtin printf — builtins have no /proc entry, which strengthens the argv-hygiene claim too).
- **Run shell probes in a container from an arbitrary local image with `--entrypoint /bin/sh`** — server images' entrypoints (a homeserver binary, an MCP server) consume `sh -c ...` as their own arguments and the probe does nothing; pin the entrypoint on the first try instead of rediscovering the failure class a second time.
- **When a reviewer's finding fix offers 'drop the claim or run the probe', run the one-command probe** — the weakened form silently costs the design a load-bearing property (volume ownership, a network path) that a later round argues about again, while an ephemeral-container probe costs minutes and lands as a numbered evidence row the fix cite can point at; record the failed attempt alongside the passing one so the retry is auditable.
- **An evidence register records what EXECUTED on the box, per binary — a sha256-verified download is not a run.** Phrase each artifact's evidence by what actually happened on the host ('aarch64 binary runs: <version string>; x86_64 sha256-verified only — not executable on this arm64 host'); claiming the plural when one leg could not execute (wrong arch, no qemu-user, no matching binfmt handler) records an execution that never happened, and the false claim propagates through the doc until a reviewer with the box's exec-feasibility facts catches it.
- **Never record an execution claim the evidence cannot support** — the register/evidence layer is the doc's trust anchor: this loop's concurrent fold wrote "binaries run" when only the arm64 binary could execute on the host (x86_64: no qemu-user, binfmt has no ELF handler). Scope execution claims to the architecture that actually ran; hash-only verification is recorded as hash-only. The reviewer tag for a fictional execution is as fatal as a fictional mechanism.
- **When consolidating reviewer output, fold any reviewer-run probe the doc depends on into the doc's §1.1 baseline as a numbered probe (add as P<n+1>, P<n+2>, …), not a citation to the review round** — the baseline is the doc's single reproducible ground truth; a probe that exists only in a comments file cannot be re-run by the next reviewer (scratch prunes after ~24 h idle), so evidence resting on it reads as unverifiable next round. Copy the reviewer's probe SCRIPT FILES too, not only their outputs: one numbered P-file per script plus a provenance README in the evidence dir (recorded-by round, window pinning, any overwritten-output disclosure) is what lets the next round re-run the fixture instead of re-deriving it, and it is the only durable form of a fixture the acceptance-gate rule depends on. This extends to PROSE pointers: the final doc may not cite the comments file anywhere (grep its name before every re-dispatch and before publishing) — 'verified clean' records the doc's claims lean on are transcribed as numbered probes in the evidence dir, because the comments file is overwritten each round and prunes, while the doc ships. Transcribe in the SAME batch as the fix that rests on the verification — a mechanism claim patched into the doc while its verification survives only in the soon-to-be-overwritten comments file surfaces as its own finding a round later; the transcription is the numbered probe file, its manifest row, a §13 sources entry, and a cite at the consuming step. Persist each probe record with its status attribution (a status line in the file, or a per-file manifest beside the bodies carrying url, HTTP status, byte count, and sha256) — bodies without statuses leave the doc's '404'/'200' claims verifiable only by re-probing. And after any sandbox or container reset mid-loop, re-locate the corpus and re-run the read-only probes whose record files did not survive into the canonical evidence dir — a doc citing probe files that no longer exist is itself a MAJOR finding: re-persist the records, then restate the doc's claims against the durable re-capture before the next round.
- **When a fix round changes or adds evidence files, refresh the manifest in one staged maintenance script** — hash-refresh the changed rows, append rows for the new probes, and add tool-artifact rows for the scripts themselves marked non-evidence; a manifest whose hashes no longer match the files it certifies turns the next round's integrity check into findings instead of a pass. Refresh EVERY row's hash on each run, including the maintenance script's own row — a tool that re-hashes only the rows it knows changed goes stale on its own bytes the moment it is edited, and the reviewer's all-rows loop then fails on the tool artifact itself.
- **Keep machine-payload evidence files pure — provenance rides the manifest row, never appended prose** — an annotation appended to a JSON/CSV probe corrupts the format every later re-reader parses, and the write guard's refusal on such a file is the tell to move the provenance into the manifest origin string instead.

- **Re-read the design registry at loop start AND at every resume, and sweep sibling designs for claim collisions** — the corpus moves (synced-tree migrations, parallel loops working the same tree), so an index read at loop start is stale by resume time, and a new doc's mechanical choices (loopback port, host paths under the service user, nologin username, image and env-file names) can collide with a sibling design's claims. First consensus wins and the later doc reassigns: swap the value doc-wide (grep the old value, exclude the intentional mention of the conflict), record WHY at the recorded-probe site without falsifying what the probe observed ('port X was free at probe time; the registry assigns it to <sibling>'), and note the rationale in the decision row. Sweep the sibling docs' own claims in the same tree each round, not only at write time. Version cites go stale the same way: re-derive every sibling-doc Rev/date parenthetical from the registry at resume (parallel style passes and recovery re-uploads bump sibling revs between the cite being written and the resume), and correct it at every mention before the next reviewer turns the stale one into a free finding. When the stale cite names a rev the LOCAL sibling FILE does not carry (the repo merged a rev the synced tree lags), the defect is the local copy, not the citing doc: sync the local file from the merged PR (mcp__github get_file_contents on the repo path, targeted patches on header + changed decisions when the write guard blocks a full overwrite) instead of rewording the citation — the citing doc's finding then closes at the source, and the next reviewer verifies against the current file. When the repoint is a blanket sweep across sibling ROWS (a design file's current rev vs stale Attributes cells), shape the replace to the cell form and attribute every remaining old-form hit: Attributes cells must carry the current rev (the sweep's target), while History cells legitimately record the rev that was current when the recorded action happened ('per <design> Rev 1 (the operator's call)') — repointing those rewrites history, so a post-sweep grep that still finds old-form hits is a defect only when the hit sits in an Attributes cell; report the attributed remainder as expected in the next dispatch. A registry-wide stale-cite finding against sibling rows is a parent-level mechanical fix that can ride the doc's own publish PR.

## On-box deploy and verification (post-merge phase)

- **Walk the DEPLOY SURFACE (quadlet Volume lines, env example knobs, update.sh service rows, cron install contracts) against the design's runtime sections before the deploy gate** — a code-complete, test-green implementation can miss a bind mount that makes the whole feature inert on the box, and the quadlet's header comments can still carry stale pre-feature claims ('no data volume') that hide the gap; the design's runtime reach (store dirs, mounts, env names) is the checklist, not the code. Verify every file the child's final report FLAGS via a mutation verifier against the PUSHED branch before merging: a refused sandbox write does not mean the pushed bytes are wrong, and the child's fresh-clone claim is the child's own claim, not the verification.
- **Fold on-box prerequisites into the attended block ahead of the recreate, and ship the recovery line in the same reply** — a bind-mounted source directory the quadlet mounts must EXIST before the recreate (podman's statfs on a missing bind source fails the unit start outright), and a failed first recreate leaves the unit dead and the server down; the instant-recovery line (flip the behavior-changing knob to its off value with sed, re-run update.sh) belongs in the SAME reply as the diagnosis request so the box is never down while the root cause is hunted.
- **Diagnose a failed unit start without journals** — this box's users cannot read their own unit journals (journalctl --user fails on their own units with insufficient permissions); use `podman ps -a` for a leftover container, then a foreground `podman run` with the quadlet's exact `--env-file`/`-p`/`-v` flags so the crash line lands on the terminal. The statfs error on a missing bind source is the signature of the missing-prerequisite class.
- **Re-search the deferred tool catalog after a box deploy before assuming the server's MCP tools are lost** — the gateway may not re-register a recreated server in the stale session snapshot, yet a fresh tool_search finds them fully callable; run the smoke ladder through the normal MCP tool calls (bearer validity in api_status, live reads, the new api_status block) with zero relay involvement instead of hand-building loopback curl relays.
- **Re-derive 'no API for X' design claims against the USER's own exports before treating unreachable-data scope as settled** — a GDPR account export the user uploads out-of-band can hold exactly the data a design decision marked unreachable (sleep history, training metrics, unstripped FIT originals); census it directly (zip listing, per-record field keys, date ranges) instead of citing the design's claim, and fold the finding back as a measured fact that upgrades the risk row. When the export's per-activity filenames turn out to be in a different id space from API activity ids (zero filename overlap), link files to activities by decoding the FIT's own session/monitoring start_time against the API's startTimeGMT — never by filename — and read size ratios (the API-delivered copy roughly half the original for a GPS activity) as the cheap stripping signal a field census then confirms. A summarize-only activity-file tool never attaches the bytes, so a byte-level diff of the API copy needs a route other than the MCP tool.
- **Treat a relay/cron-assisted publish fire as unverified until the PR exists AND the index row is on main** — the fire's success line and the branch push both stop short of the publish: the staged payload can die between the branch push and PR creation, leaving a landed branch with no PR and an empty PROPOSED/ folder that reads as published long after. After every fire (and on any resume), read back the three landing marks — the PR list for the branch name, the PROPOSED/ listing for the doc, a DESIGN-INDEX grep for the stem — and when the PR is the missing mark, open it from the stalled branch instead of re-firing the relay (the payload encodes the state it was built for).
- **Number and date every rev in the doc header** ('Rev: N — post iteration M, tags incorporated, one clause each') so the loop is auditable and the reviewer can fix-verify mechanically, and keep a running '**Verdict history:**' line under it (one entry per round: tag counts → incorporated in Rev N) so the header alone shows the loop's progression. Append new rev and history entries below the existing ones — a replacement edit that swallows the previous rev's line deletes the audit trail and costs a round to restore. A doc that defines its own expected-registry-row fence (the house §0.3 row) hardcodes its current rev there too: move that fence in the SAME batch as every header bump — the rev value lives in exactly two doc instances (header, row fence), and a bump that moves only the header plants a Rev-vs-row mismatch the next reviewer re-flags round after round; grep the doc's rev instances (header, history line, row fence) before every dispatch.
- **Publish each finished doc immediately when it reaches zero findings** (not all at the end) — overnight/unattended loops can then report partial success if interrupted, and the user finds finals merged in the repo in the morning regardless of loop state. Opening the PR is the publish; the squash-merge can follow as soon as the required checks are green.
- **A zero-findings bar (NITs included) converges, but expect ~9–10 iterations** for a source-verified design doc — late-round findings are usually self-inflicted rewrite residues (stale cross-references, scoped-wrong flag claims), shrinking monotonically once each revision is verified against source. If counts stop shrinking across two rounds, suspect reviewer noise rather than doc defects and ask for a verdict on evidence only.
- **Track iterations and remaining tags in your status replies** — the user asks 'how many rounds?' and 'still running?' unprompted; answer from the comment files' verdict lines, not from memory. Propagate the counts into the doc's verdict history from the comments file's own tag-count line, never from the child's chat summary — the two can disagree, and the wrong arithmetic then sits in the doc's header for a later reviewer to flag.
- **(Drive-archive era only.) Verify the upload path at loop start and hold the naming convention steady** — run a read-only Drive list before the loop so a stale route surfaces then, not at the final upload; the working doc, evidence dir, AND comments file live in the synced design tree when the sandboxed terminal backend is active (its DESIGN-INDEX.md is the registry's local copy; the flat home dir and cache/scratch are unmounted or pruned there) and in the home dir otherwise — put the comments file BESIDE the doc in the working tree in both eras (`review-comments[-<topic>].md`, overwritten per iteration), never in cache/scratch, which prunes after ~24 h idle and wiped a round's comments file mid-loop once; final copy `<topic>-design-final.md` uploaded to `/design-docs/PROPOSED` on Proton Drive via the proton MCP: cp the working doc to the `-final.md` name first (the dest is a FOLDER and the committed name is the src basename), stage it to `/srv/mcp_files/send/` (sandbox-writable, world-readable), then call `mcp__proton__proton_drive` upload with confirm=false dry-run first — that proves the proton container can SEE the staged path (it mounts only its own filesystem plus the spool bind; map its reach with a dry-run against a must-exist path like `/etc/hostname` before assuming any staging location) — then confirm=true after the user's go; the CLI fallback during the proton-CLI offboarding is `/home/hermes/.hermes/bin/proton drive items upload <file> /design-docs/PROPOSED --if-exists replace --output json --no-input` via the relay (absolute path; there is no bare `drive` alias); the folder exists per the design-organization doc — recreate only if the list shows it missing) and verified with the MCP list count for `<name>`; for a bytes-level guarantee on the ~50 KB finals, round-trip-download the item and compare sha256 against the local file — the folder grep proves presence, the hash proves byte-integrity (the proton container must be able to WRITE the download destination: `/srv/mcp_files/receive` rejects its temp file until the operator grants the mcp user write there — ask rather than skipping the verify; `--dest -` streams to stdout where the wrapper supports it).
- **(Drive-archive era only.) Drive-publish mechanics are retired** — registered-path updates, root-hit sweeps, and 0-byte stub cleanup belong to the frozen archive tree; an old session's unfinished Drive work gets re-published through the git PR flow (the canonical path), not resumed through the retired upload commands.
- **Locate design-repo files by registry stem, never by an assumed folder** — the GitHub repo organizes by status folders (PROPOSED/, ADOPTED/, WITHDRAWN/) plus root-level docs, while the local synced tree is flat with a few status folders (ADOPTED/ observed, no PROPOSED/): a merged PROPOSED doc can sit at repo root, so a folder-guessed path 404s and a flat-tree ls cannot prove folder membership. Grep the stem in DESIGN-INDEX.md first (the registry wins on placement conflicts), then fetch the exact path it names; verify a folder-membership claim by listing that folder, not by assuming it.
- **(Drive-archive era only.) Register every upload and every status change in the Drive registry** (`/design-docs/DESIGN-INDEX.md`; taxonomy + schema in `design-docs-organization-design-final.md`): after uploading a final, download the Drive index fresh first (`mcp__proton__proton_drive` download with dest_dir inside the synced tree — the proton container writes only where it has mounts; if its temp file is refused, the container's write identity fails the spool dirs' group check even with the spool mounted, so rather than skipping the fresh pull verify the local synced DESIGN-INDEX.md copy is current via `get` metadata: its `sha1` must equal the local file's `sha1sum` — note Drive `size_bytes` is the encrypted padded size and `original_size_bytes` is the content size; a sha1 match IS the fresh index, the verified path while the container write is broken) and edit THAT copy — the synced design tree's DESIGN-INDEX.md is the copy sibling sessions read, so land the fresh download at the tree path, not at a flat home-dir path that no longer exists on a sandboxed surface — a parallel session may have re-uploaded it after your last pull (same drift class as the doc-copy reconciliation); add/refresh the row: Doc, Status, Attributes, Rev/date, Subject, Go + implementation evidence, Next action, History, Withdrawn→; replace-upload it (cp the edited index to `/srv/mcp_files/send/`, then MCP upload to `/design-docs` with `--if-exists replace` semantics via confirm=true), verify with the MCP root list count for DESIGN-INDEX. On a later status change (the operator's explicit go + probed implementation evidence → ADOPTED; supersede/expiry/abandonment → WITHDRAWN), move the file into the status folder and update the row, replace-upload again — the MCP wrapper has NO move action, so a status change known before first publish uploads straight into the target folder, and a post-publish move goes through the operator or the CLI fallback (`/home/hermes/.hermes/bin/proton drive items move <path> --into /design-docs/ADOPTED`). When a finalised doc supersedes an earlier NON-final copy of itself still sitting in the target folder (the parked-draft class), move that copy to /design-docs/WITHDRAWN and add its row there (SUPERSEDED → <final-name>, 'no Rev · <draft date>') — a folder grep for the base name otherwise counts the stale copy and misreads the folder state. The index row is the source of truth; the folder is physical convenience — on disagreement, fix the folder. A REV UPDATE of an already-registered doc is MCP-first too: edit the working copy, cp it to `/srv/mcp_files/send/` (mode 644), MCP upload with `if_exists: replace` to the REGISTERED path, verify via `get` sha1 against the local `sha1sum`, then bump the row's Rev/date and replace-upload the index the same way — no CLI anywhere; the relay/CLI path stays as fallback only.
- **Publish every finished doc as a PR to the design repo** — `<your-org>/design-docs` (private) is the canonical source of truth (enforcement runs at the GitHub free tier: squash-only merges + delete-head-on-merge; full branch protection is Pro-gated and its payloads live in the repo's guards/); Proton Drive `/design-docs` is a frozen pre-migration archive (never re-upload docs there; one file per design, finals only; pre-final drafts are deleted after review and git history retains them; the layout mirrors the Drive folders: PROPOSED/ ADOPTED/ WITHDRAWN/ plus archive/, with the in-repo AGENTS.md as the process contract; the Drive-era bullets below apply only to the archived copies or an old session's unfinished Drive work). The flow: write and revise on a `design/<name>` branch, PR against `main`, required checks (`docs / markdownlint`, `secrets / gitleaks`) must pass, then squash-merge — the merge is the checkpoint, and the repo's AGENTS.md lets agents squash-merge their own PRs when checks are green. The index row update rides the same PR. Large new docs ride the user-run staged-script path (the github-repo-management skill's bulk-repo-sync reference; that file lives in that skill's directory, not here), or inline `push_files` dispatched through a subagent, gated by blob-sha verification either way — the push channel strips trailing newlines and mangles backslash escapes, so the sha check is the gate, not the path (see Doc and patch integrity).
- **Reproduce the repo's lint gate locally with the gate's own config mechanics before pushing** — markdownlint-cli2 has no CLI config flag; a `-c` argument is silently ignored and the run falls back to defaults, so a config-less local run neither proves nor disproves CI. Copy the changed file plus the repo's `.markdownlint-cli2.jsonc` into a scratch dir and run the pinned version there; the repo's config disables a large MD set, so a config-less run floods with false findings.
- **Read PR check state from `mergeable_state` on a pull_request_read get — `get_check_runs` is token-blocked on private repos** — `unstable` means only non-required checks are red or pending and the merge is still allowed; `blocked` means a required one is. Close-and-reopen does not retrigger CI while the head SHA is unchanged, and `update_pull_request_branch` answering 'there are no new commits on the base branch' is the base-staleness diagnostic, not an error to retry; a head-commit push is the retrigger that works.
- **Grep the synced DESIGN-INDEX.md copy for the doc's stem before appending its row** — sibling sessions mirror main's index into the same tree between your read and your write, and an append without the grep creates a duplicate row the registry's readers count twice; on a hit, merge updates into the existing row instead of adding a second.
- **Never re-trigger a queued publish/relay job whose target state has already moved** — a blocked job encodes the state it was built for (target folder, stale copy, pre-adoption status); after any other path completed the work, check the current registry state before re-firing anything, and report the superseded job as done-by-other-means instead of re-triggering it.
- **Post-consensus mechanical one-liners (renames, footers, quote completions) don't need a fresh reviewer pass** — apply them and self-check with grep for the exact strings; re-dispatching for them wastes a round. Reserve new passes for findings that change mechanics. Close the loop itself with one bookkeeping rev: fold the final round's verdict into the verdict history, update the probe-count line for probes late rounds added, and refresh the status line (a doc that reached consensus is no longer 'awaiting review').
- **A doc that defines a registry, index, or lifecycle must walk ITSELF through it as the worked example** — name its own final's upload target for the state where the target structure does not exist yet (which root/folder, at which trigger), its own registry row, and the transition that first moves it out of PROPOSED; a scheme whose migration never registers its own doc strands the pointer its own skill-patch text hard-codes and produces impossible orderings (upload before the folder exists) that cost a full review round. And the registry schema's columns must host every 'the row records X' claim the prose makes (go-evidence, round-trip history) — a state rule that requires row content no column can hold fails on internal consistency; add the column, not a footnote.
- **When a completed draft targets the wrong app, park it renamed — never delete it or rewrite it in place.** An identity flip voids the doc's target, not its research: rename the file to the scope its content actually covers, repoint its Comments line at a matching comments-file name, and write a Status line stating the identity finding and that the doc sits unreviewed. The replacement dispatch reuses the same evidence dir (the wrong-target probes become the new doc's identity evidence) and re-aims every locked decision before reuse — answers to a mis-aimed clarify card describe the card's framing, not the target (a 'keeps the satirical personality' answer does not transfer to a journaling app), and app-specific open questions die with the old doc.

## Loop operations and environment

- **User steers mid-loop arrive after the reviewer finished** — check the delegate list before steering; if the child already exited, fold the steer into your next patch + re-dispatch instead of trying to message a dead agent.
- **Let the researcher/reviewer run the host probes — do not re-probe ground truth yourself in the main thread** — in an interactive-approval environment a read-only probe from the main thread opens an approval prompt that stalls the whole unattended loop on user silence, while the identical probes run unattended inside subagents; keep the main thread to file moves, patches and dispatches, and verify child self-reports by grepping the doc and artifacts instead of re-running gated commands. Downloads are probes too: fetching a release binary to scratch (curl + chmod + exec `--help`) gates the same way — hand the pending re-probe to the next reviewer round instead of running it in the main thread. Exception: in an ATTENDED window (the user is present and answering), run the one consent-blocked probe in the main thread rather than burning a review round on it — the delegation rule protects unattended loops from stalls, not attended ones — and record its output as a numbered probe row in the doc so the baseline stays reproducible. Batch file edits take the same rule: in an unattended loop apply them as targeted patch-tool replacements, not as one consent-gated script-execution batch — the script sits on an approval prompt for its whole timeout when the user is away, and the stall is exactly the window in which a concurrent session re-opens the same file. The timeout also bites when the user was present minutes earlier and steps away: a large mutating edit batch sits on its card through the full ~10-minute timeout and dies unexecuted, so keep big edit batches for windows when the user is actively replying, and fall back to sequential targeted patches (each its own quick gate) otherwise. If the user later explicitly says to re-request the approval, re-sending the IDENTICAL blocked command is correct — that explicit instruction overrides the no-retry default; a silent timeout does not.
- **Map the approval surface before scheduling the loop's unattended work — it is three shapes, and each has its own lever.** Shell commands gate on dangerous classes; execute_code scripts gate whole-script on gateway/messaging surfaces (a viewer-typed local turn is exempt); patch/write_file and MCP verb calls never prompt (servers default trust: full). A container terminal backend skips the shell gate entirely unless host paths are bind-mounted, so after such a switch the unattended-stall surface shrinks to MCP verbs and host-side operations — pick the lever to match the shape: an allowlist rule key only for a class you would run unattended, smart_policy text for a recurring benign shape the guardian should auto-approve, a scoped MCP wrapper verb for a gated host-side operation, a workflow shape change (script files, not heredocs) for whole-script asks. And a READ-ONLY probe whose command TEXT embeds classifier-flagged literals (deny-rule strings, gateway-restart wording) still trips the gate on its text alone: put such literals in a file the probe reads, not in the shell line; a denied or pending probe is disclosed to the user and handed to the next round, never retried (a card left pending by a finished child ages out as a timeout; tell the user to deny any stray card). And a candidate rule text shipped in a doc (allowlist entry, deny rule, smart_policy rule) gets a verdict test against every recorded member of the family it targets before review — positives must match their intended rule and negatives must stay clean; a rule whose text denies the population it claims to auto-approve (an option or path condition every real command carries) is an inverted-benefit defect, and the round's fixture re-run is its acceptance gate.
- **Research dispatches for box-touching designs must pre-declare the terminal sandbox** — when the terminal backend runs container-sealed, the researcher cannot probe host services (/etc, systemctl, host ss); state the constraint in the dispatch context and point every box claim at sibling docs' recorded baselines (cite file + probe number as provenance); anything underivable lands in honest notes as task-context. An undeclared constraint surfaces as a round of 'unverified' findings, or as fabricated probes. Two dispatch-side duties ride with it: stat every local artifact path you name in the dispatch FROM THE SURFACE the subagent will run on before dispatching (the sandbox sees a subset of the host tree, and a named-but-absent clone costs the writer a discovery round plus a substitution probe it must record), and point every private-repo read in the dispatch at the GitHub MCP tools (tokenized) rather than raw curl — unauthenticated requests 404 on private repos, and a reviewer that loses a ground-truth source that way burns a round disclosing or re-deriving the loss.
- **On a sandboxed surface, 'Failed to read file' from patch/read tools is the container boundary, not a deleted file** — desktop-wrapped sessions run terminal AND file tools inside the sandbox (host home invisible), so a doc that 'vanished' is usually just out of view; stat via terminal (and check `hostname`) before diagnosing deletion, and never spend the same-tool loop-halt budget on identical read failures (10 identical patch failures fired the hard stop in this loop). The reviewer loop cannot run from a wrapped surface until its ground truth is reachable (host source tree, state.db, evidence dir, upload target); pause until the operator mounts the needed paths, then resume INSIDE the sandbox with a sandbox-adjusted ground-truth list — captured probe files instead of live-box probes, re-clones of public repos via egress, web re-fetches — and state the swap explicitly in the reviewer dispatch so 'unprobed' does not read as 'unverified'. Improvised host syncs are still the wrong first move; the mount is.
- **Treat a prior session's 'unreachable from the sandbox' claim as a hypothesis about THAT session's mounts, not a standing fact — re-probe the mount table at resume before deferring anything to a 'next host-side window'.** Mount lists change between sessions (consolidation passes, profile switches, new binds), so the blocked step may now be one copy away; when it is, run it immediately, transcribe what survives of the referenced probes (script, output, or both; record the missing half in the provenance note instead of reconstructing either), and rewrite the doc's honest note from 'pending' to 'done' in the same pass so the next reviewer does not re-flag a stale deferral.
- **In an attended chat session, a user message arriving while a mutating tool call sits on its approval card WITHDRAWS the approval and cancels the call plus any queued reads behind it in the same batch** — sequence long mutating commands away from likely reply moments, split state-changing steps into independently-valuable commands (each gate separately approvable, so a withdrawn approval loses nothing), and afterward reconcile what actually ran from disk state (mtimes, sha256, marker greps), never from the interrupted call's intent: a cancel mid-batch leaves an unknown subset applied.
- **Keep unattended verification commands free of trailing cleanup (rm, mv-back) clauses — a compound `verify && cleanup` line gates as ONE approval unit, and the gate kills the whole line including the verification results when nobody answers; the `rm -rf` clause is what trips the classifier.** Two reviewer rounds ended their closing machine batteries unexecuted exactly this way; run the verification alone, run scratch cleanup as a separate disposable call (or an attended step), and label scratch dirs non-evidence in the next dispatch instead of deleting them mid-round.
- **Never truncate the output of a state-changing probe script** — piping a mutating script through a truncating reader (`head`, `less` in a pipe) closes the pipe and SIGPIPEs it at a stdout flush boundary, killing it mid-flight with its own cleanup steps still unexecuted. Run it to completion with output captured to a file, then read that file with `read_file`; when only the generator part is needed, run that one command, not the whole script.
- **`delegate_task list` shows 0 live children even mid-loop when the reviewers just finished** (results re-enter as completion messages one per batch), so a bare 'running' claim looks fabricated to the user. Cite the comment files' timestamps + verdict lines and the delegation transcript paths; those files are the loop's ground truth for status.
- **Tell every dispatched researcher/reviewer to pin an explicit `workdir` on its FIRST terminal call** — the persisted shell cwd can point at a directory another session deleted (shared container `/tmp` scratch) or a dead container path, and every terminal call then exits 126 with a stale `cd` error before the command runs, which reads to the child as a broken environment and burns a round diagnosing it. One line in the dispatch context ('pin workdir on your first terminal call') costs nothing and prevents it.
- **Stat the doc, evidence dir, and one ground-truth file at the start of every round; if they vanish mid-loop, stop the loop and tell the user** — the environment under the loop can change beneath it (tool shells wrapped into an isolated container with no host mounts makes doc + evidence + monorepo + upload target unreachable in one step while the conversation continues); dispatching a reviewer into a broken environment burns a round discovering the loss. The doc's last verified state and every applied-fix diff survive in the session context, so the doc is rebuildable byte-exactly and web-based evidence is re-capturable via egress once the environment settles; live-box probes wait for the mount. Two hard-won refinements: (1) hold a MIRROR of the working doc in a wipe-surviving location while the loop runs (the synced design tree and `~/.hermes/` survived a host-side wipe that took the top-level home dir) — a single top-level copy dies with its directory, and a mirror turns recovery from a full rebuild into a diff check; name that fallback copy in each reviewer dispatch when the doc's path sits in a wiped-class location, so a reviewer that loses its target mid-round has a stated fallback instead of halting. (2) A rebuild replayed from recorded tool-call arguments is byte-exact EXCEPT at credential-mask spans: the recorded read_file output is itself redacted (it swallowed the closing backtick after an `ApiKey ***` mask and shortened an env-var placeholder), so the replayed text differs from disk there no matter how faithfully the record is replayed — verify the rebuild against the last round's pinned sha, attribute residual mismatch at mask spans to the channel's redaction rather than a lost patch, restore the span shape the reviewer's verified-clean section recorded (it checked delimiter balance on disk), disclose the residual uncertainty in the next dispatch, and never repair the divergence by inventing masked content. (3) Replay EVERY revision layer of the doc's recorded patch history in order when reconstructing — a replay that applies only the layers it finds in the current window leaves a hybrid that reads coherent, mismatches the last pinned sha for reasons the mask-span rule does not explain, and costs a wasted verification round; count the replayed layers against the verdict history's rev list before trusting the result. And after a rebuild relocates the doc, grep it for its own path self-references (evidence dir, registry, sibling-doc paths) — the recorded text carries the old locations, and a fresh reviewer flags every stale one.
- **A wake trigger that greps the comments file fires on STALE verdicts** — a `CONSENSUS: reached` line persists in the file after the round that wrote it until the next reviewer overwrites it, so a watcher started after a consensus round matches the old marker and wakes immediately (verdict-shaped boilerplate inside the file header trips it too). Gate any file-grep trigger on the comments file's mtime being newer than the watcher's start, or watch the unambiguous end-state instead (git era: the doc's PR merge or its DESIGN-INDEX row landing).
- **When resuming after a crash ('run again' with no context), reconstruct state from the record, not from memory** — the dead session's transcript (session search: browse recent sessions, read the latest, scroll to its end) shows its last in-flight action; a tool call with no recorded result never landed. Confirm against live ground truth before replaying (doc and comments mtimes, delegation dirs, grep for the edit's unique markers) — a batch can be partially applied. Recover the user's exact decision text from the recorded chat messages instead of paraphrasing it; a fold built on a paraphrased decision inherits the paraphrase's drift.
- **Zombie and sibling-loop races: the full detection, liveness-forensics, and reconciliation playbook lives in `references/loop-mechanics.md` — read it before re-dispatching after any crash and whenever a foreign edit lands mid-round** — quick tells: a verdict citing a rev you never created, a doc sha or line count you did not move, a self-describing 'fix pass' narrating itself in the doc's own header, a comments file you did not expect, or a patch answering 'already contains the target text' on text you are about to write.
- **Write a relay-executor payload against the executor's environment, not the composing sandbox's — stat every path the payload references through the executor's context before the first fire.** The relay executor is a separate process with its own mount table and $HOME: /workspace resolves only inside the agent sandbox, and a payload carrying sandbox path assumptions ($HOME-relative credential paths, a BIND_DIR fallback to /workspace) dies on missing files or empty output, one fire per discovery. Stage everything the payload needs (probe scripts, staged credentials, output captures) under a path both surfaces reach — the synced design tree is the proven one — reference absolute shared paths only, and `bash -n` the payload before firing.
