# Rootless Podman Quadlet Services

## When to Use

Load when creating, updating, restarting, or debugging a rootless podman quadlet service on this infra (`.container` files under a dedicated user's `~/.config/containers/systemd/`) — including shipping image updates and diagnosing services that start but don't answer.

Pattern for long-running containerized services on this infra: user-scoped systemd units generated from `.container` files, no root, no exposed ports.

## Hard rules

- **A restart re-creates the container ONLY from the generated unit, and only with a fresh daemon-reload behind it.** Quadlet units run `podman run --replace --rm ...` in ExecStart: with the generated ExecStart current, a `systemctl --user restart` DOES recreate from the current `.container` and pulled image (verified live). But the generator runs only at daemon-reload: edit the `.container` and restart WITHOUT `systemctl --user daemon-reload` first, and systemd re-runs the STALE generated ExecStart — nothing you edited applies. If the containers have no units at all (standalone; `podman-restart.service` restored them on manager cold-start), no restart is possible — register units first (see the units-exist rule), then restart via the unit. For genuinely standalone containers, stop + `podman rm -f` + start is the only apply path. After ANY apply, verify what actually runs with `podman inspect` (UsernsMode, Mounts) — the unit's active state does not tell you.
- **`systemctl --user disable --now` does not survive a reboot for a quadlet unit — disable the `.container` FILE too.** The quadlet generator re-runs at every boot and re-creates both the unit and its enablement from the `.container`'s `[Install]` section, so disabling the generated unit alone is silently reverted at the next boot (and `is-enabled` prints `generated` for these units, not `enabled`). To take a service down for a window: `mv ~/.config/containers/systemd/<name>.container <name>.container.disabled && systemctl --user daemon-reload` (quadlet ignores non-`.container` files), then verify `systemctl --user list-unit-files` no longer lists it and the published port is gone. Data volumes and the pulled image stay untouched — the inverse is rename back + daemon-reload + `enable --now`, so a trial-off window loses nothing. A teardown keep list therefore names the IMAGE, never a container: a quadlet unit runs `podman run --replace --rm`, so a stopped service leaves NO container object (`podman inspect <name>` answers 'no such container') — a keep-list review that expects a stopped container reads a false absence, and the restore recreates the container from the kept image.
- **Bind-mount FILES the container must READ need mapped-root readability — 0600 kills the run.** The host owner uid is UNMAPPED inside the rootless container (→ `nobody`), so a 0600 host-owned config file bind-mounted in is unreadable by container root and `podman run` dies instantly. Install mounted config files 0644 (a 0700 parent dir still gates access) or `podman unshare chown 0:0` them — the same mapping logic that requires `unshare chown` on the data DIR.
- **A root-run helper that writes into a container-mounted dir must chown its outputs to the service user, and loudly.** Root cron helpers (backup/checker scripts) that drop state inside a bind-mounted dir owned by the service user leave root-owned files under a umask-077 0700 dir the container cannot traverse — the app then stalls writing its own state and its status endpoints crash with Permission denied. `chown <user>:<user> <dir> <file>` immediately after the write, and log a WARN on failure instead of `2>/dev/null || true` — tolerance is correct only where the failing environment is CI (no such user exists); on the box, silence re-introduces the bug invisibly.
- **Shell values enter a kit script's embedded Python as ARGV under a QUOTED heredoc delimiter — never interpolated inline.** A shell boolean interpolated straight into the payload source produces the bash literals `true`/`false` as bare Python names, a NameError on EVERY run regardless of outcome — a nightly status writer can crash before its first successful write for its whole deployed life while its log shows only the traceback. Pass values as argv (`python3 - "$OUT" "$HEALTHY" <<'PY'` plus an `sys.argv` unpack), parse typed fields from their string form, and smoke-run the fragment against BOTH outcome values before deploying — one flag value exercised proves only that flag value's path.
- **A deploy gate that installs host scripts must verify the scripts' runtime dependencies in the identity each subprocess runs under — not just the script files and cron entries.** A backup script running as root that shells out via `runuser -u hermes -- <home>/.hermes/bin/proton` fails with `env: '<path>': No such file or directory` on every run when the binary exists only in a different tree (agent sandbox vs host, or wiped by an update): the gate read green, the rail looks configured, and nothing has ever uploaded. Gate rule: for every external binary a script invokes through a user switch, `runuser -u <user> -- test -x <path>` as a signed-off gate step, re-verified after any CLI update. And propagate across sibling kits: when one kit surfaces a missing shared dependency, audit every kit referencing the same path — a kit with a skip-if-missing guard stays dark silently for weeks while a fail-loud kit surfaces the same breakage in one night.
- **Podman does not create a missing bind-mount SOURCE directory — pre-create every new bind source before the first start.** A quadlet whose `Volume=` binds a host dir that does not exist yet fails the unit start with `statfs <path>: no such file or directory` and nothing else: the journal line is only 'control process exited with error code', the nologin service user cannot read its own journal for more, and a foreground `podman run` with the same mounts prints the real cause. Make each new bind source an explicit deploy step with the service user's ownership and intended mode (`install -d -o <user> -g <user> -m <mode> <dir>`) ordered BEFORE the recreate; an env-knob change that activates a fresh mount at start is exactly when this bites.
- **Rust binaries bundling jemalloc abort on the Pi 5's 16K-page kernel — a published arm64 image can be unrunnable no matter how correct the packaging is.** `<jemalloc>: Unsupported system page size` (exit 133 under systemd, nothing useful in logs) means the binary's jemalloc was compiled for 4K pages; page size is compile-time (tikv-jemalloc-sys still defaults to 4K on aarch64). Remedy is a REBUILD with `JEMALLOC_SYS_WITH_LG_PAGE=14` (16K granularity runs on 4K+16K hosts): in CI on the cross-compile (see `references/ci-arm64-images.md`), or natively on the host as the no-CI fallback (plain user systemd unit — also sidesteps the bind-mount id-mapping traps below). Verify with `getconf PAGESIZE` (16384 on a Pi 5) and run the built binary with a deliberately broken config — a clean config-error (not the jemalloc panic) proves the allocator works.
- **Quadlet hard-fails on unsupported keys — put resource limits in [Service], not [Container].** podman 5.4 (Debian 13) quadlet generator EXITS 1 and produces NO unit if any key is unsupported for its group (e.g. `MemoryMax` under `[Container]`) — `daemon-reload` stays silent, `systemctl --user start <name>.service` then says 'Unit not found'. Debug by running the generator manually: `/usr/lib/systemd/user-generators/podman-user-generator /tmp/qgen` (Debian name has dashes) — the parse error prints verbatim. Resource limits (MemoryMax, Restart, etc.) live in `[Service]`.
- **Apply a change to a LIVE unit through a gated script, not ad-hoc commands.** Order: backup the deployed file(s) under a known suffix → install the staged copy and `cmp` it byte-identical → `daemon-reload` → assert the change on the REGENERATED unit (`systemctl --user show -p <Property>`) BEFORE any restart → on gate failure restore the backups + `daemon-reload` and stop there → only then stop/`podman rm -f`/start (or unit restart per the first hard rule) with a readiness poll → after start re-verify on the unit AND at the cgroup (e.g. cpu.max) plus a fresh-ctr.log unknown-key count when a config file changed. Run the script to completion with stdout captured to a file and read the file after (a truncating reader in a pipe SIGPIPEs a mutating script mid-flight, leaving half-applied state). Rendering pair for CPU caps: `CPUQuota=200%` shows as `CPUQuotaPerSecUSec=2s` on the unit and `cpu.max` = `200000 100000` at the unit cgroup.
- **Containers running ≠ their quadlet units exist — confirm `systemctl --user list-unit-files` lists `<name>.service` before any restart.** A user manager that cold-starts late brings containers back via podman-restart.service from their OLD creation config (everything 'Up', zero mcp units), leaving every quadlet edit unapplied and `systemctl --user restart` dead with 'Unit not found'. Diagnose in order: the user journal for quadlet-generator lines, then a manual generator run with REAL argv — `/usr/lib/systemd/system-generators/podman-system-generator $XDG_RUNTIME_DIR/systemd/generator` (the `-dryrun` form is preview-only and scans `/etc` sources too; prune any non-mcp generated units from the output dir before daemon-reload so foreign system units don't leak into the user manager).
- **`useradd -r` allocates NO subuid/subgid ranges on Debian** (system uids sit below the auto-allocation threshold) → rootless podman image PULL fails at unpack: `potentially insufficient UIDs or GIDs available in user namespace (requested 0:<n> for /etc/…) … lchown …: invalid argument`. Fix: `sudo usermod --add-subuids <free-start>-<+65535> --add-subgids <same> <user>` (derive <free-start> from the LIVE /etc/subuid + /etc/subgid at install time — collect every allocated start, sort, and take the first gap a 65536-wide range fits; recorded 'next free' numbers in older docs go stale as later services allocate, and allocations are NOT uniform: early users sit at 100000, later ones wherever their install left them), then `sudo -u <user> -H podman system migrate`. Check `grep ^<user>: /etc/subuid /etc/subgid` in preflight. Mind the two range notations: the flag's argument is FIRST-LAST, while the /etc/subuid file's own format is start:count — re-typing the file's shape into the flag (`<start>:65536`) is rejected outright with 'invalid subordinate uid range'; spell the flag form `<start>-<last>` with last = start + 65535.
- **`sudo -u <user> -H` has no user bus.** Before `systemctl --user` or `podman` under sudo, export `XDG_RUNTIME_DIR=/run/user/$(id -u)` and `DBUS_SESSION_BUS_ADDRESS=unix:path=$XDG_RUNTIME_DIR/bus`, else daemon-reload/restart fails with a bus-connection error that looks like a unit bug. Copy the canonical bash -c form from the Standard verification loop below VERBATIM into every doc fence and kit script; hand-composed variants fail two ways: an inline `env DBUS_SESSION_BUS_ADDRESS=unix:path=$XDG_RUNTIME_DIR/bus` expands $XDG_RUNTIME_DIR in the CALLING shell (unset under sudo, yielding `unix:path=/bus`), and dropping the DBUS variable carries half the dance (a bus failure, or a stale inherited address silently hitting the wrong user's manager where a list-units read-back false-passes).
- **Quadlets live in the target user's `~/.config/containers/systemd/`**, owned by that user (0644). Copying with sudo chowns to root — fix ownership after every copy or the user unit generator may not read it. When the fix runs from an agent shell that cannot traverse the service user's 0700 home, the `*.container` glob EXPANDS TO NOTHING in that shell and the sudo chown silently no-ops ('No such file or directory' on the literal pattern) — make the glob expand with root's privileges instead: `sudo bash -c 'chown <user>:<user> <path>/*.container'`. And create the unit-dir tree with `mkdir -p` + an explicit `chown -R <user>:<user>` of the parent — `install -d -o <user>` applies its ownership only to the FINAL path component, so the intermediates it creates (`.config`, `.config/containers`) land root-owned and the generated-unit chain breaks downstream at the first elevated call.
- **Publish only loopback:** `PublishPort=127.0.0.1:<host>:<port>`. Never `0.0.0.0` for private services; front them with an auth-ingress (or bearer check) if anything else must reach them.
- **Keep quadlet `HealthCmd=` quote-free by default — quote NESTING ORDER decides survival.** The quadlet→podman→/bin/sh layering mangles an outer-double-quoted form like `python3 -c "import urllib.request; …"` into an unterminated string: every scheduled check exits 1 with `Syntax error: Unterminated quoted string` while the app keeps serving (FailingStreak climbs; the unit stays up — a failing healthcheck poisons `podman ps`/inspect status, it does not stop the container). Live-verified Nov 13 2026 (booklogr kit): the SAME python probe with outer SINGLE + inner DOUBLE quotes passes, so the survival rule is quote ORDER, not quote depth — when quoting is unavoidable use outer-single/inner-double, otherwise a bare binary probe (`curl -fsS http://127.0.0.1:5000/`, `wget -q --spider http://127.0.0.1:80/`) and confirm the probe binary exists in the image first (`podman exec <c> command -v curl wget`) — a probe naming a missing binary fails for the same shape of reason. Read the health result from `podman inspect <c> --format '{{.State.Health.Status}}'`, not the run command's stdout — this podman prints `unhealthy` on failure but NOTHING (empty line) on success. Diagnose in two steps: `podman inspect <c> --format '{{json .State.Health}}'` (the Log entries carry each check's Output and ExitCode), then the same command via `podman exec <c>` — exec exit 0 beside healthcheck exit 1 means the runner mangled the command, not the app. HealthCmd is a container-create-time setting: apply the fix per the first hard rule (daemon-reload, then a unit restart that re-creates the container); a restart without the fresh daemon-reload leaves the old probe running.
- **Env files live beside the unit's user** (`~/env/<name>.env`, 0600, owned by the service user), referenced via `EnvironmentFile=` or `Environment=%h/env/name.env` — never baked into the `.container` and never readable by other users. Paste credential values BARE — no surrounding quotes or trailing whitespace: quote characters ship into the credential itself and the upstream auth then fails with a 401 indistinguishable from a bad key, costing a replace-and-recreate round trip; the house env templates carry bare empty placeholders for exactly this reason. When the operator fills a secret into a kit env TEMPLATE that git tracks (the repo .gitignore covers only `state/`), `git update-index --skip-worktree <file>` right after the fill — otherwise the filled template sits one `git commit -a` away from leaking, and git pull on the dirty file can also wedge. Never trust a knob edit you have not read back: the file is not readable by the agent user, so verify every change with `sudo grep -n '^<KEY>='` — and `sed -i` exits 0 even when the pattern matches nothing, so a no-op replace reports success while the knob keeps its old value, which the server then treats as its off/disabled default.
- **Encrypted tarball backups pipe through age and restore through the identity file — a public key cannot decrypt.** Kit shape: stop the service, `tar -C <home> -czf - <data-dir> | age -r "$AGE_PUBKEY" > /srv/backups/<svc>/<STAMP>/<data>.tgz.age`, restart via an EXIT trap plus a serving check, prune to the N newest stamps; restore and restore-test decrypt with `age -d -i "$AGE_IDENTITY_FILE" <stamp> | tar -x` under the same elevation the tar used. Key material resolves through ONE operator env file `/etc/<svc>-backup.env` (root-only 0600, operator-created, holding `AGE_PUBKEY=` and `AGE_IDENTITY_FILE=` — the path of a root-only 0600 identity copy he extracts from the SOPS+age store; the keypair is generated once, the private half lives in the store, nothing commits key material): backup scripts source it for AGE_PUBKEY, restore/restore-test for AGE_IDENTITY_FILE. Name the stamp `<data>.tgz.age` and give EVERY consuming surface the matching decrypt form (backup mechanics, restore test's first step, production restore) — a mechanics line still writing a plaintext tar while the policy says encrypted is a self-contradiction that surfaces as a failed mandatory restore test, not a review nit. The plain-tarball variant (no age tier; kits without an offsite copy) keeps the same stop-copy-restart shape with the tarball direct to `/srv/backups/<svc>/<STAMP>/<data>.tgz`, and `/srv/backups/<svc>` is root-only 0700: EVERY consuming surface that reads it — the restore test's stamp-selection `ls` and its tar extract included, not just the backup script — runs those `/srv` reads under sudo, or the stamp variable comes back empty and the test cascades into missing-file errors that look like a broken backup.
- **The backup script's post-restart serving check must retry ALL errors, never sleep-then-single-curl.** Through a published port the same pasta mechanics as the boot gate apply (pasta accepts then resets while the app boots), so `sleep 3` + one bare curl fails the nightly BY CONSTRUCTION whenever the boot window exceeds the sleep — Spring-Boot-class restarts take tens of seconds, and the failure mode is a scary 'FAIL: not serving after backup' log line on a perfectly healthy instance (the app was already up when the check gave up). Shape: `curl -fsS --retry 30 --retry-delay 3 --retry-all-errors --retry-max-time 90 http://127.0.0.1:<port>/`. Propagate the lesson to the sibling kits in the same pass — a retry-shape fix applied to one kit's scripts while a sibling kit (or the design doc's embedded fences and evidence staging copies) keeps the dead form leaves the next review to catch it class-wide.
- **Harden each unit** (`MemoryMax=`, `CPUQuota=200%`, `Restart=on-failure`, `no-new-privileges`) — keeps a compromised container contained. JVM-class images get a generous INTERIM `MemoryMax` at authoring time and the real cap is measured at first boot: read the peak from `systemctl --user status`, set 1.5x that peak rounded up, and record the measurement date in the quadlet comment — a JVM image sized from a Flask-class estimate wedges under its first real load, and a cap set from one idle reading undersizes a JVM's working-set growth. CPUQuota=200% (2.0 cores) is the standing default for EVERY quadlet on this box: bake it into every new quadlet's `[Service]` and add it to existing ones on request — a unit-level cap also covers podman, conmon, and pasta, which a container-level flag leaves uncapped (rendering pair in the apply-gate rule above). **Scope each container's env file and mounts to what THAT container actually touches**: a serving process that never calls a provider gets no provider credential and no token-cache volume — put the credential in a separate env file only the one-shot sync job reads — and mounts it only reads go out `ro,Z`. Every unused credential and writable mount is blast radius a compromise inherits for free.
- **Multi-arch pulls on the Pi:** build arm64 images in GitHub Actions and pull by `:latest` on the Pi — never build images on the Pi itself. Heavy builds (large Rust trees) cross-compile natively on a standard amd64 runner (rustup target + `gcc-aarch64-linux-gnu` — no QEMU, emulated buildx crawls for hours); then assemble the runtime image COPY-only (no RUN steps in the arm64 stage, so buildx needs no emulation). Full recipe, C-dep sysroots, and run-monitoring pattern: `references/ci-arm64-images.md`. QEMU-buildx is fine only for light images.
- **Pin third-party images tag@digest — the digest is the immutability guarantee; the tag is decoration.** A mutable registry tag re-points silently: a later `podman pull` resolves whatever the publisher last pushed, and upstream tag discipline ("immutable X.Y.Z releases") is publisher convention, not a registry mechanism. Digest-pin every image from a publisher you do not control (docker.io upstream apps); self-built ghcr images may ride `:latest` because you are the publisher. Re-derive tag AND digest from the registry tag API at every update and record both in the kit change log. When a vendor security fix rides the toolchain (e.g. a Go stdlib advisory mitigated by a build-version bump), assert the binary's embedded build info post-deploy — an up-to-date app tag does not prove the image was built with a patched compiler. Read it IN-CONTAINER from the running process (`podman exec <c> grep -a 'go1\.' /proc/1/exe`): `podman cp` of an entrypoint-named path can ENOENT even while the kernel executes that exact binary (dual-layout images), so don't route the check through cp. Enforce the toolchain floor as an OSV affected-range query at the recorded version, never a version comparison — a strict `==` false-fails a newer patched toolchain, and a naive `>=` false-passes patch lines that carried the CVE above the floor version.
- **Derive a third-party image's layout from the IMAGE (inspect + the running container), not from either upstream manifest — a publisher's own manifests can contradict each other on the same tag.** One published image's entrypoint metadata named a runtime dir `/app-with-s/` while its own Dockerfile built everything under `/app-without-s/` and the compose example used the entrypoint's spelling — the image carried BOTH trees: an entrypoint-named runtime dir whose binary inode is not ls-visible or cp/exec-addressable after start, plus the layer tree the binary actually reads its assets from. Before mounting into or exec-ing any container path, derive the layout from the live artifacts: `podman image inspect <ref> --format '{{.Config.Entrypoint}} {{.Config.WorkingDir}}'`, `podman container inspect <c> --format '{{json .Mounts}} {{json .Config.Volumes}}'`, `podman exec <c> ls -la <dir>`; prefer reading the running binary in-container via `/proc/1/exe` over copying it out. Record the contradiction in the kit notes and re-check the layout at every image update — a future tag can unify the spelling and move the canonical paths, and the mounts/env must follow.
- **Fully qualify every image reference on this box — trixie podman ships NO unqualified-search registries.** A short name (`owner/repo:tag`) fails `podman pull` outright (`short-name ... did not resolve ... no unqualified-search registries are defined in /etc/containers/registries.conf`). It only resolves after a fully-qualified pull put the image in local storage, which masks the trap until the next auto-pull or a fresh host. Write `docker.io/owner/repo:tag` (or the real registry) in every quadlet `Image=`, pull command, and tool config default.
- **Nologin service users can't read their journal** (not in adm/systemd-journal, and user-unit logs land in the system journal) — failures in their units are invisible to `journalctl --user`. For services whose failures you must diagnose without sudo: set `StandardOutput=append:<file>` / `StandardError=append:<file>` in the unit and cap the file in the backup script (`truncate -s 5M`).
- **`cd /tmp` before `sudo -u <user> -H` or `runuser -u <user> --`**: both inherit the shell's cwd and chdir the target user into it — running from `~` fails with `cannot chdir to /home/hermes` (target user can't read the invoking user's home). Bake the `cd /tmp` INTO every kit script that runs podman under the elevation (first line after the `set` line) instead of relying on the caller's cwd: a script invoked from the kit dir under /home/hermes dies mid-flight at its first elevated podman call (`cannot chdir … Permission denied` → `Error: setting up the process`) with all earlier steps already applied. Stage scripts with `sudo cp -r ... /tmp/x && sudo chmod -R a+rX /tmp/x` and run from there.
- **Bind-mount writes under the default rootless userns are subuid/subgid-mapped, not the service user's ids** — check `/etc/subuid`-`/etc/subgid`: container-root writes to a mounted dir land owned by mapped sub-ids, so a mounted directory meant to be shared with OTHER host users (a spool shared agent↔container) is unreadable to them. A shared dir needs: `UserNS=keep-id:uid=0,gid=0` (container root inside; host-side creates still land as the service user) + `GroupAdd=keep-groups` + setgid on the dir, AND a one-time `chown -R <user>:<user>` of pre-existing container-written state (session/token dirs) BEFORE the first restart with keep-id — remapping orphans those files and the service silently loses its session/credentials. Spool/shared DIRS go out at 2771 (others = x-only, no listing): group propagation into the LIVE server process is unreliable (the user manager keeps its spawn-time group set; host groups unmapped in the userns display as `nogroup` inside), so a 2770 dir denies the server even when exec shells pass — x-only keeps known-path traversal while preserving filename privacy.
- **`GroupAdd=<numeric-gid>` does NOT grant a HOST group to a userns-mapped container — use `GroupAdd=keep-groups`.** A numeric --group-add adds the gid in the CONTAINER's namespace, which under keep-id reverse-maps into the service user's subgid range, while the kernel's permission check on the host-mounted dir reads the process's HOST-side supplementary groups — so the container stays 'other' and every host-group-perm access is denied (EACCES on `ls` of the mounted dir, while the mount itself succeeds). keep-groups passes the service user's real host supplementary groups through unmapped. It only carries groups live in the user's CURRENT session: `usermod -aG` reaches new sessions only, and the user manager plus its children keep their spawn-time group set — after adding a group, confirm the manager's session has it, or grant the access with a POSIX ACL on the dir instead, which sidesteps group propagation entirely. Scope keep-id to only the containers that need the shared mount: it collapses per-container uid isolation, so any container compromise reaches every other container's token/session files. And never land the chown without completing the keep-id recreate in the SAME operation — until the container is recreated, the still-default mapping cannot read 0600 user-owned files, so a chown alone cuts the running service off from its own credentials.
- **podman 5 `keep-id` maps the caller to the SAME uid inside the container (1002→1002), NOT to container-root.** Verify with `podman exec <c> id` — `uid=1002(...)` means the process is NOT root inside: it cannot traverse 0700 dirs owned by in-image uid 0 (a volume mounted under `/root` is unreachable even though mounted) and has no DAC-override on the image fs. Use `UserNS=keep-id:uid=0,gid=0` when the app needs container-root (full caps within its own namespace, e.g. a token path resolved under `/root` via `expanduser`) — host-side creates still land as the service user's uid, so the credential-isolation boundary stays the user namespace.
- **keep-id remaps the image filesystem out of the process's reach — any app that writes INSIDE the image fs dies with EACCES at its first such write.** Image layers unpacked under the DEFAULT mapping are owned by the subuid range; under plain `keep-id` those files map to OTHER in-container uids while the process runs as its own uid (not root — see the keep-id rule above), so it owns nothing in the image (bind mounts are unaffected — they keep host ownership and host-side permission checks). Symptom: the app crashes before serving, e.g. `uv run`: `Failed to initialize cache: failed to create directory <workdir>/.cache/uv: Permission denied`. Remedy: redirect app caches to a world-writable in-container path via env (`UV_CACHE_DIR=/tmp/uv-cache`) and stop the app from touching its baked artifacts (`uv run --no-sync`); when you control the image, bake both into it. Durable state belongs in bind mounts, never in the image layer.
- **Editing one quadlet among several: address it by exact FILENAME, expand `%h`, and verify the change on the CONTAINER, not the unit.** Content-greps over the quadlet dir (`grep -rl keyword | head -1`) have no defined match order, and unrelated quadlets legitimately contain the same keyword (peer lists, comments) — the edit silently lands on the wrong service. `%h` in a `Volume=` line is a systemd specifier, not a filesystem path — expand it to the user's home before any host-side `[ -e ]`/chown, or every existence check reports 'missing'. After identity/mount changes confirm what is actually live with `podman inspect <name> --format '{{.HostConfig.UsernsMode}}'` plus the container's Mounts — an 'active' unit does not tell you which config generation the container runs — verify with `podman inspect`, and apply per the first hard rule (daemon-reload, then unit restart when units exist; stop + `podman rm -f` + start for standalone).
- **Insert quadlet keys directly AFTER the `[Container]` header — never 'before the first non-[Container] section'.** Quadlet reads `UserNS=`/`GroupAdd=`/`Volume=` from the [Container] section only, and many quadlets open with comments then a `[Unit]` section, so an insert-before-next-section lands the keys outside every INI section: the generator silently emits NO unit for the file (daemon-reload says nothing; `start` says 'Unit not found'). Make the edit idempotent by DROPPING the keys wherever they sit and re-inserting after `[Container]`, not by conditionally appending.
- **A tmpfs mount starts EMPTY at every mount — anything binding paths under it dies at statfs until the subdirs exist.** After a reboot, a tmpfs-backed spool/config tree has no subdirs: every container bind of a subpath (and every agent sandbox spawn referencing one) fails exit 125 with `statfs <path>: no such file or directory` and no other symptom. Give each tmpfs mount a tmpfiles.d file (`d <dir> <mode> <owner> <group> - -` per subdir, applied once with `systemd-tmpfiles --create`) so systemd recreates them at boot before any unit or sandbox binds them.
- **A new service must be wired into BOTH install.sh and update.sh's service list — the two lists must cover the same set.** install.sh recreates every listed container; the rolling updater recreates only the services its list names, so a service absent from that list is silently skipped by every later update run while looking fully deployed. When taking over a deploy dir, diff the two lists against the deployed quadlets before trusting "everything updates itself".
- **Port collisions between quadlet templates never surface at PR review — only at install/start.** Two templates publishing the same host port each look correct in review; podman refuses the second bind at start with an opaque error. Before installing a new service, verify its host PublishPort is free across all deployed services (the port registry plus `ss -tln`), and keep the per-service port in the template consistent with every doc table that cites it.
- **A rolling-update script that copies repo templates over deployed quadlets applies the REPO state, not the live state — sync the templates before any recreate.** Keys added live after the initial deploy (a spool mount, userns mapping) vanish silently on the next image update: diff each `deploy/*.container` against its deployed copy and land the live-only keys in the repo first. And an updater that recreates only on image-ID change never re-applies a quadlet correction by itself — after correcting a bad recreate (e.g. one made from a stale staged copy), force it with stop + `podman rm -f` + start against the corrected file.
- **ghcr private→public flip: VERIFY before re-publishing.** Probe anonymously first — GET `https://ghcr.io/token?scope=repository:<owner>/<name>:pull`, then fetch the manifest with the returned bearer; the flip often takes effect immediately and the ~1h rebuild would be wasted. Re-run the publish workflow only if the probe still 403s. The visibility setting lives on the PACKAGE settings page (`users/<owner>/packages/container/<name>/settings`), not the repo's.
- **Reproduce repo CI lint locally before pushing a script into a pre-commit repo — CI lints ALL files, not just yours.** Run `pre-commit run --all-files` (the same hook set CI runs); when shfmt's `-d` diff disagrees with your formatting, apply it by running the cached shfmt binary with `-w` (find it under `~/.cache/pre-commit/**/bin/shfmt`) instead of hand-imitating its style; and mind bash precedence in one-liners — `A || B && C` runs C whenever A succeeds, so gate multi-statement hooks with real `if` blocks. Identical hooks locally = a cold CI runner cannot surprise you.
- **Verify a merged image BEFORE the host deploy by running it without a container runtime.** The agent sandbox has no docker/podman, but the image itself carries the runtime: pull the ghcr layers anonymously (registry v2 over urllib), extract, and boot the image's own interpreter plus baked venv — symlink the image-absolute prefix (`/app`), point `LD_LIBRARY_PATH` at the extracted libpython, and add the editable path-dep dir to `PYTHONPATH`. Run the transport ladder first (bearer 200/401, tools list), then the live read ladder with user-supplied credentials staged by the user in a file (never chat; `/home/mcp` is invisible from the sandbox, and only selected `/home/hermes` subpaths are bind-mounted — the working handoff is a 0600 file in `/srv/mcp_files/send/`). Full recipe: `references/pre-deploy-image-verification.md`. Layer compression varies: a BuildKit-built image can mix gzip and zstd layers, so install zstd before tar-extracting instead of assuming gzip throughout.

- **A tunnel-fronted service passes an ingress gate BEFORE its first boot — and the hostname shape is decided before any DNS record exists.** Cloudflare's Universal SSL covers the zone apex and FIRST-LEVEL subdomains only: a second-level name (`api.books.example.com` shape) gets no edge certificate and every TLS handshake dies at the edge before any ingress or origin logic runs — the record resolves, the connection never completes. Pick first-level names (or budget for the ACM add-on) at design time, not at the Block-C gate. `cloudflared tunnel route dns` creates proxied records but has NO delete verb — record deletion is a dashboard step, so treat record creation as deliberate and rename-resistant.
- **Classify the pre-boot ingress answer instead of debugging it — the four signatures each name their own fix.** With the containers not yet booted, hit both public URLs and expect a Cloudflare origin error (502-class): NXDOMAIN after the record exists = the local resolver cached the pre-creation negative (confirm via DoH JSON against 1.1.1.1, then `curl --resolve <host>:443:<edge-IP>`); TLS handshake alert = second-level name outside Universal SSL (rename first-level, don't debug); 404 with an EMPTY body = the tunnel's catch-all answered, so the ingress entries are missing or sit BELOW the catch-all rule (ordering is the usual miss); 502 = the rule matched and the origin is down, which is the correct pre-boot state.
- **After any re-bake that changes bytes under an UNCHANGED URL, purge the edge cache before trusting a browser check.** Apps that inject config into built assets at container start (env values sed'd into a JS bundle) change the bundle's BYTES while the hashed URL stays identical, and the CDN edge caches cacheable extensions for the origin's TTL (observed 4h): every client keeps loading the stale bake past `podman rm -f` + recreate, and a hard refresh does not help. Verify with a query-string cache-buster against the same URL, then purge the zone (or the asset URL) in the dashboard, or wait out the TTL.

## Standard verification loop (run as the service user)

```bash
sudo -u <user> -H bash -c 'export XDG_RUNTIME_DIR=/run/user/$(id -u); \
  DBUS_SESSION_BUS_ADDRESS=unix:path=$XDG_RUNTIME_DIR/bus; \
  systemctl --user daemon-reload && systemctl --user start <name>.service'
# then: correct bearer -> 200, wrong bearer -> 401 (if the service gates on a bearer)
```

Expect the first readiness probe to 000 (container still initializing); retry a few times before declaring failure — a slow start is normal, a 401-on-correct-bearer is a real bug.

- **A boot gate against a PUBLISHED port must retry ALL errors, not just connrefused — pasta accepts the TCP connection immediately and then RESETS it while a slow app boots.** Through `PublishPort=`, the pasta listener accepts the connection before the container's app listens, so a connrefused-only retry (`--retry-connrefused`) never fires: the gate dies with `curl (56) Recv failure: Connection reset by peer` ~20 s into a Spring-Boot-class boot that serves at ~40 s. Bake the retry-all form into EVERY kit curl against a published port AT AUTHORING TIME — boot gates, backup-script serving checks, restore-test serving checks, and monitoring probes all hit the same mechanics; retrofitting after the first boot fails costs a kit PR + doc-fence + staging re-sync per curl. Shape: `--retry-all-errors --retry 20 --retry-delay 3 --retry-max-time 120`; JVM-class images get a generous HealthStartPeriod to match. Two corollaries: (1) a single visible `curl: (56)` line with retries behind it is NOT a failure — curl prints the failed attempt's error while later attempts succeed, so judge the gate by the pass/fail line the script prints after the curl, never by the leaked curl error alone; (2) a probe bracketed by the `time` shell keyword dies under /bin/sh with `time: not found` before the command runs — date-bracket instead, which also captures the exit code (the `time` keyword rule above).
- **A root-run service's post-restart FAIL lines are not necessarily the app's fault — check the INSTALLED script's version, not the repo's.** A serving-check FAIL within seconds of the restart (not after the retry budget) means the installed script predates the retry-shape fix: the installed copy came from the kit state at its last `install` run, and a later kit PR only fixes the repo. `install -m 755 <kit>/<script> /usr/local/sbin/<script>` again after the pull before blaming the app — and when the script is being retired anyway, the FAIL is moot and the tarball (taken before the restart) is the record that matters.
- **Rollback a service whose rollback path lives in a TUNNEL-RESTART step: check the other tunnel sites immediately after any cloudflared restart.** The tunnel fronts every site at once; an edit+restart can leave a sibling hostname on a stale catch-all or a dead origin while the target service works. A post-restart verification loop hits ALL tunnel hostnames (the edited one AND the previously-live ones), not just the edited one — a 404/502 on a hostname nobody edited is caught in seconds instead of by the next user.

## Updating a service (per-container, no full reinstall)

1. Push the new image (CI), wait for the workflow that PUSHES to finish — push-gated CI (push-to-main only) leaves a green PR-run build meaningless for the tag; confirm the merge-triggered run completed, or the pulled digest changed, before pulling. A pull that lands before the push gets the OLD image, and a recreate-on-image-change updater then reports 'already on the latest image' and silently recreates nothing. Diagnose a suspect "already latest" by comparing the registry's CURRENT latest against the running container: token via `curl -s "https://ghcr.io/token?scope=repository:<owner>/<name>:pull"`, then the OCI index (`Accept: application/vnd.oci.image.index.v1+json`), then the arm64 leaf's config digest — on this podman that digest IS the image ID, so a mismatch with `podman inspect <c> --format '{{.Image}}'` means the recreate never ran or CI has not built the merged code yet (the merge-to-image build is asynchronous).
2. `podman pull <image>` as the service user.
3. `podman rm -f <container>`, copy the updated `.container` if it changed (fix ownership), daemon-reload, start.
4. Re-verify 200/401 and a real read.

## Debugging

- **`systemctl --user start` returns BEFORE `podman run` finishes (Type=simple)** — a failed run surfaces only afterwards, and NOT in `podman logs` (the container was never created: 'no container with name'). After start, poll the published port; on timeout dump `systemctl --user status <name>.service -l` + `journalctl --user -u <name> -n 40` — those carry the real podman error. Bake the poll+dump into bootstrap scripts instead of trusting start's exit code.
- Unit logs: `journalctl --user -u <name>.service` (as the service user, with the bus env prelude).
- `podman logs` routes CONTAINER stderr to PODMAN stderr — services that log to stderr (most Rust daemons) have their critical lines on the pipe's stderr stream; grepping container logs with `2>/dev/null` silently deletes exactly those lines while a `2>&1` grep shows them. When a log-extraction 'finds nothing' but a diagnostic dump of the same stream shows the line, suspect stream routing first.
- **`podman run --rm` in a unit's ExecStart forwards the CONTAINER's exit code as the unit's Main PID status** — `status=2` is the app's own usage/argparse failure, not a podman flag error; the app's stderr is in `journalctl --user -u <unit>`. A crash loop with `--rm` + `ExecStopPost rm` leaves NO container object between cycles: 'unit activating/active but `podman exec` says no such container' means the app is crashing, and the run-to-rm gap is when `ps`/`inspect`/`events` go empty. Treat 'unit active but container missing' as a failure with full dump (ps -a, unit journal, `podman events`, container logs), and poll readiness with `is-active --quiet` up to ~60 s ('activating' for tens of seconds is normal — image prep/pull), re-checking 2 s after 'active' to catch instant crashes.
- **`time` is a shell keyword, not a binary — in a minimal container it kills the probe before the command runs.** `podman exec <c> sh -c 'time <cmd>'` under dash (/bin/sh in Debian/Ubuntu-based runtime images) aborts with `sh: 1: time: not found` and <cmd> never executes — a probe that returns only that line tested NOTHING, not a slow command. Date-bracket instead (it also captures the exit code): `S=$(date +%s); <cmd>; RC=$?; E=$(date +%s); echo "exit=$RC elapsed=$((E-S))s"`.
- Container state: `podman inspect <name> --format '{{.Config.Cmd}}'`, `podman logs <name>`.
- **Every podman verb that addresses a container (cp, exec, logs, inspect, healthcheck run) must run under the OWNING user's elevation dance — rootless podman storage is per-user.** The same command from another user's shell fails 'no such container' even though the container is up (their podman sees a different store). Any kit script, doc sketch, or diagnostic that touches a service container carries the full `sudo -u <user> -H env XDG_RUNTIME_DIR=/run/user/<UID> ...` prefix, not just the systemctl lines — a bare `podman cp` in a runbook silently targets the wrong user's storage.
- 'Service starts but port dead': check the PublishPort binds 127.0.0.1 and the app listens on 0.0.0.0 INSIDE the container.
- 'Daemon-reload fails under sudo': missing bus env, not a unit error.
- **Sampling a quadlet unit's resource use via cgroups: the containerized process's /proc/<pid>/cgroup resolves to the libpod-payload CHILD, not the unit.** Resource limits and throttling counters (cpu.max, cpu.stat nr_throttled) live at the unit cgroup, the payload's parent. Strip the payload suffix (`CG=${CG%/libpod-payload-*}`) before reading cpu.stat: a payload-level sample undercounts the unit by the podman/conmon/pasta share (measured ~44 percent of the unit during network-heavy churn), and unit-level throttling never appears in the payload's counters. And a unit restart resets the unit cgroup's cpu.stat/memory.events counters entirely (fresh cgroup instance): any delta or event count spanning a restart — OOM hunts, throttle attribution — comes from the container's exit evidence (`podman events` with an RFC3339 timestamp; bare HH:MM fails to parse) plus the exit code, not post-restart unit counters.
- **Debug the user generator in the TARGET user's identity.** The generator reads the invoking user's ~/.config/containers, so a bare invocation debugs the wrong user's units: run it as the service user (`sudo -u <user> ... /usr/lib/systemd/user-generators/podman-user-generator <outdir>`) with `mkdir -p` on the output dir first.
- **For a container with no usable journal, read the podman ctr.log file directly**: `~/.local/share/containers/storage/overlay-containers/*/userdata/ctr.log`, newest file first (`ls -t ... | head -1`), extracted with `2>&1` (see the stream-routing rule above). A recreated container writes a FRESH ctr.log and `podman rm -f` deletes the old one — for post-restart diagnostics grep the newest file, and grep the OLD one BEFORE any restart if you need pre-restart lines.
